# /design の各フェーズ詳細手順

> SKILL.md フェーズ 1-4 の調査・確認手順、任意セクション該当判定ルール、確信度評価の指針。

## フェーズ 1: コンテキスト読み込み

- [ ] 入口で解決したコンテキストファイル（`../../brief/reference/entry.md`）を読み込み、要件を把握
- [ ] ファイル参照（`file_path:line_number`）やコンテキスト情報を抽出
- [ ] 要件を「機能要件」「非機能要件」「制約事項」に分類
- [ ] `./tmp/research.md` が存在する場合、調査結果として追加コンテキストに含める
- [ ] `openspec/specs/` が存在する場合、関連する既存仕様を参照し、新計画との整合性を考慮
- [ ] `openspec/config.yaml` が存在する場合、プロジェクト固有のルールを参照
- [ ] **モード**: コンテキストファイルの frontmatter に `mode:` がある時、正典（`../../brief/reference/modes.md`）の解決規則でモードを読み、結果を 1 行報告する。既知のモードに解決したら `modes/<mode>.md` の `## design の観点` をフェーズ 4 で使い、plan.md のタイトル直下に `モード: <mode>` を転記する（`/implement` はコンテキストファイルを読まず plan.md だけを入力にするため）。未知の値は転記しない

## フェーズ 1.2: 業務シナリオの確認

`./tmp/scenario.md` の 3 状態で分岐する。状態の定義・記述書式・発火判定の基準は `../../grill/reference/business-scenario.md`（正典）にあり、ここでは再宣言しない。**本フェーズは読み込みと生成だけを行う**（入口・出口の割り当てはフェーズ 4）。

**どの状態かの判定は正典の評価順に従う**（下表の行順は評価順ではなく、状態ごとの手順を並べたもの）。

| 状態 | 手順 |
|------|------|
| **S-n あり** | 読み、frontmatter の `title` が今回の題材と一致するかを確認する。不一致なら上書き前に 1 問確認する（`grill/SKILL.md` の入力節と同じ規約。前題材の残骸を今回のシナリオと誤認しないため）。**「Notion 反映」欄の反映先 URL が `未定` または未記入なら、1 問で尋ねて記入する**（grill Phase 0 が URL を得られないまま閉じた場合の再取得） |
| **シナリオ不要** | 業務シナリオ不要と判定済みとして扱い、以降の割り当てと DoD の AC 生成を行わない |
| **不在** | **まず正典の判定 1・2 を当てる**（grill Phase 0 と同一の基準）。いずれかが Yes → 正典に従い `S-n` を立て、**反映先 URL を 1 問で尋ねて「Notion 反映」欄に記入する**（URL を持たなければ `未定` と明記。grill Phase 0 と同じ生産手順で、フォールバック経路でも URL の生産者を欠かさない）。いずれも No → 正典の `## 判定: シナリオ不要` の書式で 1 ブロックだけを書いて閉じる |

**不在のときに無条件で `S-n` を立てない理由**: 純技術的な内部変更に業務シナリオを強制すると、埋められない項目が『オープン質問』に積まれるか、形式だけ埋めた `S-n` が生まれる。後者は `/implement` の Phase 4 が「S-n あり」の経路として扱うため、**不要な確認依頼と未回答クローズの記録が連鎖する**。`grill/SKILL.md` の観点節（純技術的な内部変更で業務観点を機械的に全件問わない）と揃える。

## フェーズ 1.5: 既存 plan.md の確認

`./tmp/plan.md` が既に存在する場合、**プロセスを即座に停止**してユーザーに確認:

- 既存 plan.md の概要（タイトル・ステップ数）を表示
- 選択肢を提示:
  1. **上書き**: 既存 plan.md を破棄し新計画で置き換え
  2. **追記**: 既存末尾に新計画を追加（複数機能を 1 ファイル管理する場合）
  3. **キャンセル**: 計画作成を中止

ユーザー選択に従って後続フェーズを実行。

## フェーズ 1.6: Notion 価値ページへの反映

**このフェーズがフェーズ 1.5 の後にあるのは**、Notion への書き込みが Git で戻せない副作用だからである。フェーズ 1.5 でユーザーがキャンセルを選ぶ可能性がある間は、外部システムへ書き込まない。

**発火条件**: `./tmp/scenario.md` に価値ページ URL が書かれている場合のみ。URL が無ければ「反映先 URL 未記入」として『オープン質問』へ上げ、**書き込まない**。

0. **冪等性の確認** — 「Notion 反映」欄に反映日が既に入っている場合、前回反映からの差分を確認する。**差分が無ければスキップ**する（同じ内容を 2 度書き込まない）
1. **提示** — 反映する差分をユーザーへ提示して**承認**を取る。**承認が得られなかった場合は書き込まず、「Notion 反映」欄に未反映の理由を記録して後続フェーズへ進む**（承認しない判断は正当なので `/design` 自体は止めない）
2. **書き込み** — `notion-update-page` を使う。`colspan` / `rowspan` は使わず、置換は `<tr>`〜`</tr>` か `<td>…</td>` の単位で閉じる
3. **読み直し** — `notion-fetch` で読み直す（省略しない）。書込前と**列数を照合する**
   - 一致 → 反映完了。`./tmp/scenario.md` の「Notion 反映」欄に反映日と確認依頼先を記入する
   - **不一致** → 反映を完了扱いにせず、欠損内容をユーザーへ即時報告し、Notion のページ履歴からの**復元**を促す

**なぜ読み直しが必須か**: API は列が消えても成功応答を返すため、書き込み結果から欠損を検知する手段が無い（実績: 同一セッションで 2 回発生し、3 列と 13 行分の 1 列が消失）。Notion への書き込みは `/design` が持つ唯一の **Git で戻せない副作用**であり、成功経路だけを定義すると復旧の指示が誰にも残らない。

## フェーズ 2: ユーザー確認（必要に応じて）

以下を検出した場合、**プロセスを即座に停止**してユーザーに報告:

- **曖昧な要件**: 複数解釈が可能 → どの要件が曖昧かを提示し質問
- **矛盾する要件**: 整合性が取れない → 矛盾する要件を並べて優先度確認
- **技術的制約が不明**: 実装方式に影響する制約が特定できない → 不足情報を列挙

複数の問題がある場合:

```
## 問題 1: [問題の要約]
[該当する要件の引用と、何が問題なのかの説明]

## 問題 2: [問題の要約]
...
```

サブエージェントを使って**並列に**調査:

## フェーズ 4: 実装計画の策定

### 基本作業

- [ ] 要件を実装ステップに分解
- [ ] 各ステップの影響範囲・変更対象ファイルを特定
- [ ] テスト方針を明記（TDD で書くべきテストの種類: 単体 / 統合）
- [ ] 各ステップの依存関係と実行順序を決定
- [ ] **要件カバレッジを検証**: すべての要件が実装ステップでカバーされているか確認
- [ ] **モードの観点を反映**: 既知のモードに解決した場合、`## design の観点` の 3 ラベルを反映する — 先行ステップの候補は実装ステップの先頭に、重点を置くセクションは該当セクション（またはフェーズ 4 のチェックカテゴリ）に、アンチゴールに加える項目はアンチゴールに。採らない候補は「検討した代替案」に理由を 1 行書く（観点は候補であって必須ではないため）
- [ ] **業務シナリオの入口・出口をステップへ割り当て**: `./tmp/scenario.md` に `S-n` がある場合、各入口・各出口を担当するステップを明示する（入口が 3 つなら 3 つとも）。入口の一部だけを直した実装は、残りの経路で QA に落ちる。割り当てが漏れた入口・出口は『オープン質問』へ上げる
- [ ] **業務シナリオの DoD を AC にする**: `./tmp/scenario.md` に `S-n` がある計画では、受入条件に「**Notion 反映と確認依頼を済ませ、未回答なら開発者が明示的に閉じた**」AC を **`S-n` ごとに 1 つ**生成する（`/implement` の Phase 4 がこの欄を検査するため、AC が無いと検査対象が計画に現れない）。1 つの AC に畳まないのは、`S-1` / `S-2` が併存する計画で**どちらの記録欄が未記入か**を AC が表現できなくなるため
- [ ] **verification.md の要否判定**: ユーザー経路から到達できる機能を実装する計画では、対象 capability の `openspec/specs/<capability>/verification.md` を新規作成 or 更新するステップを含める（実装直後の検証を計画に載せないと、実機での確認が「余裕があればやること」に落ちる）

### プロジェクト固有規約の参照

階層的フォールバックで規約を取得し、計画策定時の考慮事項として反映する。該当する規約が見つかったら、それ以降のフォールバックは行わない:

1. **リポジトリ root の `CLAUDE.md`** に `## プロジェクト固有規約` セクション（または `## プロジェクト固有規約（/design 用）`）があれば、そのセクション内容を参照
2. **`openspec/config.yaml`** に `rules.design` キーがあれば、その値を参照（既存の `/spec-propose` と整合）
3. どちらも見つからなければ、汎用 best practices（DRY / YAGNI / SOLID / 「シンプルさ第一・最小限のインパクト」）を適用

#### `## プロジェクト固有規約` セクションのフォーマット（推奨）

H2 ヘッダ + 太字キー + 箇条書きの自由文:

```markdown
## プロジェクト固有規約（/design 用）

- **アーキテクチャ**: レイヤード, CQRS
- **エラーハンドリング**: Result 型, ErrorWithDisplayMessages
- **多言語対応**: en, ja, id, vn, th, zhCN
- **クロステナントアクセス防止**: 必須
```

代替: コードブロック内 YAML 形式（`architecture: [layered, cqrs]` のような構造化キー）も受け付ける。フォーマット崩れや内容不在の場合は次の階層へフォールバック。

### 任意セクションの該当判定

フェーズ 5 テンプレートには `[該当時]` 指示の任意セクションがある。以下の判定で出力セクションを決定する。該当しない場合はセクションごと省略する（空セクションを残さない）:

- **公開インターフェース**: 公開 API・型エクスポート・DB スキーマのいずれかが変わる場合に出力
- **データモデル変更**: DB マイグレーションが発生する場合に出力
- **ロールバック方針**: 本番影響のある変更（API 変更・データ移行等）の場合に出力
- **全体テスト戦略**: E2E / CI パイプライン / テスト環境構築 / テストデータ戦略 など、ステップ横断のテスト事項がある場合に出力（ステップ内「テスト方針」と切り分け）
- **マイルストーン**: 実装ステップが 10 を超える、または段階リリースの単位がある場合に出力

### 確信度評価

各根本原因 / 主要設計判断について必須記述:

- `**確信度: high / medium / low**`
- **low** の場合は「**検証ステップ**」を併記必須（実コード照合、実行確認、調査エージェント起動など）
- 「low なまま実装に進まない」原則を徹底し、検証ステップの結果で再評価

## 構造的欠陥防止チェックリスト（フェーズ 4 必須）

> **SSOT 宣言**: 本セクションは `/design` フェーズ 4、`/revise` フェーズ 6.5、`/review-plan` フェーズ 3（観点 3.2・3.3）の 3 箇所から参照される single source of truth。テンプレートと [BAD]/[GOOD] 例の重複コピーは禁止。他 SKILL.md からは 1 行リンクで誘導する。

同じ抽象度でレビューを反復しても発見されにくい 7 種の構造的欠陥に対し、計画段階で防衛機構として 7 カテゴリのチェックを必須化する。各カテゴリは「いつ書くか / [BAD] / [GOOD] / 該当しない場合」の 4 ブロックで記述する（カテゴリ 3 のみ、並列実行特有のリスクを補うため「追加確認事項」ブロックを加えている）。

### 1. 統合点トレース

**いつ書くか**: 計画内に「skip」「削除」「短絡」「フォールバック」を含む step がある場合（既存の処理経路を省略する提案）。

**[BAD]** — 副作用が追跡されていない。downstream の何が壊れるか不明。

```
ステップ 3: 既存の validate ステップを skip する（理由: 高速化）
```

**[GOOD]**

```
ステップ 3: 既存の validate ステップを skip する
  副作用追跡:
    - downstream A の前提条件 X が満たされなくなる → ステップ 4 で代替検証を追加
    - エラー報告経路 B でのエラーコード分布が変わる → 監視アラートの閾値見直し（F-2 で起票）
    - 既存テスト T1, T2 が validate を前提としている → ステップ 5 で再設計
```

**該当しない場合**: 新規処理のみで既存経路の skip / 削除 / 短絡を含まない場合は「該当なし」と明記。

### 2. Decision 間相互整合性マトリクス

**いつ書くか**: 計画内で Decision（設計判断）を 3 個以上立てた場合。

**[BAD]** — Decision 間の前提・衝突関係が見えない。

```
- Decision 1: キャッシュは Redis を使う
- Decision 2: マルチテナント分離は DB レベルで行う
- Decision 3: バックグラウンドジョブは BullMQ で実行
```

**[GOOD]**

| Decision | 前提 | 衝突しない相手 | 責任分界 |
|----------|------|-----------------|----------|
| 1. Redis キャッシュ | Redis インスタンスがテナント単位で分離されている | Decision 2 (DB マルチテナント分離と独立) | キャッシュ層は tenant_id プレフィックスで分離 |
| 2. DB マルチテナント分離 | row-level security 有効 | Decision 1 (Redis は別チャネル) | DB クエリ層で必須適用 |
| 3. BullMQ ジョブ | Redis インスタンスが必要 | Decision 1 と **Redis インスタンス共有** | キャッシュ用 DB と job queue 用 DB を分離（DB 0 / DB 1） |

**該当しない場合**: Decision が 2 個以下なら「該当なし」。ただし 2 個の Decision に明らかな相互依存がある場合はマトリクスを書く。

### 3. 並列性マトリクス

**いつ書くか**: 並列実行（並列 step / Step Functions Map state / Promise.all / worker pool / multi-tenant 同時アクセス）を伴う feature を計画する場合。

**[BAD]** — 共有リソースと並列度が未定義。競合状態の可能性が見えない。

```
ステップ 5: ユーザーごとに並列で集計処理を実行する
```

**[GOOD]**

| 共有リソース | 並列度 | 衝突パターン | 対処 |
|--------------|--------|-------------|------|
| DB connection pool (max 20) | ユーザー数 × ステップ数 | 並列 100 → connection 不足 | semaphore で 同時実行 15 に制限 |
| S3 bucket prefix `summary/` | ユーザー数 | 同一 prefix 書き込み → eventual consistency 問題 | prefix を `summary/{user_id}/` に変更 |
| Stripe API レート制限 (100 req/s) | ユーザー数 | 並列 200 → 429 | exponential backoff + jitter |

**該当しない場合**: 直列処理のみ / 並列実行が独立リソースのみ（in-memory 計算など）の場合は「該当なし」と明記。

**追加確認事項**:
- **安全性根拠の区別**: 「安全」の根拠が排他制御（`SELECT ... FOR UPDATE` 等のロック、トランザクション分離）によるものか、メッセージ順序保証（SQS FIFO の `messageGroupId` 等）のみに依存していないかを明示する。後者のみを根拠にしている場合、エントリポイントを跨いだ排他は保証されないため `/review-plan` で Critical 扱いとする。
- **書き込みエントリポイントの完備性**: 同じ共有リソースに書き込みうる全コードパス（= 書き込みエントリポイント。push/pull、CRUD 各操作、正常系/フォールバック分岐等）を洗い出し、対策範囲がその全てをカバーするかを一覧で示す。1 系統のみの対策で「対応済み」と書かない。

### 4. 「変更不要」「透過」断言の根拠付け

**いつ書くか**: 計画内に「変更不要」「透過」「影響なし」「既存のまま」と書く箇所がある場合。

**[BAD]** — 根拠が無い。後から見ると本当に確認したのか判別不能。

```
- 既存の AuthMiddleware は **変更不要** （新機能から透過的に使える）
```

**[GOOD]**

```
- 既存の AuthMiddleware は **変更不要**
  - 根拠: `grep -rn "AuthMiddleware" src/` で利用箇所 12 件を確認、すべて `req.user` 経由でのみアクセスしており、新機能の追加属性 `req.user.workspaceId` は middleware を経由しないため衝突なし
  - 確認した実装: `src/middleware/auth.ts:L42` `next()` 呼び出し時点で req.user は他フィールドを保持する
```

**該当しない場合**: 「変更不要」「透過」断言を計画内で行わなかった場合は「該当なし」。

### 5. HTTP / API contract concrete 化

**いつ書くか**: 計画内で API・RPC・コマンドインターフェースを定義する場合。抽象 IF（型シグネチャ・OpenAPI 概略・自然言語の API 説明）を含む。

**[BAD]** — method / path / header / body / response の 5 要素が揃っておらず、実装時の解釈ぶれが発生する。

```
- 新規エンドポイント: POST /workspaces/:id/members を追加する
```

**[GOOD]**

```
POST /workspaces/:id/members
  Headers:
    Authorization: Bearer <jwt>
    Content-Type: application/json
  Body:
    { "email": "user@example.com", "role": "editor" }
  Response (201):
    { "memberId": "mem_...", "invitedAt": "2026-05-26T10:00:00Z" }
  Response (409 if already member):
    { "error": "ALREADY_MEMBER", "memberId": "mem_..." }

  curl で叩ける具体例:
    curl -X POST https://api.example.com/workspaces/ws_123/members \
      -H "Authorization: Bearer $JWT" -H "Content-Type: application/json" \
      -d '{"email":"a@example.com","role":"editor"}'
```

**該当しない場合**: API・RPC・コマンドインターフェースを定義しない計画（純粋な内部リファクタリング・ドキュメント変更等）は「該当なし」。

### 6. 完了パスツリー

**いつ書くか**: feature 完了パスが複数分岐する場合（成功 / 失敗 / partial / リトライ / キャンセル など）。finalize 系のパスが複数ある feature 全般。

**[BAD]** — 完了パスの分岐が網羅されていない。AC との対応が不明。

```
- ステップ 7: ジョブ完了処理を実装する
```

**[GOOD]**

```
ジョブ完了パスツリー:

complete()
├── success
│   ├── full → AC-3 (全件処理成功)
│   └── partial (一部失敗あり) → AC-4 (skipped 件数を report に含む)
├── failure
│   ├── retryable (network / 5xx) → AC-5 (3 回までリトライ後 dead-letter)
│   └── unrecoverable (validation / 4xx) → AC-6 (即座に dead-letter)
└── cancelled (user / timeout) → AC-7 (中間状態を rollback)
```

各葉に AC を割り当て、`## 受入条件` で網羅性を保証する。

**該当しない場合**: 完了パスが単一（成功か失敗のみで、partial や retryable / unrecoverable の分岐がない）の場合は「該当なし」。

### 7. 対称性チェック

**いつ書くか**: 計画内で並行する分岐・CTE・実装パス（成功系/失敗系で類似処理を別々に持つ、複数エンティティに同種ロジックを適用する等）が存在する場合。

**[BAD]** — 対称な経路の一方だけ変更され、もう一方への波及確認がない。

```
- 注文（Order）の合計金額計算に割引ロジックを追加する
```

**[GOOD]**

```
対称性チェック: 同種の集計ロジックが見積り（Quote）側にも存在する
  → 同様の変更が必要か確認し、不要ならアンチゴールに明記
```

**該当しない場合**: 並行する分岐・CTE・実装パスを持たない単一経路のみの変更の場合は「該当なし」。
