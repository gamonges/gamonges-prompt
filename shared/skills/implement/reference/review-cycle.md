# レビュー・修正サイクル詳細（implement skill 補助）

サイクルに入ったら、**レビュー → 修正** を **修正が出なくなるまで反復**する。テストの照合（`./test-audit-flow.md` の ③）はサイクルの外にあり、3.3 で常に行う。

- **参加条件**: 次のどれかに当たるステップ（Phase 2 で決め、計画に `セルフレビュー: 回す` と書く。基準の正本はここだけ）と、Phase 6。3.3 で回さなかったステップは Phase 6 が受け持つ
  - (a) 外から見える契約（公開 API・DB スキーマ・認可・データ移行）に触れる
  - (b) 並行性・トランザクション境界に触れる
  - (c) 計画でそのステップの確信度が low
  - (d) Medium/Large ステップ（変更ファイル >= 3。`./agent-selection.md` の区分）
- **開始トリガー**: 参加したステップの実装が完了しテストが通った時点（Phase 6 では Phase 5.5 の完了後）
- **反復トリガー**: レビューで修正が発生した場合、修正後に再レビューする
- **完了条件**: レビューで修正が出なくなった時点（修正ゼロなら 1 巡で完了）
- **打ち切り**: 3 巡しても収束しない場合は中断し、残る指摘と収束しない理由をユーザーに報告する

## レビューサイクルの手順

```
ステップ実装完了（3.3 で回すと決めたとき）/ Phase 6
    ↓
【レビュー】セルフレビュー実行 ←──────────┐
    ↓                                     │
 ┌─修正発生あり─→【修正】指摘事項を修正──┘
 │                （3 巡で収束しなければ打ち切り、状況を報告）
 └─修正発生なし──→
                  ↓
        サイクル完了（3.3 なら 3.5 へ、Phase 6 なら Phase 7 へ）
```

### 発動条件の判定

「修正発生あり」とは以下のいずれかに該当する場合:

- レビュー観点チェックリストで 1 件以上の問題を検出
- リファクタリングが必要と判断
- テストの追加・修正・統合・削除が必要と判断
- lint / format 違反を発見

テスト主担当表の更新だけでは「修正発生あり」に数えない（記録の更新でレビューを反復させないため。`./test-audit-flow.md` の ③）。

「修正発生なし」(= 1 回で完了) は:

- すべてのレビュー観点が問題なし
- 軽微な改善点のみで、修正コストが利益を上回らないと判断

## レビュー観点チェックリスト

各レビューでは以下の観点を確認する:

1. **コード品質**
   - 型安全性（any 型の使用禁止）
   - 命名規則の遵守
   - 単一責任原則の遵守
   - 不要なコメントの削除

2. **エラーハンドリング**
   - サイレント失敗がないか
   - 適切なエラーメッセージ
   - エッジケースの考慮

3. **プロジェクト規約**
   - CLAUDE.md の規約遵守
   - .cursor/rules/ の規約遵守
   - 既存コードパターンとの整合性
   - 責務（ロック・書き込み・関数）を別の場所へ移したら、移す前のシンボル名・場所を**コメントも含めて** grep し、移した責務（ロック順・作るもの・理由）を語る参照を直す。宣言（interface・abstract）と実装の両方のコメントを見る（シンボルが残ったまま意味だけ古くなるので、存在確認では捕まらない）
   - 関数や型を足す前に、同じ形の既存のもの（変換関数・共通の読み出し・型の慣習）を探して使う。写す・作り直すなら、その理由を書く。既存が各所に写す慣習なら、それに従うのは「使う」とみなす

4. **テスト**
   - テストカバレッジの確認
   - テストケースの網羅性
   - テストの可読性
   - 偽陽性: 実装を壊してもテストが通り続けないか（アサーション不足の兆候）
   - 偽陰性: 期待値が仕様に基づいているか、過剰な厳密さで脆くなっていないか
   - 書くべきか・junk でないか・主担当表と一致するか — 照合そのものはサイクルの外（3.3 の `./test-audit-flow.md` ③、Phase 6 では ④ の変更監査）で行う。ここでは済んでいるかだけを確かめ、当て直さない

5. **外から見える契約**
   - 新しく返すステータス・エラーを、API ドキュメント（DTO・OpenAPI・JSDoc・contract など、その repo で API の契約を書く場所）に書いたか。書く場所が無ければ該当なし
   - 計画やタスク表（openspec の `tasks.md` など）の「残り」を、この実装で終えた分だけ更新したか。全部終えた項目はチェックを付け、一部だけ終えた項目は残りを、引き継いだ項目は引き継ぎ先を注記する。タスク表を別のブランチで直す方針なら、この差分に無いことを理由に外さず、そこで直したか・引き継ぎに書いたかを確かめる
   - ユーザーに見える文言は、経路（どの操作から来たか）に依存しない言い方か。画面の表記が同じ repo で読めるなら、それにもそろえる

## 初回の巡回手順

**レビュー実行**:
```
1. 変更したファイルの差分を確認（git diff）
2. レビュー観点チェックリストに基づいて自己レビュー
3. 問題点をリストアップ
```

**修正実行（修正発生時のみ）**:
```
1. リストアップした問題点を優先度順に修正
2. 修正内容を記録
3. lint/format を変更対象ファイルのみに実行して整合性確認
   ※ プロジェクト全体への lint/format 実行は禁止（L-1）
```

修正が 1 件も出なければここで完了。1 件でも出たら次の巡回へ進む。

## 2 巡目以降の手順（前の巡回で修正が発生した場合）

**レビュー実行**:
```
1. 前の巡回の修正結果を確認
2. 見落とした問題がないか再度チェック
3. 修正によって新たに発生した問題がないか確認
```

**修正実行（残存指摘があれば）**:
```
1. 残存する問題点を修正
2. 最終的なコード品質を確認
3. lint/format を変更対象ファイルのみに実行
   ※ typecheck は自動実行しない（L-2: 実行に数分かかりタイムアウトの原因になる）
```

修正が出なくなるまでこの巡回を繰り返す。**3 巡しても収束しない場合は打ち切り**、残る指摘と収束しない理由（設計上の問題か、レビュー観点の解釈揺れか）をユーザーに報告する。

## 設計思想

> モデル依存の設計判断は `shared/skills/skill-authoring/SKILL.md` の「Claude 5 プロンプト規約」に集約している。ここには本サイクル固有の判断のみを記す。

本サイクルは**回数ではなく状態で制御する**:

- **回すと決めたら初回は必須**（回すかどうかは参加条件で決まる。最低限のセーフティネットの役は、必ず通る Phase 6 が持つ）
- **反復は修正発生を条件とする**（無駄な巡回を抑制）
- **完了は「修正が出ないこと」で判定する**

これにより、修正が不要な単純ステップは 1 巡で完了し、修正が必要な複雑ステップは収束するまで再検証される。「最大 2 回」のような回数上限を完了条件にすると、2 巡目で新たな修正が出た場合に未検証のまま先へ進んでしまうため採用しない。ただし無限ループを避ける安全弁として 3 巡での打ち切りは設け、**到達した場合は完了扱いにせず**残る指摘と収束しない理由を報告する（完了条件と打ち切りは別物）。

深い検証が必要な場合は scaffold を増やすより effort（xhigh/high）を上げる方が効果的。
