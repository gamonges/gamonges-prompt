# 移行と撤退の問い

## 移行と撤去（観点 10）

- **段**: 今の状態から決定の後の状態まで、どの段を踏むか（expand → migrate → contract。フラグ・log → enforce の段）。一度に切り替える決定で、戻すのに移行が要るなら High
- **contract の省略**: 新しい形を足した（expand）後に、古い形を消す段（contract）と期限があるか。無ければ Medium（古い形と新しい形が並んで残ると、元より悪い状態に留まる）
- **フラグ・例外の撤去**: フラグ・例外の一覧・許可の口に、撤去の期限と撤去する人がいるか。期限の無い例外は在庫として残るので Medium
- **kill switch**: 新しい仕組みが問題を起こしたとき、すぐに止める手段（設定・フラグ）があるか
- **ロールバック**: 段ごとに戻す手順があるか。戻せなくなる点（データの書き換え・外部への公開・鍵の切り替え）はどこか。その点を越える前に確かめることが書いてあるか
- **移行の量**: 書き換える箇所・データの件数の見積もりがあるか。コードで数えられるなら数え、見積もりと桁がずれていれば Medium（大きくずれ、費用が判断を変えるなら High）

## 検証できるか（観点 11）

- **遵守の確かめ方**: 決定が守られていることを、何で・いつ・誰が確かめるか（テスト・lint・監視・定期の点検）。書いていなければ Medium
- **切り替えの基準**: 段を進める基準が数値か（「問題が無ければ」は基準にならない）。数値でなければ Medium
- **基準の根拠**: 基準の値（日数・件数・割合）の根拠が、問題の性質から来ているか。道具の制約（ログの保持期間・料金・上限）から来ているなら、そう書いてあるか。書かずに道具の制約を基準にしていれば Medium（稀な経路が基準の期間の外に出ると見逃す。`fact-check` と重なってよい。集約でまとめる）
- **観測の手段が今あるか**: 基準を測る手段（ログ・メトリクス）が、決定の時点で既にあるか。これから作るなら、その段が計画に入っているか
- **判定者**: 段を進める・戻す判断を誰がするか

## ADR 以外の文書に当てるとき

- 実装計画（`tmp/plan.md`）: ステップの順序が expand → migrate → contract になっているか、各ステップの後に戻せるか
- PR の本文: デプロイの順序（DB の移行とアプリの順序）、フラグの初期値、戻す手順が書いてあるか
