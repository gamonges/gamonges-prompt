# 失敗の想像の問い

## 失敗の原因（観点 9）

1 年後に、この ADR の判断が失敗だったと分かったとする。原因の候補を次の型から少なくとも 3 つ出し、それぞれ ADR の記述で防げているかを見る。

| 型 | 問い |
|---|---|
| 前提の崩れ | 規模（件数・利用者・チーム数）・依存先（ライブラリ・外部サービス・前の ADR）・道具（ログ・監視）の前提が変わったら、決定は持つか |
| 運用の漏れ | 決定を守らせる手順を、誰がいつ回すか。回す人がいなくなったら何が起きるか |
| 新しい入口 | 決定の後に足される別の入口（新しい API・バッチ・管理画面・スクリプト）が、決定の外を通らないか |
| 人の入れ替わり | 決定の理由を知らない人が、制約を「不要な複雑さ」として外さないか |
| 部分的な実装 | 決定の一部（強制の仕組み・撤去）だけが実装されないまま時間がたったら、どの状態に留まるか |

原因に対して ADR に緩和策が無ければ Medium。起きやすく、起きたときの影響が大きい（データの漏れ・壊れ・戻せない状態）なら High。

## 古くなる条件と、誰が気づくか（社内の弱点 1）

- この ADR が古くなる条件を書いているか（「〜になったら見直す」）
- その条件が満たされたことに、誰がどの手段で気づくか（監視・定期の見直し・別の ADR の起票）。気づく手段が無ければ Medium

## 強制の手段の仕分け（社内の弱点 5）

決定を守らせる手段を 1 つずつ次に仕分け、指摘の本文に仕分けを書く。

| 仕分け | 例 | 弱くなる条件 |
|---|---|---|
| 構造で防ぐ | 型・権限・DB の制約・入口の一本化 | 構造の外の経路（直接の SQL・別のクライアント） |
| 検出で止める | ログで数える・監視・テスト・lint | 検出が漏れる経路（ログを出さない入口・サンプリング・保持期間を超えた期間）、検出の後に誰が止めるか |
| 規約と人の運用に頼る | レビューで見る・手順書・周知 | 人の入れ替わり・忙しい時期 |

- 不変条件・セキュリティの境界を「規約と人の運用」だけで守る決定は High
- 「検出で止める」なら、検出が漏れる条件を 1 つ以上挙げ、ADR がそれを扱っているかを見る（例: 「0 件が N 日続いたら強制する」の N 日がログの保持期間に縛られていると、保持期間の外の稀な経路を見逃す）

## 実行時の意味論（ADR が実行時の仕組みを決めているときだけ）

コンテキストの伝播（AsyncLocalStorage など）・並行・再試行の仕組みを決めている ADR では、次を問う。

- 複製: 子のタスク・コールバック・キューに渡ったとき、コンテキストは複製されるか共有されるか。片方の書き換えがもう片方に漏れないか
- ネスト: 内側で別の値を入れたとき、外に戻った後で元の値に戻るか
- 並行: 同時に走る 2 つの処理が、同じコンテキストを取り違えないか
- 再試行・タイムアウト: 途中で失敗したとき、状態が中途半端に残らないか

コードで確かめられる問いは、対象 repo の実装を `rg -n` で探して確かめる。確かめられなければ「人への問い」に返す。
