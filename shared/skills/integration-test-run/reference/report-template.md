# 統合テスト結果報告テンプレート

## status 4区分（緑で丸めない）

- ✅ **実機live**: UI操作→実際のnetworkリクエストを実捕捉、**または** UI操作→`Side effect:` SQL で副作用を読み戻し（**どちらの分岐も UI 操作が前提**。SQL 単独の確認は実機liveではない）
  - 2 つの証拠を同格に置くのは、`verify-scenario`（① 実装直後の検証）が network を捕捉せず DB の副作用を読み戻すため。片方だけを証拠と定めると、① から ② へ判定を引き継いだ時に「実機liveと書いてあるのに network ログが無い」という不整合が出る
- ✅ **実API再現**: UI駆動不能なため、該当処理を担う関数/APIリクエストを同じ手順で直接実行して検証
- ✅ **endpoint共有**: 別の実機live確認済み経路と同一endpoint・同一コア関数であることをsourceで確認
- ⚠️ **データ未到達**: 環境にテストに必要なデータが存在しない。core/endpointの妥当性はsource確認のみ。データ作成が多段ウィザード等で脆く副作用を伴う場合、無理に作成せずこの区分に留める

## 報告構成

① サマリ表（status区分×件数）
② 観点別全経路結果
③ 経路別テーブル（URL / 発行method+status / 実測status / トースト文言 等）
④ 実測ログ抜粋
⑤ 発見・注意（経路固有の制約、判定チェックリストで切り分けた環境要因の記録を含む）
⑥ 参照実装（該当コアの実装ファイルパス）
