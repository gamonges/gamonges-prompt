> **`/series-run` と明示して起動する。** 自然言語からは起動しない。

1 つの対応を複数の PR に分ける（シリーズ）とき、横断計画の LGTM の後から全段の完了までを 1 つのセッション（coordinator）で監督する。初動で series-init の手順を行って worktree と `series.md` を用意し、作業単位（worktree）ごとに工程別の worker（design → implement → review → fix）を起動して、worker からの質問と完了報告をここに集める。ユーザーには、仕様・範囲の判断と、ユーザー専用の操作だけを回す。

本文はツールに依存しない。起動・待ち合わせ・応答などは adapter の操作名で書き、ツールのコマンドは adapter のファイルにだけ置く。

## パラメーター

`series-run [<横断計画>]` — 横断計画のパス。指定が無ければ `./tmp/plan.md`（series-init と同じ）。

## ワークフロー上の位置付け

```
/design（## PR の段 を書く）→ /plan-lgtm → /series-run（初動で series-init の手順 → 作業単位ごとに design → implement → ユーザーの /create-pr → review → triage → fix）
```

series-init・series-sync は単体でも今までどおり使える。

## 4 役の分担

worker の skill が「ユーザー」に求めていたことを、4 つの役に分ける。

| 役 | 担い手 |
|----|--------|
| ① 起動者（`/skill` を打つ） | coordinator（worker を起動する） |
| ② 定型の判断の回答者 | coordinator（下の 4 の「質問」で自分で返す範囲） |
| ③ 仕様・範囲の決定者 | ユーザー（coordinator が回す） |
| ④ ユーザー専用の操作者（PR の作成・DB の migrate・破壊的な git） | ユーザー（worker は依頼として報告する） |

## 手順

`<wt>` は作業単位の worktree のパス。状態ファイルは 1 つの出来事を処理するたびに書く（state-format の「書く時」）。

### 0. 入口の判定

横断計画の worktree の `./tmp/series.md` と `./tmp/series-run.md`（state-format の置き場所）を探す。

| series.md | series-run.md | 入口 |
|-----------|---------------|------|
| 無い | 無い | 初動。1 から |
| 無い | ある | series.md を正とする。series-run.md は消さずに残し、「前の実行の状態ファイルが残っている。初動から始めてよいか」をユーザーに確かめてから 1 に入る。2 で series-run.md を作り直すときは、古いものを `series-run.archived-<日時>.md` に移す |
| ある | 無い | 引き継ぎ。作業単位ごとに、series.md の PR・worktree の `tmp/plan.md`・`tmp/plan-review.md`・`tmp/review/unified.md`・コミットと upstream から工程の現在地を推定し、**表にして 1 回でユーザーに確かめてから** 2 に入る（推定を黙って正にしない） |
| ある | ある | 再開。series-run.md を読み、adapter の「再開」を行う。未処理の出来事を 4 で処理し、`## ユーザーへの依頼` の `未提示`・`未回答` の③を 4 の「③をユーザーに聞く」で出し直してから（前のセッションで出した問いは、処理済みなので待ち受けには戻ってこない）、3 で着手できる作業単位を起動し、4 の待ち受けに入る |

どの入口でも、series.md の `## 段` の表から作業単位ごとの段の数を数え、2 つ以上なら `対象外` にして、段の型の「前提: 作業単位の段は 1 つ」の案内を出す。

### 1. 初動

`../series-init/SKILL.md` を読み、その手順 1〜8 を行う（series-init は `disable-model-invocation: true` で、`Skill` ツールでは呼べないため。`../create-pr/SKILL.md:L245` と同じ形）。series-init の手順 9 の報告のうち「次の手順」は出さずに 2 へ進み、ほかの報告（作った worktree・handoff・残骸）は 7 の報告に含める。

### 2. 監督の開始

1. adapter の「前提の確認」と kernel の読み込み。前提を満たさなければ止まって報告する
2. adapter の「監督の開始」
3. series-run.md を state-format の書式で作る。series.md の段から作業単位の行を作り、既定は `未着手`、handoff に回った段は `worktree 待ち`、段が 2 つ以上の作業単位と series-init で対象外にした段は `対象外` にする（引き継ぎの入口では、0 で確かめた現在地を書く）
4. `## 運用の約束` をユーザーに 1 回で確かめる（リポジトリ固有の制約・工程ごとの agent・環境の準備）。環境の準備が空のときは「準備は要らない」で合っているかも同じ問いに含める（空のまま始めると、最初の工程が環境の不足で失敗し、再試行を 1 回使い切ってからユーザーに回るため）

### 3. 起動

`worktree 待ち` の作業単位は、worktree ができて `tmp/context.md` が置かれていれば `未着手` に移す（ユーザーが handoff を済ませた）。着手できる作業単位ごとに、段の型の次の工程の worker を起動する。着手できるのは、`worktree 待ち`・`対象外`・`ユーザーの操作待ち`・`<工程>: 作業中`・`<工程>: 判断待ち`・`完了` のどれでもなく、series.md の段の順序の前提を満たす作業単位。

1. 段の型の「起動の前の確認」を行う（review と fix の PR が open か・その worktree に終わっていない試行が無いか。段の数は 0 で確かめてある）。満たさなければ起動せず、③としてユーザーに回す
2. `./reference/worker-spec.md` の雛形を埋める。「この作業単位に効くユーザーの決定」には、`## ユーザーの決定` のうち効く作業単位にこの作業単位を含む行を写し、配布済みにこの作業単位を足す
3. 段の型の「起動時の HEAD と時刻」を `## 工程の記録` に書く
4. adapter の「worker の起動」（再試行なら「工程の再試行」）。agent は `## 運用の約束` の指定に従う（review は claude）
5. 作業単位を `<工程>: 作業中` にする

独立した作業単位を全部起動してから、4 の待ち受けに入る（1 体ずつ起動して待つと、並列にした意味が無くなる）。1 つの worktree には同時に 1 体だけを入れる。

### 4. 出来事の処理

adapter の「出来事を待つ」で待ち、戻ってきたら次のとおり処理する。

**待ち受けの戻り**: 戻ってきたバッチの全メッセージを、下の種類ごとに処理してから、adapter の「出来事を処理済みにする」でまとめて処理済みにする（途中で処理済みにすると残りを失い、処理済みにしないと同じバッチがまた返る）。「処理」は状態ファイルに書き終えた時点で完了とし、ユーザーの答えは待たない。

- **heartbeat**: 送信の時刻を worker ごとに `## adapter` に控えるだけでよい（生存の判定の割り引きに使う）。heartbeat だけのバッチなら、処理済みにして待ち受けを張り直す
- **質問**: 4 役の分担で仕分ける
  - **coordinator が自分で返す（②）**: TDD の Red の確認・テストの層・計画の意図を変えない技術判断・段の型と `## 運用の約束` で答えが決まっているもの。例: 次の段に移ってよいか・ロックの衝突の解き方・作業の邪魔になるファイルの退避。adapter の「質問に答える」で返す
  - **ユーザーに回す（③）**: 仕様・範囲・UX の文言・ユーザーの過去の決定に関わるもの、段の型で判断がつかないもの、迷ったもの（安全側に倒す）。例: 画面に何を出すか・タスクの範囲・QA への回答。`## ユーザーへの依頼` に `Q-<n>` で問いと推奨を書き、`## adapter` に問いの番号と ID の対応を書いた時点で処理済みにしてよい。作業単位を `<工程>: 判断待ち` にする
- **完了報告**: 段の型の「完了の証拠」を coordinator が自分で確かめる（報告の文面だけで次に進めない）
  - 満たせば `## 工程の記録` を埋め、次の工程へ（3 に戻る。pr の工程は段の型の「pr の工程」、triage は 5）
  - 満たさなければ失敗として、段の型の「失敗したとき」に従う
  - 報告の「残り」にユーザーへの依頼があれば、`## ユーザーへの依頼` に `R-<n>` で書き、作業単位を `ユーザーの操作待ち（<操作>）` にして、adapter の「worker の terminal を残す」の後、どの worktree・terminal で何を打つかを案内する。ユーザーが操作を終えたと伝えたら、`R-<n>` を `済み` にし、残した worker を adapter の「worker を解放する」で解放して、段の型の次の工程へ進む（pr の工程の `/create-pr` は、段の型の「pr の工程」の証拠で進む）
  - 依頼が無ければ、adapter の「worker を解放する」（段の型の「pr の工程」で残す implement の worker を除く）
- **escalation**: 内容を読み、質問と同じ基準で②か③に仕分ける。止まって見えるときは、下の時間切れと同じく adapter の「生存の判定」に従う

**時間切れ**: 待ち受けが出来事なしで時間切れになったら、adapter の「生存の判定」で、生きているはずの全 worker を判定し、`ユーザーの操作待ち（/create-pr）` の作業単位の証拠を確かめてから、待ち受けを張り直す。

**待つ相手の worker が居ないとき**: 作業中の worker が 0 体（残りが③の答え待ちと、ユーザーの操作待ちだけ）なら、待ち受けを張らずに、残る問いと依頼を出してターンを終え、ユーザーの返事を待つ。返事が来たら、状態ファイルを読み直して続ける（待ち受けを張ると、ユーザーの返事が最大 15 分届かない）。終了の積極的な証拠が無い限り、止まったとみなさない。

**③をユーザーに聞く**: 待ち受けの間はユーザーとやり取りできないので、バッチを処理し終えて待ち受けを張り直す前に、`未提示` の③があれば聞く（聞いている間に届いた worker の出来事は受信箱に溜まり、失われない）。表（番号・作業単位・問い・推奨）にまとめて一度に聞き、1 件ずつ聞かない。聞いたら `未回答` にする。coordinator が自分から回す③（段の型の 2 回目の失敗・PR が open でない・権限確認の画面など）も同じ表に入れる。答えが出たら:

1. `## ユーザーへの依頼` の状態を `回答済み` にし、`## ユーザーの決定` に記録する。記録するときに「効く作業単位」を決める（用語・文言・API の形・データの扱いなど、リポジトリをまたぎうる決定は、迷ったら全作業単位）
2. worker が問うてきた③なら、その worker に、`## adapter` の対応から ID を引いて、adapter の「質問に答える」で返し、作業単位を `<工程>: 作業中` に戻す。coordinator が自分から回した③なら、答えに従って作業単位の次を決め、状態を書き直す（起動し直すなら 3 へ、飛ばすなら段の型の次の工程へ、手で進めるなら `対象外` にして理由を書く）
3. 効く作業単位のうち、生きている他の worker には adapter の「追加の指示を送る」で届ける。まだ起動していない作業単位には、3 の起動のときに spec に写す。どちらも配布済みに書く

**pr の工程の確認**: `ユーザーの操作待ち（/create-pr）` の作業単位があれば、出来事を 1 つ処理するたびと時間切れのたびに、段の型の pr の工程の完了の証拠を確かめる。

### 5. 仕分け（triage）

review の工程の完了の証拠を確かめたら、coordinator が `<wt>/tmp/review/unified.md` を読み、各指摘を横断計画の段の分担と series.md に照らして分ける。

- **この作業単位で直す**
- **後の段で配線される**（その段の名前。指摘の前提が後の段で満たされるもの）
- **直さない**（理由）

直すものを `<wt>/tmp/fixes.md` に書く（既にあれば `tmp/fixes.archived-<日時>.md` に移してから書く）。これは仕分けの結果を fix の worker に渡すための入力で、ソースの修正は fix の worker が行う。判断がつかない指摘は③としてユーザーに回す。仕分けを `## 工程の記録` に残し、fix の工程へ（3 に戻る）。直すものが 0 件なら、段の型の「仕分け（triage）が 0 件のとき」に従う。

### 6. 状態の表示

出来事を処理するたびに、`## 作業単位` の表（工程の現在地・待っている相手）を 1 回出す。PR の進捗は series.md と series-sync が持つ。PR の全体像の同期が要れば、`../series-sync/SKILL.md` の「同期の手順」を読んで行う。

### 7. 終わり

全作業単位が `完了`・`対象外`・`ユーザーの操作待ち`（pr の工程の `/create-pr` 待ちを除く。それは監督を続けて待つ）のどれかになったら終える。

1. adapter の「完了の後始末」を行う（ユーザーが操作した terminal の確かめと片付けを含む）
2. `## ユーザーの決定` の配り漏れ（効く作業単位のうち配布済みに無いもの）が無いかを見る
3. 報告する
   - 作業単位ごとの結果と根拠（完了の証拠）
   - 残るユーザーへの依頼（`## ユーザーへの依頼` の未回答・未了）
   - 閉じなかった terminal と理由
   - 1 の初動での series-init の報告（作った worktree・handoff・残骸）
   - `対象外` にした作業単位と理由

上の終わりの条件を満たすまで 4 の待ち受けを続ける。打ち切りは工程ごとの上限（段の型の「失敗したとき」・adapter の「生存の判定」の 2 回）で行い、上限に達した作業単位はユーザーに回る。ユーザーが監督を止めると伝えたら、その時点の状態ファイルを書いて 7 の 3 の報告を出す（状態ファイルから再開できる）。

## 書かないもの

- series.md を直接書かない（書き手の口は決まっている。`../series-sync/reference/series-format.md` の「書き込みの規則」）
- 横断計画を書き換えない
- worker の worktree のソースを coordinator が直さない。例外は 5 の `tmp/fixes.md` だけ
- coordinator は push しない（push は implement・fix の worker だけ）
- coordinator は `/create-pr` の手順を代わりに行わない（ユーザーが意図して打つという関門を残す）
