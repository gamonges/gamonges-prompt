> **`/series-run` と明示して起動する。** 自然言語からは起動しない。

1 つの対応を複数の PR に分ける（シリーズ）とき、横断計画の LGTM の後から全段の完了までを 1 つのセッション（coordinator）で監督する。初動で series-init の手順を行って worktree と `series.md` を用意し、作業単位（worktree）ごとに工程別の worker（design → implement → review → fix → recheck）を起動し、push の後の CI と bot の結果を待って（checks）、worker からの質問と完了報告をここに集める。ユーザーには、仕様・範囲の判断と、ユーザー専用の操作だけを回す。

本文はツールに依存しない。起動・待ち合わせ・応答などは adapter の操作名で書き、ツールのコマンドは adapter のファイルにだけ置く。

## パラメーター

`series-run [<横断計画>]` — 横断計画のパス。指定が無ければ `./tmp/plan.md`（series-init と同じ）。

## ワークフロー上の位置付け

```
/design（## PR の段 を書く）→ /plan-lgtm → /series-run（初動で series-init の手順 → 作業単位ごとに design → implement → ユーザーの /create-pr → checks → review → triage → fix → checks → recheck）
```

series-init・series-sync は単体でも今までどおり使える。

## 4 役の分担

worker の skill が「ユーザー」に求めていたことを、4 つの役に分ける。

| 役 | 担い手 |
|----|--------|
| ① 起動者（`/skill` を打つ） | coordinator（worker を起動する） |
| ② 定型の判断の回答者 | coordinator（下の 4 の「質問」で自分で返す範囲） |
| ③ 仕様・範囲の決定者 | ユーザー（coordinator が回す） |
| ④ ユーザー専用の操作者（PR の作成・DB の migrate・破壊的な git） | ユーザー（worker は依頼として報告する） |

## 手順

`<wt>` は作業単位の worktree のパス。状態ファイルは 1 つの出来事を処理するたびに書く（state-format の「書く時」）。どの処理の中でも、作業単位の状態を書き換えたら（完了報告・時間切れ・ユーザーの返事・ターンを終える前の確認のどれでも）、全作業単位に 3 の着手の条件を当て直し、着手できるものを起動してから先へ進む（積む段の順序の待ちは、ほかの作業単位の記録が変わったときに解ける）。

### 0. 入口の判定

横断計画の worktree の `./tmp/series.md` と `./tmp/series-run.md`（state-format の置き場所）を探す。

| series.md | series-run.md | 入口 |
|-----------|---------------|------|
| 無い | 無い | 初動。1 から |
| 無い | ある | series.md を正とする。series-run.md は消さずに残し、「前の実行の状態ファイルが残っている。初動から始めてよいか」をユーザーに確かめてから 1 に入る。2 で series-run.md を作り直すときは、古いものを `series-run.archived-<日時>.md` に移す |
| ある | 無い | 引き継ぎ。作業単位ごとに、series.md の PR・worktree の `tmp/plan.md`・`tmp/plan-review.md`・`tmp/checks.md`・`tmp/review/unified.md`・コミットと upstream から工程の現在地を推定し（PR があって review の成果が無ければ checks の前後。`tmp/checks.md` の `head` が PR の HEAD と同じなら checks は済んでいる）、**表にして 1 回でユーザーに確かめてから** 2 に入る（推定を黙って正にしない）。series.md の worktree 列が空の段は、対象外にした段か handoff 待ちの段かを series.md からは区別できないので、同じ表で聞く |
| ある | ある | 再開。series-run.md の frontmatter の `series:` が今の series.md の絶対パスと一致することを確かめる。違えば、ユーザーに確かめる。選択肢は「同じシリーズで、worktree を移しただけ（`series:` を今のパスに直し、`## 作業単位` の各 worktree も実際のパスを確かめて直してから再開する。push の照合の相手になるため）」と「別のシリーズ（この状態ファイルは別のシリーズのもの。`series-run.archived-<日時>.md` に移し、今の series.md で引き継ぎの入口に入る）」。選ばなかった状態ファイルは消さずに残す。series-run.md を読み、adapter の「再開」を行う。続けて、今の terminal で受信箱の `register`（上書き）と `render` を行う（`./reference/inbox.md`。別の terminal で再開したとき、答える terminal を新しくするため）。`checks: 確認中` の作業単位は、checks の行の入口の時刻から段の型の「checks の工程」の判定をやり直す。未処理の出来事を 4 で処理し、`## ユーザーへの依頼` の `未提示`・`未回答` の③と `済み` でない④、`ユーザーの操作待ち（/create-pr）` の作業単位の案内（段の型の「pr の工程」の 2）を 4 の「③をユーザーに聞く」で出し直してから（前のセッションで出した問いは、処理済みなので待ち受けには戻ってこない）、3 で着手できる作業単位を起動し、4 の待ち受けに入る |

引き継ぎ・再開の入口では、series.md の `## 段` の表から作業単位ごとの段の数を数え、2 つ以上なら `対象外` にして、段の型の「前提: 作業単位の段は 1 つ」の案内を出す。初動では series.md がまだ無いので、1 の確認で分け、2 の 3 で判定する。

### 1. 初動

`../series-init/SKILL.md` を読み、その手順 1〜8 を行う（series-init は `disable-model-invocation: true` で、`Skill` ツールでは呼べないため。`../create-pr/SKILL.md:L245` と同じ形）。series-init の手順 2 の 5 の確認（「段の解決と worktree の提案」）を出すとき、次に当たるものがあれば同じ確認に含める（series-init の確認が終わった後では、分け直すのに series-init をやり直すことになるため）:

- 同じ worktree にまとめる段: 「series-run は段が 2 つ以上の worktree を回さない（対象外になる）。段ごとに worktree を分けるか」
- 横断計画の worktree（状態ファイルを置く worktree）を段に割り当てる提案: 「横断計画の worktree は段に使えない（`/design` が横断計画の `tmp/plan.md` を上書きしうる）。段の worktree を別に作るか」。別に作ると答えたら、その段を worktree の無い段として扱い、下の当て直しと同じく series-init の手順 2 の 3・4 を当て直す。分けないと答えたら、その段を 2 の 3 で `対象外`（横断計画の worktree を別に作らないと決めた）にし、series-init の手順 7 でその段の context.md を書かない（横断計画の worktree の `tmp/context.md` を書き換えないため）

ユーザーが段ごとに分けると答えたら、分けた後の構成で series-init の手順 2 の 3・4（作る worktree と、作らない段の判定）を当て直し、その結果を同じ確認の続きとして見せてから確定する（積む段は、前の段のブランチが origin に無いので handoff に回りうる）。

series-init の手順 9 の報告のうち「次の手順」は出さずに 2 へ進み、ほかの報告（作った worktree・handoff・残骸）は 7 の 4 の報告に含める。

### 2. 監督の開始

1. adapter の「前提の確認」（手順の正の読み込みを含む）。前提を満たさなければ止まって報告する
2. adapter の「監督の開始」
3. series-run.md を state-format の書式で作る。series.md の段から作業単位の行を作り、既定は `未着手`（worktree には実際のパスを書く）、handoff に回った段は `worktree 待ち`、段が 2 つ以上の作業単位、series-init で対象外にした段、1 の確認で横断計画の worktree を分けないと答えた段は `対象外` にする（引き継ぎの入口では、0 で確かめた現在地を書く）。`worktree 待ち` の段ごとに `## ユーザーへの依頼` に `R-<n>`（handoff のパスと、作れるようになる条件。base が別の段を指すなら「その段の implement が push した後」）を立てる。続けて受信箱の `register`（`--terminal` は adapter の「自分の terminal の識別子」）と `render` を行う（`./reference/inbox.md`。失敗しても監督は止めず、7 の 4 で報告する）
4. 次を 1 回でユーザーに確かめる
   - `## 運用の約束`（state-format の項目: リポジトリ固有の制約・工程ごとの agent と model と advisor・環境の準備・検査のコマンド・bot・dispatch する workflow・checks の上限）。環境の準備・検査のコマンド・bot・dispatch する workflow が空のときは「要らない」「無い」で合っているかも含める（空のまま始めると、最初の工程が環境の不足で失敗し、再試行を 1 回使い切ってからユーザーに回るため。検査と CI を黙って飛ばさないため）
   - context.md（worktree が無い段は series-init の handoff のファイル `tmp/handoff/<repo>.md`）の「シリーズでの担当」に「前提」（本番に出ていることなど）がある段: 前提を待たずに着手してよいか。待つと答えた段は `対象外`（理由: 前提待ち）にする（series-run は本番の状態を判定しない。段の型の「起動の前の確認」の順序）

### 3. 起動

`worktree 待ち` の作業単位は、ユーザーが作ったと伝えたパス、または series-init の手順 2 で見せたパスに worktree があり（`git -C <作業用 clone> worktree list --porcelain` で確かめる）、`tmp/context.md` が置かれていれば、実際のパスを `## 作業単位` の worktree に書いて `未着手` に移し、`R-<n>` を `済み` にする（ユーザーが handoff を済ませた）。`R-<n>` の作れるようになる条件（前の段の implement の push）が満たされたら、その `R-<n>` を `未提示` に戻し、内容に「今なら作れる」を足して、③の表で案内し直す。

着手できるのは、`未着手` か、`<工程>: 済み` で段の型の次が worker の工程のもの。それぞれ、段の型の次の工程の worker を起動する（`checks: 済み` の次は checks の行の `前:` で決まる。`前: implement` なら review、`前: fix` なら recheck）。`<工程>: 済み` で次が worker の工程でないもの（再開で `implement: 済み`・`pr: 済み`・`fix: 済み`・`review: 済み`・`recheck: 済み` になった作業単位など）は、ここで coordinator の工程を行う: `implement: 済み` は段の型の「pr の工程」、`pr: 済み` と `fix: 済み` は段の型の「checks の工程」の入口、`review: 済み` は 5、`recheck: 済み` は段の型の「recheck の工程」の 4（指摘が 0 件か、新規が 0 件なら下の「`完了` にする前」の後に `完了`）。

1. 段の型の「起動の前の確認」を行う。満たさなければ起動せず、③としてユーザーに回す（順序の確認だけは③にせず待つ。段の型の「起動の前の確認」）
2. `./reference/worker-spec.md` の雛形を埋める。「この作業単位に効くユーザーの決定」には、`## ユーザーの決定` のうち効く作業単位にこの作業単位を含む行を写し、配布済みにこの作業単位と口（`spec`）を足す。「前の段から引き継いだ指摘」には、5 の仕分けでこの段に回した指摘を、起動のたびに全件写し（ユーザーの決定と同じ）、届け済みに足す。recheck の起動では、「これまでに直さないと決めた指摘」に `## 直さないと決めた指摘` のこの作業単位の行を全件写す（出どころが `推奨で進めた` の行と、取り消した行は写さない: worker-spec）
3. 段の型の「工程の基準の HEAD と、試行の起動時の HEAD・時刻」を `## 工程の記録` に書く
4. 段の型の「worker のモデルと advisor」を当ててから、adapter の「worker の起動」。起動し直すときの操作の選び方は、段の型の「失敗したとき」に従う。agent は `## 運用の約束` の指定に従う（review と recheck は claude）
5. 作業単位を `<工程>: 作業中` にする

独立した作業単位を全部起動してから、4 の待ち受けに入る（1 体ずつ起動して待つと、並列にした意味が無くなる）。1 つの worktree には同時に 1 体だけを入れる。

### 4. 出来事の処理

adapter の「出来事を待つ」で待ち、戻ってきたら次のとおり処理する。

**待ち受けの戻り**: 戻ってきたバッチの全メッセージを、下の種類ごとに処理してから、adapter の「出来事を処理済みにする」でまとめて処理済みにする（途中で処理済みにすると残りを失い、処理済みにしないと同じバッチがまた返る）。「処理」は状態ファイルに書き終えた時点で完了とし、ユーザーの答えは待たない。

- **heartbeat**: 送信の時刻を worker ごとに `## adapter` に控えるだけでよい（生存の判定の割り引きに使う）。heartbeat だけのバッチなら、処理済みにして待ち受けを張り直す（6 の表も出さない）
- **質問**: 次の 3 段を上から当て、最初に当たった段を採る（迷ったものは 1 段目に倒れる。ただし、旧仕様では聞いていたレビュー指摘の取捨と、計画に値の無い UX の文言は 3 段目に移した。3 段目で「直さない」としたものは、ユーザーが確かめるまで既決にも PR 本文にも使わない）。worker の質問・escalation・5 の判断のつかない指摘・recheck の新規・coordinator が自分から回す③のすべてに当てる
  1. **ユーザーに聞く（③）**: 次のどれか 1 つに当たる — (i) 答えによって計画の変更対象（`tmp/plan.md` のステップ・変更するファイル）が増減する（計画で値として決めた文言・値を変える答えを含む）(ii) `## 運用の約束` を変える (iii) 外部の事実（作成済みの物・認証方式・相手のシステムの挙動）を前提にする (iv) 戻せない物（例: migration・スキーマ・公開 API・実アカウント・外部への送信・データ・ファイル・ブランチ・PR の削除や破棄）に触れる (v) coordinator が推奨を 1 つに決められない。**checks の指摘（CI の失敗・bot の P0/P1）への判断も常にここ**（recheck の 4 では直す・直さないのどちらでも、5 の triage では直さない・後の段にするとき。推奨で進めると、CI が赤のままであることをユーザーが知らずに `完了` になりうる）。ユーザーが推奨を覆してきたのは (i)〜(iii) の種類である。`## ユーザーへの依頼` に `Q-<n>` で問いと推奨を書き、`## adapter` に問いの番号と ID の対応を書いた時点で処理済みにしてよい。作業単位を `<工程>: 判断待ち` にする
  2. **coordinator が自分で返す（②）**: 答えが `## ユーザーの決定`・`## 直さないと決めた指摘`・段の型・`## 運用の約束` で一意に決まり、その出どころ（`D-<n>`・`K-<n>`・節の名前）を引用できる（出どころが `推奨で進めた` の `K-<n>` は引用に使わない。ユーザーが確かめていないため: state-format）。答えと引用を `## 工程の記録` に残す（state-format。カードには出さない）。例: 既決の再出・前提が消えた・マージ順で守る・ツールの失敗からの復旧・TDD の Red の確認・テストの層・計画の意図を変えない技術判断・次のステップに進んでよいか（plan-lgtm・implement の区切りの確認）・ロックの衝突の解き方・再試行のときの、前の試行の成果物の上書き（更新時刻が前の試行の起動時刻より後のものに限る）。`tmp/code-review.md` は「上書き」。`tmp/plan.md` は、前の試行の `tmp/plan-review.md`（更新時刻が前の試行の起動時刻より後のもの）が LGTM なら「キャンセル」と返し、続けて「今の `tmp/plan.md` を入力に `/plan-lgtm` だけを回す」と添える。そうでなければ「上書き」（前の試行の正しい成果を捨てないため。段の型の「工程の基準の HEAD と、試行の起動時の HEAD・時刻」）。adapter の「質問に答える」で返す。それ以外の `tmp/` の成果物の上書き・退避は 1 段目（`tmp/` の成果物を黙って上書きしない）
  3. **推奨で進めて事後報告**: 1 にも 2 にも当たらず、推奨が 1 つに決まる（レビュー指摘の取捨・UX の文言・テストの追加の要否）。聞かずに推奨で決め、`## ユーザーへの依頼` に `Q-<n>` を `推奨で進めた（<日付>）` で書く（state-format。一覧と受信箱と意味のカードの前半に出る）。worker の質問なら、推奨を adapter の「質問に答える」で返す。推奨が指摘を「直さない」なら、`## 直さないと決めた指摘` には出どころ `推奨で進めた Q-<n>`・PR 本文 `未（推奨）` で足す（確かめるまで、recheck の照合・2 段目の引用・PR 本文に使わない: state-format）。ユーザーが確かめたか覆したら、その答えを下の「答えが出たら」で処理する
- **完了報告**: 次の順に当てる（報告の文面だけで次に進めない）
  1. 報告の「残り」に push の手順で止めた旨（「手順 1」〜「手順 4」。番号が無くても、強制の push の依頼は手順 4、前の段の取り込みは手順 1 として扱う）があり、工程の基準の HEAD から新しいコミットがあれば、段の型の「失敗したとき」の先頭だけに従い、下の 2〜4 は当てない（worker の解放・依頼の立て方・状態名は段の型が決める）。ただし、同じ「残り」に push の手順と関係ないユーザーへの依頼（DB の migrate など）があれば、3 と同じく `R-<n>` に書く。PR 本文の更新は 3 の仕分けに従う（実装に即したものは `R-<n>` にせず、段の型の「失敗したとき」で `@{u}` と HEAD の一致を確かめた時点で coordinator が書く。PR に乗っていない差分を本文に書かないため）。新しいコミットが無ければ、番号があっても 2 に進む（push する物が無いので、通常の失敗か、fix なら段の型の「fix が新しいコミットを作らなかったとき」になる）
  2. 段の型の「完了の証拠」を coordinator が自分で確かめる。満たせば `## 工程の記録` を埋め、作業単位を `<工程>: 済み` にする。続けて 3・4 を当ててから次へ進む（手順の 3 の起動に戻る。pr の工程は段の型の「pr の工程」、triage は 5、recheck は段の型の「recheck の工程」）。3 で④を立てたら、④が `済み` になるまで次の工程を起動しない（pr の工程の `/create-pr` は除く。それは pr の工程そのもの）。満たさなければ失敗として、段の型の「失敗したとき」に従う。ただし fix が新しいコミットを作らなかったときは、段の型の「fix が新しいコミットを作らなかったとき」に従う
  3. 報告の「残り」にほかのユーザーへの依頼があれば、`## ユーザーへの依頼` に `R-<n>` で書き、作業単位を `ユーザーの操作待ち（<操作>）` にして、adapter の「worker の terminal を残す」の後、`R-<n>` を `未提示` で書く（どの worktree・terminal で何を打つか）。案内は③と同じ表で出し、出したら `依頼中` にする（state-format の④の状態）。implement の「残り」の PR の作成の依頼は、pr の工程が引き受けるので `R-<n>` にしない（pr の工程と同時にほかの④があれば `ユーザーの操作待ち（/create-pr ほか）`）。「残り」の PR 本文の更新は次のとおり仕分ける: 実装に即したもの（コードの挙動・テストの説明・マージ後 TODO を済みにする）は④にせず、coordinator が段の型の「PR 本文の更新」で書く。仕様・範囲の判断を含む記述（扱いは別の人が決める、など）は③（`Q-<n>`）で聞く。ただし、③か triage で直さないと決まった指摘を節「意図した挙動・受け入れた残差」に書くのは、判断が済んでいるので coordinator が書く（段の型の「PR 本文の更新」）。ユーザーが操作を終えたと伝えたら、`R-<n>` を `済み` にし、残した worker を adapter の「worker を解放する」で解放して、段の型の次の工程へ進む（pr の工程の `/create-pr` は、段の型の「pr の工程」の証拠で進む）
  4. 依頼が無ければ、adapter の「worker を解放する」（段の型の「pr の工程」で残す implement の worker を除く）
- **escalation**: 内容を読み、質問と同じ 3 段で仕分ける。止まって見えるときは、下の時間切れと同じく adapter の「生存の判定」に従う

**時間切れ**: 待ち受けが出来事なしで時間切れになったら、adapter の「生存の判定」で、生きているはずの全 worker を判定し、段の型の「pr の工程」の 3・4、`ユーザーの操作待ち（強制の push）` の作業単位の `@{u}` と HEAD の一致（段の型の「失敗したとき」）、`checks: 確認中` の作業単位の判定（段の型の「checks の工程」の 2）、3 の `worktree 待ち` の確認を当ててから、待ち受けを張り直す。

**待つ相手の worker が居ないとき**: 作業中の worker が 0 体で、3 で着手できる作業単位も無い（残りが③の答え待ち・ユーザーの操作待ち・`checks: 確認中`・`worktree 待ち`・順序の待ちだけ）とき。`checks: 確認中` の作業単位があり、`未提示`・`未回答` の③も `依頼中` の④も無ければ（④の完了の連絡も、待ち受けの間は届かないため）、ターンを終えずに adapter の「出来事を待つ」を時計として張り続け、時間切れのたびに checks を確かめる（ターンを終えると、CI の結果を誰も見に行かない。worker が 0 体でも待ち受けは時間切れまで待つ: adapter の「待ち受けの時間」）。それ以外（③か `依頼中` の④が残っている・`checks: 確認中` が無い）は、待ち受けを張らずに、残る問いと依頼（`ユーザーの操作待ち（/create-pr）` の作業単位の案内を含む）を出してターンを終え、ユーザーの返事を待つ。ターンを終える前と、返事が来るたびに、状態ファイルを読み直し、`ユーザーの操作待ち（/create-pr）` の作業単位の証拠（段の型の「pr の工程」）、`ユーザーの操作待ち（強制の push）` の作業単位の `@{u}` と HEAD の一致（段の型の「失敗したとき」）、`checks: 確認中` の作業単位の判定（段の型の「checks の工程」）、`worktree 待ち` の作業単位（3）を確かめてから続ける（③が残るときは、CI が先に終わっても次の返事まで気づかない。待ち受けの間はユーザーの答えを受け取れないので、答えを最大で checks の上限まで待たせるよりこちらを採る。時間切れが来ないので、ここで確かめないと証拠がそろっても進まない。待ち受けの間はユーザーの返事が届かない。待ち受けの時間は adapter）。

**質問と回答の一覧**: どの手順の中でも、`## ユーザーへの依頼` の行を足す・状態を変えるたび、および作業単位を `ユーザーの操作待ち（/create-pr）` にする・そこから進めるたびに、同じ書き込みで状態ファイルの `## ユーザー向け: 質問と回答の一覧` を書き直し、続けて受信箱の `render` を行う（中身は state-format の各節。受信箱は `./reference/inbox.md`。遷移の箇所ごとに書くと、書き漏れた経路で一覧が古くなるので、ここ 1 か所の規則にする）。`## 作業単位` の状態を書き換えた後と、意味のカードを書いた後にも `render` を行う（受信箱の「作業単位」の現在地とカードのリンクが古いまま残らないため）。

**③をユーザーに聞く**: 3 段目（推奨で進めたもの）は聞かずに記録だけする（上の「質問」）。待ち受けの間はユーザーとやり取りできないので、バッチを処理し終えて待ち受けを張り直す前に、`未提示` の③があれば聞く（聞いている間に届いた worker の出来事は受信箱に溜まり、失われない）。表（番号・作業単位・問い・推奨）にまとめて一度に聞き、1 件ずつ聞かない。聞いたら `未回答` にする。coordinator が自分から回す③（段の型の 2 回目の失敗・PR が open でない・権限確認の画面など）も同じ表に入れ、作業単位の状態は state-format の `<工程>: 判断待ち` の規則で決める（`worktree 待ち` と `ユーザーの操作待ち（/create-pr）` は書き換えない）。

- 作業中の worker が 1 体以上いれば、表を出した後にターンを終えず、待ち受けを張り直す（ほかの worker の出来事の処理を止めない）。ユーザーの返事は待ち受けが戻った区切りで受け取るので、戻りのたびに、返事が届いていれば下の「答えが出たら」で処理する。表の末尾に「答えは次の区切りで反映する（最大で待ち受けの時間）」と添える
- 作業中の worker が 0 体なら、上の「待つ相手の worker が居ないとき」に従ってターンを終える

答えが出たら:

1. `## ユーザーへの依頼` の状態を `回答済み` にし、`## ユーザーの決定` に記録する。記録するときに「効く作業単位」を決める（用語・文言・API の形・データの扱いなど、リポジトリをまたぎうる決定は、迷ったら全作業単位）。review・recheck・外部のレビューの指摘を直さないと決めた答えなら、`## 直さないと決めた指摘` にも 1 指摘 1 行で足し、段の型の「PR 本文の更新」の節「意図した挙動・受け入れた残差」に書く
2. worker が問うてきた③なら、その worker に、`## adapter` の対応から ID を引いて、adapter の「質問に答える」で返し、作業単位を `<工程>: 作業中` に戻す。coordinator が自分から回した③なら、答えに従って作業単位の次を決め、状態を書き直す（起動し直すなら 3 へ、飛ばすなら段の型の次の工程へ、手で進めるなら `対象外` にして理由を書く）。push の手順で止めた③は段の型の「失敗したとき」の先頭、triage の③は 5、recheck の③は段の型の「recheck の工程」の 4 に従う。作業単位を `対象外` にしたら、段の型の「起動の前の確認」の順序（その段を指す段が無いか）を当てる
3. 効く作業単位のうち、生きている他の worker には adapter の「追加の指示を送る」で届ける（配布済みに口 `send` で書く）。まだ起動していない作業単位には、3 の起動のときに spec に写す

3 段目（`推奨で進めた`）の③にユーザーが番号で答えたら、上の 1〜3 の代わりに次のとおり処理する（どちらも、一覧の行の `推奨で進めた（<日付>）` の語を state-format の「答えが出たもの」に従って置き換える）:

- **推奨どおりと確かめた**: ③を `回答済み` にする。`## 直さないと決めた指摘` に出どころ `推奨で進めた Q-<n>` の行があれば、出どころを `③ Q-<n>（推奨を確かめた）` に書き換え、PR 本文の列を `未` にして段の型の「PR 本文の更新」の節「意図した挙動・受け入れた残差」に書く（以後は既決の照合と 2 段目の引用に使える）
- **覆した**: ③を `回答済み（<日付>・覆した）` にし、`## ユーザーの決定` に記録する。`## 直さないと決めた指摘` の行があれば、その行の PR 本文の列を `取り消し（Q-<n> で覆した）` にする（行は消さない。PR 本文にはまだ書いていないので、本文から取り消す行は無い）。答えは次のとおり届ける: 同じ工程の worker が生きていれば adapter の「追加の指示を送る」で送る／工程が先に進み、作業単位が `完了` でなく fix の工程がまだなら `<wt>/tmp/fixes.md` に足す（5 の「直す」と同じ）／それ以外（`完了` の後・fix の後）は④（`R-<n>`。どの worktree で何を直すか）で残す。ほかの効く作業単位への配布は上の 3 と同じ

ユーザーが番号の無い指摘や抜けを入れてきたら（意味のカードの後半を見て、など）、`## ユーザーへの依頼` に `Q-<n>` を新しく立てて 1 段目の③として扱い、ユーザーの言葉をその答えとして、上の「答えが出たら」で処理する。

**pr の工程の確認**: `ユーザーの操作待ち（/create-pr）` の作業単位があれば、段の型の「pr の工程」の 3 のタイミングで、その完了の証拠を確かめる。

**`完了` にする前**: 作業単位を `完了` にする前（triage が 0 件・fix の後・recheck の後のどれでも）に、5 で後の段としてこの作業単位に回された指摘のうち、反映済みでないものが無いかを見る。反映済みかは届け済みの口で決める（「追加の指示を送る」の成功は受信箱に入ったことしか示さず、worker が読んだかは分からないため）:

- この作業単位の 5 の triage で仕分けたもの（直す・後の段で配線される・直さないのどれでも。後の段なら、さらに後の段に届けている。直さないなら理由が記録にある）は、反映済みとみなす（同じ指摘を二度聞かない）
- それ以外で反映済みとみなすのは、計画かコードを変える工程（design・implement・fix）に届いたものだけ。review・recheck・triage にだけ届いたものは、直す工程を通っていないので反映済みにしない
- そのうち `spec` で届けたもの: 反映済み（起動の時点で worker が読む）
- そのうち `send` で届けたもの: その worker の完了報告か成果物（`tmp/plan.md`・コミット）に、その指摘への言及があるときだけ反映済み

反映済みでないものが残っていれば、③で回す（「fix を起動して直すか・直さないか」）。直すと答えたら、その指摘を `<wt>/tmp/fixes.md` に書いて（既にあれば 5 と同じく退避してから）fix の工程に入る（この確認から fix に入るのは作業単位ごとに 1 回だけ。巡の数え方は段の型の「fix の 2 巡目」）。直さないと答えたら、理由を `## 工程の記録` に書いて `完了` にする。この確認から fix に入った後の、2 回目のこの確認で直すと答えたら、fix に入らずに、その指摘を④（`R-<n>`。どの worktree で何を直すか）で残して `完了` にする（自動で回す巡を文で決めておくため）。

### 5. 仕分け（triage）

review の工程の完了の証拠を確かめたら（`review: 済み`）、coordinator が `<wt>/tmp/review/unified.md` と `<wt>/tmp/checks.md`（implement の後の checks。CI の失敗と bot の P0/P1）と、前の段からこの作業単位に届いた指摘（届け済み）のうち反映済みでないもの（4 の「`完了` にする前」と同じ判定）を読み、各指摘を横断計画の段の分担と series.md に照らして分ける。

- **この作業単位で直す**
- **後の段で配線される**（その段の名前。指摘の前提が後の段で満たされるもの）
- **直さない**（理由）

直すものを `<wt>/tmp/fixes.md` に書く（既にあれば `tmp/fixes.archived-<日時>.md` に移してから書く。段の型の「工程の境目での `tmp/` の退避」の暫定）。これは仕分けの結果を fix の worker に渡すための入力で、ソースの修正は fix の worker が行う。仕分けを `## 工程の記録` に残す。直さないものは `## 直さないと決めた指摘` に 1 指摘 1 行で足し（`## 工程の記録` には番号だけ）、段の型の「PR 本文の更新」の節「意図した挙動・受け入れた残差」に書く。ただし、下の 3 段目（推奨で進めた）で「直さない」にしたものは、出どころ `推奨で進めた Q-<n>`・PR 本文 `未（推奨）` で足し、ユーザーが確かめるまで PR 本文に書かない（4 の「答えが出たら」）。

後の段で配線される指摘は、ユーザーの決定と同じ 2 つの口で、その段の作業単位に届ける。その段の worker が生きていれば adapter の「追加の指示を送る」（届け済みに口 `send`）、まだ起動していない工程には 3 の起動のときに spec の「前の段から引き継いだ指摘」に写す（口 `spec`）。

- checks の指摘を「直さない」「後の段」にするときは、4 の「質問」の 1 段目でユーザーに聞く（推奨で進めない）。判断がつかないそのほかの指摘は 4 の「質問」の 3 段で仕分け、1 段目に当たれば③としてユーザーに回し、作業単位を `triage: 判断待ち` にする（2・3 段目は答えを決めて仕分けに入れる。3 段目の「直さない」は上の印の付け方で足す）。③が残るうちは fix を起動しない。答えが出たら、直すものを `tmp/fixes.md` に足して（直すものが 0 件のままなら、下の 0 件の扱いへ）進む
- ③が無ければ、作業単位を `triage: 済み` にして fix の工程へ（3 に戻る）
- 直すものが 0 件なら、段の型の「仕分け（triage）が 0 件のとき」に従う

### 6. 状態の表示

出来事を処理するたびに、`## 作業単位` の表（工程の現在地・待っている相手）を 1 回出す。heartbeat だけのバッチでは出さない。PR の進捗の記録は series.md と series-sync が持つが、PR の進捗（draft・state・review・CI・未解決のスレッド・mergeable）を報告に書く前と、それをもとに判断する前には、GitHub から取り直す（状態ファイル・series.md の写し・自分の作業の記録を正にしない。ユーザー側の操作は coordinator から見えない。段の型の「起動の前の確認」の review・fix・recheck は、この一例）。PR の全体像の同期が要れば、`../series-sync/SKILL.md` の「同期の手順」を読んで行う。

### 7. 終わり

全作業単位が `完了` か `対象外` になったら終える。`ユーザーの操作待ち`（`/create-pr`・強制の push など、操作の後に段の型の工程が残る）・`判断待ち`・`worktree 待ち` は終わりにせず、監督を続けて待つ（worker が 0 体なら 4 の「待つ相手の worker が居ないとき」でターンを終えて返事を待つ。`worktree 待ち` は、ユーザーが作らないと決めたら `対象外` に移す）。`完了` の後に残る④（recheck で直すと決めた指摘など）は、終わりを止めず 7 の 1 の報告に出す。

1. 完了を短く報告する（後始末より前に出す。後始末はツールの不具合で詰まりやすく、その間ユーザーが完了を知らずに待つため）
   - 作業単位ごとの結果と根拠（完了の証拠）・PR
   - 推奨で進めた判断（`推奨で進めた` の③。確かめるか覆すなら番号で答える。確かめるまで、直さないとしたものは既決・PR 本文に使わない）
   - CI を見ずに進めた作業単位（checks の③で「飛ばす」「失敗として扱う」と答えたもの。段の型の「checks の工程」の 4）
   - 残るユーザーへの依頼（報告の前に `## ユーザー向け: 質問と回答の一覧` を正本の `## ユーザーへの依頼` に合わせて書き直し（節が無い古い状態ファイルなら足す）、その「待っているもの」を出す。recheck で直すと決めた指摘を含む）
2. 受信箱: `## ユーザー向け: 質問と回答の一覧` の「待っているもの」が空なら `unregister` と `render`。残る④があれば、登録を残して `render` だけを行う（受信箱が残る依頼を出し続ける。`./reference/inbox.md`）。続けて adapter の「完了の後始末」を行う（ユーザーが操作した terminal の確かめと片付けを含む）
3. `## ユーザーの決定` の配り漏れ（効く作業単位のうち配布済みに無いもの）が無いかを見る。口 `send` で届け、その worker の完了報告に言及が無いものは「届いたか未確認」として 7 の 4 の報告に出す（決定は起動のたびに spec に全件を写すので、取りこぼしうるのはその作業単位の最後の工程だけで、報告で足りる）
4. 後始末の結果と残りを報告する
   - 閉じなかった terminal と理由
   - 手順 1（初動）での series-init の報告（作った worktree・handoff・残骸）
   - `対象外` にした作業単位と理由
   - 受信箱の `register`・`render`・`unregister` の失敗（ビューは写しなので、失敗しても監督は止めない）
   - 次の手順: PR のマージの順序（積む段は前の段の後）・ドラフトを ready にする操作（ユーザーが行う）・後の段に回した指摘の残り・recheck で残った指摘
   - 7 の 2 で登録を残したときは、残る依頼を片付けた後に打つコマンド（`python3 ~/.claude/skills/series-run/scripts/series_inbox.py unregister --state <状態ファイルの絶対パス>` と `render`）

上の終わりの条件を満たすまで 4 の待ち受けを続ける。打ち切りは工程ごとの上限（段の型の「失敗したとき」・adapter の「生存の判定」の 2 回）で行い、上限に達した作業単位はユーザーに回る。ユーザーが監督を止めると伝えたら、その時点の状態ファイルを書いて 7 の 1 と 7 の 4 の報告を出す（状態ファイルから再開できる）。7 の 1 は「中断」として、作業単位ごとの今の工程を書く。7 の 2 の後始末はしていないので、7 の 4 の後始末の結果は「未実施」と書く（受信箱の `unregister` もしない。再開の `register` で上書きする）。

## 書かないもの

- series.md を直接書かない（書き手の口は決まっている。`../series-sync/reference/series-format.md` の「書き込みの規則」）
- 横断計画を書き換えない
- worker の worktree のソースを coordinator が直さない。例外は `tmp/fixes.md`（5 の仕分けと、4 の「`完了` にする前」から fix に入るとき）・`tmp/checks.md`・`tmp/meaning-card.md`・`tmp/meaning-card.html`・`.claude/settings.local.json` の `advisorModel` キーだけ（段の型の「checks の工程」「worker のモデルと advisor」・`./reference/meaning-card.md`）
- coordinator は push しない（push は implement・fix の worker だけ）
- 外部への操作は、`## 運用の約束` に書いた bot の起動のコメントと `workflow_dispatch` だけを coordinator が行う（段の型の「checks の工程」の 1）。ほかの PR へのコメント・レビューはしない
- coordinator は `/create-pr` の手順を代わりに行わない（ユーザーが意図して打つという関門を残す）
- PR 本文は、4 の完了報告の 3 で coordinator が書くと仕分けた範囲だけを書く
