# 状態ファイル `series-run.md` の書式

coordinator の状態の正本。コンテキストが尽きたり、ツールが再起動したりした後も、別のセッションがこのファイルから監督を再開できるようにする。

## 置き場所と書き手

- 置き場所: series.md と同じディレクトリの `series-run.md`。series-init は series.md を横断計画の隣（既定 `./tmp/series.md`）に作るので、既定は横断計画の worktree の `./tmp/series-run.md`。series.md がまだ無いときも、ここを探す
- 書き手: coordinator だけ。worker は書かず、完了報告で届ける
- 書く時: 1 つの出来事を処理するたびに書く。コンテキストが尽きても、失うのは処理中の 1 件だけにする

## 写さないもの

**series.md が持つ項目（ブランチ・PR・進捗）は写さず、段名で参照する。** series.md は書き手の口が決まっていて（`../../series-sync/reference/series-format.md` の「書き込みの規則」）、別の worktree の `/create-pr` が書き換える。写すと 2 つが食い違い、どちらが正か決まらなくなる。

`## 作業単位` の行の鍵は担当の段（段名）で、worktree は値として coordinator が確かめた実際のパスを書く（`worktree 待ち` の間は空になりうるので、鍵にしない）。series.md の worktree 列の写しではない（handoff に回った段では、series.md の worktree 列は空のまま残る）。push の照合の相手はこの値（`./stage-type.md` の「push の手順」）。

## 書式

```markdown
---
type: Series Run
series: <series.md の絶対パス>
adapter: <adapter の名前。reference/adapter-<名前>.md に対応する>
timestamp: <最後に書いた日時>
---

## 作業単位

| worktree | 担当の段 | 工程の現在地 | 待っている相手 | 次 |
|----------|---------|-------------|--------------|----|

## 工程の記録

| 担当の段 | worktree | 工程 | 試行 | 工程の基準の HEAD | 起動時の HEAD | 起動時刻 | 成否 | 完了報告の要約 | 成果物の場所 |
|----------|------|------|-----------------|--------------|---------|------|---------------|-------------|

## ユーザーへの依頼

| 番号 | 種別 | 作業単位 | 内容 | 推奨 | 状態 |
|------|------|---------|------|------|------|

| 日付 | 内容 | 効く作業単位 | 配布済み |
|------|------|------------|---------|

| 番号 | 作業単位 | 出どころ | 指摘の要旨 | 直さない理由 | 根拠 | PR 本文 |
|------|---------|---------|-----------|-------------|------|--------|

## adapter

## ユーザー向け: 質問と回答の一覧

### 待っているもの

```

## 各節

### `## 作業単位`

作業単位（担当の段）ごとに 1 行。`## 工程の記録` の行も段名で引く（worktree の列は、その試行の時点のパスの記録）。

- **worktree**: 作業単位の worktree の絶対パス（上の「写さないもの」）。`worktree 待ち` の間は空で、`未着手` に移すときに実際のパスを書く
- **担当の段**: series.md の `## 段` の段名
- **工程の現在地**: 下の「状態名」のどれか
- **待っている相手**: `worker`・`ユーザー`・`なし`
- **次**: 段の型の次の工程、または次にすること（例: 「PR の作成を待つ」）。`対象外` なら理由を書く

### `## 工程の記録`

worker を起動するたびに 1 行足し、工程が終わったらその行の成否・要約・成果物を埋める。

- **試行**: その工程の何回目の試行か（段の型の「失敗したとき」の上限の数え方に従う。起動そのものの失敗は数えない）。fix・recheck の 2 巡目は `2-1` のように巡を添える（段の型の「fix の 2 巡目」）
- **工程の基準の HEAD・起動時の HEAD・起動時刻**: 段の型の「工程の基準の HEAD と、試行の起動時の HEAD・時刻」
- **design の工程**: 段の型の「工程の境目での `tmp/` の退避」の 3 点を要約の欄に写す
- **triage**: 指摘ごとの仕分け（直す / 後の段で配線される（その段の名前）/ 直さない（`K-<n>`））を、別の行か脚注で残す。直さないものの理由は `## 直さないと決めた指摘` に書き、ここには番号だけを書く（中身を 2 か所に書かない）。後の段に回した指摘には「届け済み」として、届けた先の工程と口（`spec` / `send`）を書く。0 件で fix と recheck を飛ばしたら、両方の行に「飛ばした（0 件）」と書く
- **checks**: 試行の欄は空、起動時刻は入口の時刻（上限の数え始め）、起動時の HEAD は入口の HEAD。要約の先頭に `前: implement` か `前: fix`、続けて dispatch した workflow の表示名と run id、判定（指摘の件数）を書く（`./stage-type.md` の「checks の工程」）
- **③の 2 段目（coordinator が自答）**: 問いの元の工程の行に、問いの要旨・答え・引用（`D-<n>`・`K-<n>`・節の名前）を書く。`## ユーザーへの依頼` には書かない（SKILL.md の 4「質問」）

### `## ユーザーへの依頼`

- **種別**: `③`（仕様・範囲の判断）または `④`（ユーザー専用の操作）
- **番号**: ③は `Q-<n>`、④は `R-<n>`
- **作業単位**: 問うてきた、または依頼を出した作業単位。coordinator が自分から回した③（2 回目の失敗・PR が open でない・権限確認の画面など）は、その作業単位を書き、内容に「coordinator から」と添える（答えを返す worker の ID は無い）
- **内容**: ③は問い、④はどの worktree（と terminal）で何を打つか
- **推奨**: ③の推奨の答え（「OK」で返せる形にする）
- **状態**: 種別ごとに次の順に進む
  - ③: `未提示`（まだユーザーに見せていない）→ `未回答`（見せて答えを待っている）→ `回答済み（<日付>）`。答えの前に要らなくなった③（証拠が先にそろった・作業単位を `対象外` にした）は `取り下げ` にする
  - ③の 3 段目（SKILL.md の 4「質問」）: 聞かずに推奨で決め、最初から `推奨で進めた（<日付>）` で書く。`回答済み` と同じく答えが出たものとして扱う。ユーザーが覆したら `回答済み（<日付>・覆した）` にし、その答えを SKILL.md の 4 の「答えが出たら」で処理する
  - ④: `未提示`（書いたが、まだ案内していない）→ `依頼中`（どこで何を打つかを案内した）→ `済み`（ユーザーが操作を終えたと伝えた、または完了の証拠がそろった）。作業単位を `対象外` にして要らなくなった④は `取り下げ` にする
  - ④の `未提示` は、③と同じ表（SKILL.md の 4 の「③をユーザーに聞く」）に入れて案内し、`依頼中` にする

③の答えを worker に返すための ID は、ここではなく `## adapter` 節の「問いの番号 → ID」の対応に置く（ツール固有の ID をこの節に書かないため。再開した後も、番号から ID を引いて元の worker に返せる）。

### `## 運用の約束`

ユーザーと決めた、リポジトリ固有のもの。監督の開始のときに 1 回で確かめる。

- リポジトリ固有の制約（typecheck の流し方・ローカルの DB や port の使い方など）。spec の「作業の制約」に写す
- 工程ごとの agent の指定（既定は claude。review と recheck は claude に固定）
- 環境の準備の手順（`.env` の複製・依存の install など）。要らないなら「要らない」と書く（空のままにしない）
- 工程ごとの model と advisor（既定: implement・fix は `claude-sonnet-5-5` と advisor `opus`、review・recheck は advisor 無し）。worktree ごとの `.claude/settings.local.json` の `check-ignore` の結果も控える（`./stage-type.md` の「worker のモデルと advisor」）
- 検査のコマンド（push の前に worker が回す。重い typecheck は書かず checks に任せる）。要らないなら「要らない」
- bot: アカウント・起動の文面・完了の印・重大度の書式（例: `greptile-apps[bot]`・`@greptile-apps review`・本文に `greptile_summary`・`P0`/`P1`）。無ければ「無い」。完了の印が空の bot は起動しない
- dispatch する workflow（ドラフトでは CI が動かないリポジトリで、checks の入口に `workflow_dispatch` を打つ workflow のファイル名）。無ければ「無い」
- checks の上限（既定 45 分。入口の時刻から数える）

項目が空のまま監督を始めない（「要らない」「無い」と書く）。空と「要らない」を区別できないと、検査や bot を黙って飛ばしたのか、要らないと決めたのかが残らないため。

### `## ユーザーの決定`

③で決まったこと。

- **効く作業単位**: その決定が効く作業単位。用語・文言・API の形・データの扱いなど、リポジトリをまたぎうる決定で迷ったら、全作業単位にする
- **配布済み**: 決定を届けた作業単位と口。生きている worker に「追加の指示を送る」で送ったもの（`send`）と、起動のときに spec の「この作業単位に効くユーザーの決定」に写したもの（`spec`）の両方を書く

効く作業単位のうち、配布済みに無いものが残っていれば配り漏れである。worker を起動する前と、③の答えを記録した後に、この差を見る。

### `## 直さないと決めた指摘`

review・recheck・外部のレビュー（bot や人）の指摘のうち、直さないと決めたものの正本。recheck の worker の照合（段の型の「recheck の工程」の 3）と、PR 本文の節「意図した挙動・受け入れた残差」（段の型の「PR 本文の更新」）の両方の元になる。

- **番号**: `K-<n>`
- **出どころ**: `review`・`recheck`・`外部（<レビュアー>）` と、その中の指摘の番号
- **指摘の要旨**: どのコードの何についてか。照合に使うので `path`（できれば行）と挙動を書く
- **直さない理由**: 1 文
- **根拠**: `Q-<n>`（③の答え）か `triage`（coordinator の仕分け）
- **PR 本文**: `未` か `済み`（節「意図した挙動・受け入れた残差」に書いたか）
- **書く時**: triage で「直さない」と仕分けたとき、review・recheck・外部のレビューの③で直さないと答えが出たとき。recheck で既決と裏取りした指摘は、同じ行の再来なので足さない

### `## adapter`

ツール固有の ID と値（監督・試行・terminal の ID、問いの番号 → ID の対応など）。中身は adapter のファイルの「状態ファイルの `## adapter` 節に書くもの」に従う。

**ほかの節にツール固有の ID を書かない。** ツールを替えるときは、この節だけを捨てて、新しい adapter で書き直す。

### `## ユーザー向け: 質問と回答の一覧`

`## ユーザーへの依頼` を、ユーザーが読み返す形にした写し。正本は `## ユーザーへの依頼` のままで、この節は coordinator が書く読む用の写しである（正本の 1 行は長く、読み返しに向かないため）。食い違ったら正本に合わせて書き直す。③の答えは `## ユーザーの決定` から写す。書き直す時点は SKILL.md の 4 の「質問と回答の一覧」の 1 つの規則に従う。

- **待っているもの**: ③の `未提示`・`未回答` と、④の `未提示`・`依頼中`、`ユーザーの操作待ち（/create-pr）` の作業単位（`R-<n>` にしないが、ユーザーが打つ操作なので載せる）。番号と作業単位ごとに、答えるのに要る中身（問い・指摘の表・推奨と理由。④ならどの worktree で何を打つか）を写す
- **答えが出たもの**: ③の `回答済み`・`推奨で進めた`・`取り下げ` と、④の `済み`・`取り下げ`。新しい順に、番号・内容の要約・答え（④は済んだこと、取り下げは理由）を書く。`推奨で進めた` は行に `推奨で進めた（<日付>）` の語を残し（横断の受信箱がこの語で拾う: `./inbox.md`）、「覆すならこの番号で答える」と添える

## 状態名

`## 作業単位` の「工程の現在地」は次のどれか。

| 状態名 | 意味 |
|--------|------|
| `未着手` | まだどの工程の worker も起動していない（監督の開始のときの既定） |
| `<工程>: 作業中` | その工程の worker が動いている |
| `checks: 確認中` | coordinator が CI と bot の結果を待っている（`./stage-type.md` の「checks の工程」。worker は動いていない） |
| `<工程>: 済み` | その工程の完了の証拠を確かめた。次は段の型の「次」（3 の起動、または pr の工程・triage の処理。`recheck: 済み` の次は `完了`。`checks: 済み` の次は、checks の行の要約の `前:` で決まる: `前: implement` なら review、`前: fix` なら recheck）を待つ |
| `<工程>: 判断待ち` | ③の問いへのユーザーの答えを待っている。worker が問うてきた③も、coordinator が自分から回した③（2 回目の失敗・PR が open でない・push の手順で止めた・recheck の指摘など）も、その③のもとになった工程の名前で書く。工程を始める前の作業単位（`未着手`）に立てた③は、次に起動する工程の名前で書く（例: `design: 判断待ち`）。`<工程>: 済み` の後に立てた③（`完了` にする前の確認など）は、その済んだ工程の名前で書く（例: triage が 0 件の後なら `triage: 判断待ち`）。triage の③が残るときは `triage: 判断待ち`。checks の③（上限・必須チェックが全部 skipping・dispatch の run が見つからない）は `checks: 判断待ち`。`worktree 待ち` と `ユーザーの操作待ち（/create-pr）` の作業単位に立てた③は、状態を書き換えない（③の表には出す。書き換えると、その状態で行う確かめから外れる） |
| `ユーザーの操作待ち（<操作>）` | ④の依頼を待っている。pr の工程の `/create-pr` を含む。④が 2 つ以上なら `ユーザーの操作待ち（/create-pr ほか）` のように並べる |
| `worktree 待ち` | series-init が worktree を作らず handoff に回した段。worktree ができ、`tmp/context.md` が置かれたら `未着手` に移す |
| `対象外` | series-run が工程を回さない作業単位。理由を `## 作業単位` の「次」に書く。理由は次のどれか: 段が 2 つ以上（段の型の前提）・series-init の確認でユーザーが外した・前提待ち（context.md の「前提」を待つと答えた）・worktree を作らないと決めた（`worktree 待ち` の段）・横断計画の worktree を別に作らないと決めた・手で進める（③の答え）・依存先が `対象外` で積む段も外した |
| `完了` | 段の型の最後の工程の完了の証拠を確かめた（飛ばした工程を含む） |
