# worker の spec の雛形

coordinator が worker を起動するときに渡す指示（spec）の雛形。既存の開発サイクルの skill は変えず、worker として動くための約束はこの spec で渡す。

**この雛形にはツールのコマンドを書かない。** 質問・報告の手段は、ツールが worker に注入する指示にあり、worker はそれをそのまま使う。spec にコマンドを書くと、注入された引数と食い違ったときに worker が組み立て直してしまう。

## 雛形

`<…>` を埋めて渡す。5 項目の見出しは、今の adapter（Orca）の spec の 5 項目（Target / Change / Constraints / Ownership / Observable acceptance）にそろえてある。adapter が別の形を求めるときは adapter に従う。

```markdown
## Target
- worktree: <worktree の絶対パス>
- 担当の段: <段名>（シリーズ: <series.md の絶対パス>）
- 工程: <段の型の工程名>
- リポジトリ: <段のリポジトリ。`owner/repo`。push の手順 2 の照合に使う>

## Change
<段の型の「起動する skill」。push がある工程では、段の型の「push の手順」を手順ごと写し、手順 1 で比べる前の段のブランチ（引いたもの）も書く。recheck では強さ・PR 番号と、段の型の「recheck の工程」の 2・3 を写す。例: `/implement tmp/plan.md` を実行し、次の手順で push する: …。implement・fix では「この工程の前の試行がコミットを残していれば、それを確かめて、残りの作業（push を含む）だけを行う」を、design では「前の試行の `tmp/plan.md` が残っていれば、それを入力に `/plan-lgtm` だけを回し直してよい」を書く（段の型の「工程の基準の HEAD と、試行の起動時の HEAD・時刻」。工程の再試行は spec を差し替えないので、1 回目から書く）>

## Constraints

### worker の契約
- あなたは coordinator に起動された worker である
- 定型の判断（TDD の Red の確認・テストの層・計画の意図を変えない技術判断）の質問は、注入された指示にある質問の手段で coordinator に聞く。確認の画面（`AskUserQuestion` など）は開かない。coordinator が答えられない
- 仕様・範囲・UX の文言・過去の決定に関わる判断も、同じ手段で coordinator に聞く（coordinator がユーザーに回す）
- ユーザー専用の操作（PR の作成・DB の migrate・破壊的な git・強制の push）は行わず、完了報告の「残り」に依頼として書く。依頼が残っていても、自分の工程が終わっていれば成功で報告する（依頼が残ることは失敗ではない）。push の手順が push を止めたときは、「残り」に手順の番号（「手順 1」など）と理由を書く（coordinator が番号で扱いを決める）。push のコマンドそのものが通信の障害などで失敗したときは、番号を書かずに失敗で報告する
- この契約は、この工程の作業の中で起動される skill にも当てる。連鎖して起動される skill（plan-lgtm → review-plan / revise、fix-lgtm-implement → fix / plan-lgtm / implement）と、完了報告の前に人がこの terminal で打った `/skill` を含む
- 完了報告を送った後に、人がこの terminal で打った指示（`/create-pr` など）は、この契約の外にある人自身の作業である。その skill の手順どおりに、質問は目の前の人に直接聞き、確認の画面も使ってよい。終えた工程の質問・報告の手段（と、その ID）は使わない

### 作業の制約
- ステージは対象ファイルを明示する（全体を一括で追加しない）
- `tmp/` はコミットしない
- `git checkout`・`git restore` でファイルを戻さない（権限確認で止まる。戻すなら patch で退避する）
- `series.md` を書かない（書き手の口は決まっている）
- push は、Change に push の手順があるときだけ、その手順で行う
- <状態ファイルの `## 運用の約束` から、リポジトリ固有の制約・環境の準備・検査のコマンド（push の前に回す。「要らない」ならその旨）を写す>

### この作業単位に効くユーザーの決定
<状態ファイルの `## ユーザーの決定` のうち、効く作業単位にこの作業単位を含む行を写す。0 件なら「なし」と書く>

### これまでに直さないと決めた指摘
<recheck のときだけ、状態ファイルの `## 直さないと決めた指摘` のうち、この作業単位の行を番号・指摘の要旨・直さない理由ごと全件写す。0 件か recheck 以外なら「なし」と書く>

### 前の段から引き継いだ指摘
<前の段の triage で「後の段で配線される」として、この段の名前を挙げた指摘を写す。0 件なら「なし」と書く>

## Ownership
- 編集してよいもの: この worktree の中だけ。ほかの worktree・横断計画の worktree には触れない
- 状態ファイル（`series-run.md`）は書かない。結果は完了報告で届ける

## Observable acceptance
<段の型のこの工程の「完了の証拠」をそのまま写す>

完了したら、注入された指示にある完了報告の手段で、次の 3 文を 1 回だけ送る。成否は手段の成否の欄で明示し、文面だけで失敗を伝えない。
1. 成否: 成功か失敗か（失敗なら理由）
2. 成果物の場所: 書いたファイルと、作ったコミット（push したならブランチ）
3. 残り: 終えていない作業と、ユーザーへの依頼（どの worktree で何を打つか）。無ければ「なし」
```

## 埋め方

- **Change** と **Observable acceptance** は、段の型（`./stage-type.md`）の工程の行から写す。言い換えない（coordinator が完了の証拠を確かめるときに、worker と同じ基準を使うため）。push がある工程（implement・fix）では、段の型の「push の手順」も Change に写す。worker は段の型を読まない
- **作業の制約** の最後の行は、状態ファイルの `## 運用の約束` から写す。リポジトリに依存しない制約は雛形の行で足りる
- **これまでに直さないと決めた指摘** は、recheck の worker が `code-review` の指摘に `[既決 K-<n>]` を付ける照合の相手（段の型の「recheck の工程」の 3）。番号を変えずに写す
- **この作業単位に効くユーザーの決定**・**これまでに直さないと決めた指摘**・**前の段から引き継いだ指摘** は、欄を消さない。0 件でも「なし」と書く（写し忘れと区別するため）。写したら、状態ファイルの `## ユーザーの決定` の配布済み・triage の記録の届け済みに、この作業単位と口（`spec`）を足す
- 完了報告の 3 文は、今の adapter（Orca）の完了報告に添える要約の文の数（3 文）にそろえてある
