description: スタックの各レイヤーを PR 化し create-pr と同じ本文テンプレートを適用する。「スタックを PR 化」「まとめて submit」`/stack-pr-submit` で使用
---

現在のスタックの各レイヤーを GitHub 上の PR として一括作成・更新する。`gh stack submit` にはタイトル・本文をコマンドから直接渡すオプションが無い（対話ターミナルでは単一画面エディタ、非対話では auto-generated タイトルのみ）ため、`--auto` で PR を作成した後に `gh pr edit` で本文を上書きする 2 段階方式を取る。本文を上書きするのは、この実行で新しく作った PR だけ（既存の PR の本文は残す。ステップ 5）。

## 前提条件チェック

詳細は `../stack-pr-init/SKILL.md` の「前提条件チェック（SSOT）」を参照し同じチェックを行う（再宣言しない）。

## 実行プロセス

### 1. スタック構成の取得

`gh stack view --json` で現在のブランチ一覧・親子関係・既存 PR の有無を取得する。

### 2. 各レイヤーの変更分析

各ブランチについて `create-pr` の Phase 3-4 相当のロジックを、そのブランチの**直接の親ブランチ**（trunk またはスタック内の 1 つ下のブランチ）を基準に実施する:

- `git diff <parent>...<branch>` で変更ファイル・diff stats を取得
- `git log <parent>..<branch>` でコミットメッセージを収集
- 変更内容とコミットメッセージから PR の目的（機能追加 / 仕様変更 / バグ修正 / リファクタリング）を判定する

### 3. PR タイトル・本文の生成

- タイトル: `create-pr` Phase 2 のブランチ命名規則ロジックを各ブランチ名に適用する
- 本文: `../create-pr/reference/pr-description-template.md` の構成に従う
- 全体像: `./tmp/context.md` の先頭の frontmatter の `series:` で分ける（判定と series.md が無いときの扱いは `../create-pr/SKILL.md` の Phase 4.5.3 と同じ）
  - **シリーズ**: 本文に全体像を入れない（ステップ 5.5 の同期が入れる）
  - **`series:` はあるが series.md が無く、全体像なしで作るを選んだ**: 本文に全体像を入れず、ステップ 5.5 も行わない
  - **シリーズでない**（`series:` が無い）: スタック全体で 1 つの処理の流れの図を組み、レイヤーごとに強調だけを変える（そのレイヤー = `cur`、他のレイヤー = `other`、スタックの外 = `ext`。表は置かない）。形と凡例は `../create-pr/reference/pr-description-template.md` の「全体像ブロック」の「スタックの PR の図」。1 回の実行で全レイヤーを組むので、流れを共通にして兄弟の PR の間で図が食い違わないようにする。図にする処理の流れが無ければ省く
- Notion Page ID の抽出・`ref` 行付与ルールは `../create-pr/SKILL.md` の「Notion Page ID によるリファレンス付与」を SSOT として踏襲する（再宣言しない）。ID が指定された場合、スタック全体が単一の要求に対応する変更であるとみなし、**生成する全レイヤーの PR 本文に同じ `ref` 行を付与する**（レイヤーごとに異なる Notion ページへの分割は本 skill の対象外）

### 4. PR の作成

作成の前に `gh stack view --json` で、PR が既にあるブランチと PR 番号を控える（ステップ 5 で、この実行で作った PR と既存の PR を分けるため）。

```bash
gh stack submit --auto
```

新規 PR は draft として作成される（`--open` は付与しない。draft 解除は `create-pr` 同様ユーザー操作に委ねる）。

### 5. 本文・タイトルの上書き

```bash
gh stack view --json
```

で作成された PR 番号とブランチの対応を取得し、各 PR に対して:

```bash
gh pr edit <number> --title "<generated-title>" --body "<generated-body>"
```

を実行し、ステップ 3 で生成したタイトル・本文に上書きする。ステップ 4 の前に PR があった（既存の）PR には `--body` を付けず、タイトルだけを更新する（再実行の目的は失敗したレイヤーの作り直しで、既存の本文には人や `/series-run` の coordinator が書き足した内容（チェックを付けたマージ後 TODO・確認の記録など）があり、丸ごと上書きすると消える。作り直したいときは手で直す）。本文を残した PR はステップ 6 で報告する。PR 番号が取得できなかったブランチは本ステップの対象から除外し、ステップ 6 の失敗一覧に含める。`gh pr edit` が個別に失敗した場合も処理を中断せず次のレイヤーに進む。

### 5.5 シリーズへの登録と同期（シリーズのときだけ）

`series:` があり series.md もあるときだけ行う。呼び方・結果ごとの扱いは `../create-pr/SKILL.md` の Phase 6.5 と同じ（`../series-sync/SKILL.md` を読んでスクリプトを直接実行する）。

1. 各レイヤーの PR を `register` する（`--branch` はそのレイヤーのブランチ、`--worktree` は `git rev-parse --show-toplevel`）
2. exit 3 のレイヤーがあれば、レイヤーと段の対応を提案して **1 回で**確認し、`--stage` を付けて再実行する。選択肢は「段を選ぶ／シリーズに登録しない」で、登録しないレイヤーは同期の対象外。`--stage` の再実行も exit 3 なら、そのレイヤーは登録しないと同じ扱いにする（再度は尋ねない）。exit 1 のレイヤーは、PR が作成済み・未登録であることと後からの手順（`/series-sync`）を報告に回す
3. 登録できたレイヤーが 1 つ以上あれば、`../series-sync/SKILL.md` の「同期の手順」を**全レイヤーで 1 回だけ**行う。0 なら同期しない。手順が止まった・キャンセルされたときも、その結果を持ってステップ 6 へ進む

再実行しても、既存の PR の本文はステップ 5 で上書きしないので全体像も残る。この実行で新しく作った PR の本文には全体像が無く、このステップの同期が入れる（同期をキャンセルすると、全体像の無い本文のまま残る）。

### 6. 完了報告

各レイヤーの PR 番号・URL・タイトルの一覧（既存の PR で本文を残したものは、その旨を添える）、および `create-pr` と同様に「関連リンクの追加」「動作確認チェックリストの確認」「draft 解除」「レビュアーのアサイン」を次のアクションとして案内する。全体像は、シリーズでなければ図の有無（省いたなら理由）、シリーズなら登録したレイヤーと段・同期の結果（`../series-sync/SKILL.md` の「同期の手順」の手順 7 の項目）・キャンセル・登録しなかった／できなかったレイヤーと後からの手順を報告する。一部レイヤーの PR 作成に失敗した場合は、成功/失敗レイヤーを分けて報告する。`gh stack submit` は PR が無いブランチのみ新規作成し既存 PR は base branch 更新のみ行う（重複作成しない）ため、本 skill を再実行すれば失敗分のみ再試行できる旨を案内する（`gh stack submit --help` の記述に基づく想定。実機未検証のため、初回実行時は結果を注意深く確認する）。
