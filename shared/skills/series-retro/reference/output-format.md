# 成果物の形と突き合わせの規則（series-retro）

`self.md`（自分の一次の整理）・`retro.md`（突き合わせた最終版）・memory の評価記録の雛形と、突き合わせ・偏りの判定・取り込み先の規則。判定はここに書いた規則で決め、その場の印象で変えない（偏りを持つのが自分の側だと分かっているため）。

用語:
- **段** = 依頼文（`review-prompt.md`）の「アプローチの梯子」の番号 0〜8
- **種類** = 同じ根から出た欠陥のまとまり（failure class）
- **self** = `self.md`、**review** = `review.md`（独立レビュー）

## self.md（Phase 3）

独立レビューの結果を読む前に書き終える。1 件 1 行。段は必須で、依頼文の梯子と同じ番号を使う。

<!-- tmp-frontmatter: tmp/series-retro/self.md -->
```markdown
---
type: Retrospective
title: <シリーズの名前> の一次の整理
description: <シリーズの名前> のつまずきを、優先度・推奨の段・置き場つきで自分で整理したもの（独立レビューを読む前）
status: draft
---
# 一次の整理: <シリーズの名前>

| ID | 種類 | つまずき | 優先度（高・中・低） | 推奨の段（0〜8） | 置き場 | 確度（high・medium・low） | 根拠（file:L） |
|---|---|---|---|---|---|---|---|
| S-1 | <種類の短い名前> | <何が起き、何を失ったか> | 高 | 6 | <変える場所> | medium | <file:L> |
```

- 優先度: 高 = 同じ事故がまた起きる・被害が本番に出る／中 = 手戻り・レビューの往復が増えた／低 = 小さい・一度きりの可能性がある
- 同じ種類に複数の案があれば、推奨する 1 つだけを行にし、他は「置き場」の欄に「代替: 段 N …」と書く

## 段の分布の表（retro.md に置く）

行 = 段 0〜8、列 = self の件数・review の件数。review は「推奨の段: N」の行を、self は「推奨の段」の列を数える（選択肢の表の段ではなく、推奨の段を数える）。

| 段 | self | review |
|---|---|---|
| 0 受け入れる・やめる | | |
| 1 文書・memory | | |
| 2 skill・指示文 | | |
| 3 決定的なスクリプト | | |
| 4 hook | | |
| 5 lint・型・テスト | | |
| 6 製品コードの構造 | | |
| 7 基盤・プラットフォーム | | |
| 8 組織・プロセス | | |

表から次を機械的に読み、当たったものを `retro.md` の要するにに書く:

- **(a) self が見ていない段**: review が 1 件以上で、self が 0 件の段
- **(b) エージェントの層への偏り**: self の件数の 6 割以上が段 1〜4 に集まり、かつ段 5〜7 が 0 件

## 突き合わせの規則（Phase 5）

種類を単位にする。種類の名前は review の側を採る（self の項目は、review のどの種類に当たるかで寄せる）。

| 場合 | 扱い |
|---|---|
| review にあり self に無い種類 | 「抜け」として review の推奨を採る |
| self にあり review に無い項目 | 残す。「独立レビューに無い」と付け、確度を 1 段下げる（high → medium → low） |
| 同じ種類で推奨の段が割れた | **review の推奨を既定にし**、self の案は代替として並べる。逆にする根拠があれば、根拠を書いて「決めること」へ上げる（既定を黙って入れ替えない） |
| 同じ種類で段が一致 | そのまま採る |

### 独立レビューが未実施のとき

`review.md` が無いまま Phase 5 に来たときは、上の表を当てない。`retro.md` を**暫定版**として self だけから書く。

- 種類の名前は self の側。確度は下げない（下げる根拠は「review に無い」ことで、review が無いときは当たらない）
- 段の分布の表は self の列だけを埋め、(a) は当てず (b) だけを当てる
- 欠陥の流出の表は「未実施（独立レビューが無いため）」の 1 行にする
- 要するにの 1 行目に「暫定版・独立レビュー未実施（<理由>）」と書き、決めることの先頭に「独立レビューをやり直すか」を置く

## 取り込み先の表（Phase 6）

推奨の段で決める。memory と issue の書き込みは Phase 6 の承認の後に行う。

| 推奨の段 | 取り込み先 | skill が作るもの |
|---|---|---|
| 0 受け入れる・やめる | 採らない案 | `retro.md` の節 |
| 1 文書・memory | そのプロジェクトの auto-memory（`type: feedback`） | 記憶の下書き（承認の後に書く） |
| 2〜4 skill・スクリプト・hook（ハーネスが gamonges-prompt のとき） | gamonges-prompt の GitHub issue | issue の下書き（題・本文）。承認の後に作る |
| 2〜4（ハーネスが別の repo のとき） | その repo のチケット（起票はオーナー） | 下の 5〜6 と同じく下書きだけ |
| 5〜6 lint・型・テスト・製品コード | 製品のリポジトリのチケット（**起票はオーナー**） | `retro.md` に置くチケットの下書き（題・本文・根拠）だけ。skill は起票せず、承認も取らない |
| 7〜8 基盤・組織 | 決めること | オーナーへの判断依頼 |

gamonges-prompt は公開リポジトリなので、issue の本文には、作業ディレクトリのリポジトリ名・組織名・PR 番号・`prs/` の写しに出る人名を書かない。作る前に、これらの語で本文を検索して 0 件であることを確かめる。

## retro.md（Phase 5）

```markdown
---
type: Retrospective
title: <シリーズの名前> のハーネス振り返り
description: <いちばん大きな課題と推奨する最初の一手を 1 文>
status: draft
---
# ハーネス振り返り: <シリーズの名前>

## 要するに
<3 行以内。いちばん大きな課題・推奨する最初の一手・決めることの件数。段の分布の (a)・(b) に当たればここに書く。暫定版ならその旨を 1 行目に>

## 決めること
<1 件ずつ自己完結させる（何の話か・選択肢・推奨を先頭に・選ぶと何が起きるか）>

## 前回からの再発
<前回までの評価記録があるときだけ。無ければ節ごと省く>

| 前回の種類 | 採った対策（段） | 今回の再発（回数・根拠） | 対策は効いたか |
|---|---|---|---|

## 独立レビューの実施状況
<Codex（モデル・所要）／subagent（Codex を使えなかった理由）／未実施（理由）。`run.json` の `after_self` が true なら「self の後に起動」、`self_after_review` が true なら「self は独立レビューの完了後に書いた（独立性は『読まない』の指示に頼る）」と書く。後者では段の分布の (a) を参考値とし、要するにでも断定しない>

## 欠陥の流出の表
<review の表を写す。未実施なら「未実施（独立レビューが無いため）」の 1 行>

- 効いたかの測り方: <何を・いつ数えるか>

<上の「段の分布の表」>

### gamonges-prompt の issue
### 製品のリポジトリのチケット（起票はオーナー）
<承認されなかったものは「未起票（理由）」と書いて残す>

## 採らない案

## 現在地
<動いている作業・待っている判断・次にやること。評価記録を保存したか（未保存なら理由）>
```

## memory の評価記録（Phase 7）

auto-memory の `series-retro-<slug>.md`（`<slug>` はシリーズの名前を短い kebab-case にしたもの）。Phase 6 で承認されたときだけ書き、`MEMORY.md` に 1 行足す。次の振り返りの Phase 1 がこれを読み、Phase 5 が「前回からの再発」を作る。

```markdown
---
name: series-retro-<slug>
description: <シリーズの名前>（<期間>）の振り返りで採った対策と、次に再発を数える種類
metadata:
  type: project
---

<シリーズの名前>（<期間>）の振り返り。retro.md は <YYYY-MM-DD> に書いた。

| 種類 | 採った対策 | 段 | 測り方 | 次に確かめる時点 |
|---|---|---|---|---|
| <抽象化した種類の名前> | <対策> | <N> | <何を数えるか> | <次のシリーズの振り返り など> |
```

種類の名前は、製品や題材の固有名を含まない抽象化した呼び名にする（次のシリーズで、別の題材の同じ種類と照合するため）。
