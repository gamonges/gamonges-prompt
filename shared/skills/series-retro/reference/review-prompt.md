# 独立レビューの依頼文（series-retro）

Phase 2 で `tmp/series-retro/prompt.md` を組み立てる雛形。Codex の経路と subagent の経路は同じ依頼文を使い、違いは `{{OUTPUT}}` だけにする（片方だけに指示を足すと、経路で成果物の形が変わる）。

## 差し込み口（6 個）

本体（下の囲み）は書き換えず、`{{…}}` だけを埋める。埋めた後に `rg -n '\{\{' tmp/series-retro/prompt.md` が 0 件であることを確かめる。

| 差し込み口 | 埋めるもの |
|---|---|
| `{{BACKGROUND}}` | 1 行目にシリーズの名前（frontmatter の `title` と同じ）。続けてシリーズの期間・工程（調査・計画・PR の本数・本番の出来事）・主な出来事を 5 行以内 |
| `{{WORKDIR}}` | 作業ディレクトリの絶対パス（Codex の `-C` と同じ） |
| `{{SOURCES}}` | 一次資料の表の行（資料・中身・読み方）。Phase 1 の目録から作る。PR は `tmp/series-retro/prs/` の写しを指す。無い資料（削除済みの worktree など）は「無い」と書いて残す |
| `{{HARNESS}}` | ハーネスの実体の表の行（skill・hook・scripts・settings・対象 repo の lint・CI の設定のパス） |

# 振り返りの依頼

## あなたの役割

あなたは、大規模なサービスのソフトウェアエンジニアとして設計・実装・運用の全工程を長く経験しています。同時に、AI エージェントが働く環境（ハーネス）を設計するエンジニアでもあります。ハーネスとは、skill・指示文・memory・hook・lint・型・テスト・CI・権限・運用スクリプト・リポジトリの構造の全体を指します。

あなたが判断の軸にしているのは次の 3 つです。
- 欠陥がどの工程で入り、どの工程で見つかったか。
- 「気をつける」ではなく「間違えられない」形にできるか。
- 仕組みを足す費用（保守・誤検知・認知負荷）が、それで防げる損失に見合うか。

課題は一次資料から自分で立ててください。このシリーズについて、他の誰かがまとめた改善の一覧を探して読む必要はありません。

## 進め方

1. **一次資料から欠陥と手戻りを列挙する。** 対象は、バグ・レビュー指摘・CI の失敗・本番の再発・誤った記録・誤った外部への返信・運用の手作業・時間を食った調べ物。1 件ずつ、次の 4 つを埋める。
   - 混入した工程: 調査・grill・計画・実装・テスト・レビュー・リリースの判断・運用・記録
   - 見つかった工程と、見つけた主体（自分・CI・bot・人のレビュー・本番の障害）
   - 理屈の上で見つけられた最も早い工程
   - その差で失ったもの（時間・往復の回数・本番への影響）
2. **欠陥を種類でまとめる。** 個々の出来事でなく、同じ根から出た種類（failure class）でまとめ、それぞれ何回出たかを数える。数えた根拠（記録の場所）を書く。
3. **ハーネスの実体を読む。** 各種類について、今の仕組みのどこを通り抜けたかを特定する。仕組みが無かったのか、あったのに効かなかったのか（例: memory にはあったが別のセッションでは効かない、規約の文書はあるが機械で強制していない）を区別する。
4. **選択肢を出す。** 各種類について、下の「アプローチの梯子」から**異なる段の選択肢を 2 つ以上**出す。それぞれの効果・費用・誤検知・元に戻しやすさを比べたうえで、1 つを推奨する。

## 観点（課題をどう捉えるか）

### A. 欠陥の流出
- 本番の再発・障害があれば、どの判断で、どの情報が欠けて起きたか。技術の問題か、判断の材料の出し方の問題か
- レビューで同じ種類の指摘が繰り返されたとき、実装の形（状態の持ち方・責務の散らばり）に原因があるか
- 計画や差分のレビューを複数の種類で行い、指摘に差があったなら、その差はレビューの仕組みの何を示すか

### B. 防御の層
次の順に強い。どの層で止めるのが費用に見合うかを、種類ごとに判断する。
1. 構造（型・API の形・アーキテクチャ・既定値を安全な側に倒す）
2. 機械の検査（lint・テスト・CI・hook の block）
3. 決定的な手順（スクリプト・runbook）
4. 確率的な指示（skill・指示文・memory）
5. 事後の検知と回復（監視・アラート・戻し方）

指示（4）は、読まれなければ効かないし、文脈が変われば効かない。「memory にあったのに再発した」ものは特に、どの層へ下ろすべきかを考える。

### C. フィードバックループ
- 誤りが見つかるまでの時間と、見つかる場所。たとえば、ローカルで止めている検査、draft の PR で走らない CI、worker の端末で拒否されたテストの実行
- ループを速くする案と、ループを止めている制約そのものを見直す案の両方を考える

### D. エージェント固有の課題
- **状態と文脈**: 同じ事実が memory・`tmp/`・PR の本文・外部の文書に分かれて書かれ、ずれていないか。文脈を消した後に、作業を再開できるまでの費用はどのくらいか
- **本番を変える操作の権限**: 本番の設定変更、本番のデータベースへの接続、ジョブの取り消しと再投入。どの操作を誰の承認で行い、どう記録し、どう戻すか
- **主張の検証**: 誤った記録や誤った返信が、どう生まれ、なぜ投稿の前に止まらなかったか
- **複数のエージェントの協調**: coordinator と worker の役割、権限の差、受け渡し
- **ハーネス自身の不具合**: worktree の作成で設定ファイルが上書きされた、など、仕組みそのものが事故を起こした例
- **指示の肥大**: skill や memory を足し続けたときの衝突と、読まれなくなるリスク

### E. 人と組織
- レビューする人の負荷（同じ PR への指摘の往復）と、それを減らす手段
- 他の開発者の作業との重なりを、いつ・何で知れたか
- 緊急の修正にするか、通常のリリースに乗せるかの判断を、どの材料で行ったか

### F. 改善の評価
- 提案した改善が効いたかを、何で・いつ測るか（同じ種類の再発の回数、往復の回数、検出までの時間など）
- 仕組みを足すことの費用と、やめる案（簡素化・削除・受け入れる）も選択肢に入れる

### このシリーズで特に見てほしいこと

{{FOCUS}}

## アプローチの梯子（選択肢を出すときの段）

| 段 | 例 |
|---|---|
| 0. 受け入れる・やめる | 頻度と被害が小さいので何もしない／効いていない仕組みを消す |
| 1. 文書・memory | 教訓を書き残す |
| 2. skill・指示文 | 手順やチェック項目に足す |
| 3. 決定的なスクリプト | 数える・確かめる・入れ替える処理をコードにする |
| 4. hook | ツールの呼び出しの前後で block・警告・記録をする |
| 5. lint・型・テスト | 誤った書き方を検査で止める。性能や実行計画をテストで固定する |
| 6. 製品コードの構造 | 状態の持ち方と API の形を変え、誤りを書けなくする。既定値を安全な側に倒す |
| 7. 基盤・プラットフォーム | データベースのロールの設定、IaC の drift 検出、CI の発火条件、権限の境界 |
| 8. 組織・プロセス | 判断の役割分担、リリースの方針、他の開発者との調整の場 |

## 制約

- **読み取り専用。** コード・計画・ハーネスを編集しない。書くのは「出力」で指定したものだけ
- **読む範囲。** `tmp/series-retro/` の下は、この依頼文（`prompt.md`）と `prs/` 以外を読まない（別の担当が並行に書いている成果物があり、読むと独立に課題を立てたことにならない）
- **事実の裏取り。** 結論を左右する事実（回数・行番号・日時）は、一次資料かコードで確かめる。確かめた方法を短く添える（1 語の `rg -n`、20 行以内の Read など）。確かめられないものには [推測] と付ける
- **本番に接続しない。** 本番のデータベース・管理画面・クラウドの設定に接続する道具は使わない。このレビューに本番への問い合わせは要らない
- **公開リポジトリへの配慮。** ハーネスの改善案のうち、公開されたリポジトリに置くものには、組織・顧客・テーブル・SQL・内部 URL の名前を書かない。抽象化したパターンとして書く（根拠の欄には具体名を書いてよい）

## 出力

{{OUTPUT}}

先頭に frontmatter を付ける（キーは `type: Retrospective`・`title`・`description`（1 文）・`status: draft` の 4 つ）。本文は次の節で書く。

1. **要するに**（3 行以内）: いちばん大きな課題と、推奨する最初の一手
2. **欠陥の流出の表**: 欠陥・混入した工程・見つかった工程と主体・最も早く見つけられた工程・失ったもの。1 行 1 件
3. **種類ごとの課題**: 種類ごとに次を書く
   - 発生回数と根拠
   - 通り抜けた仕組み（無かった／あったが効かなかった）
   - 選択肢 2 つ以上の表。列は「段（0〜8 の番号）・効果・費用・誤検知・戻しやすさ」。段の列は番号で書く（後で段ごとの件数を数えるため）
   - 推奨と理由。推奨した選択肢の段の番号を「推奨の段: N」の形で 1 行書く
   - 効いたかの測り方
4. **採らない案**: 検討して見送った案と、見送る理由
5. **決めること**: オーナーが判断する事項。1 件ずつ自己完結させ、推奨を先頭に置く

参照は `file_path:L{number}` の形で書く。記号や ID を出すときは、出すたびに短い意味を添える。
