# 集約と `unified.md`

`review-adr` の Phase 4 の手順。観点ごとの結果を読み、重複をまとめ、観点の状態と総合判定を決めて `tmp/adr-review/unified.md` を書く。

## 観点の結果をファイルにする

1. 観点の実行役（`adr-lens-reviewer`・直接起動したエージェント）が返した最終メッセージに、`finding-format.md` の「形の不正の判定」を、手順 0（前置きを捨てる）から当てる（**書く前の**最終メッセージに当てる）
2. `tmp/adr-review/<観点>.md` に Write する。`<観点>` はスキル・エージェントの名前（自己レビューは `adr-self-review`）。書くのは、形の不正でなければ手順 0 の後の本文、形の不正なら返ってきた最終メッセージそのまま。書くものの先頭の行が `---` でなければ（形の不正のときだけ起きる）、`finding-format.md` の雛形の frontmatter を前に付けて書く（frontmatter の無い `tmp/` の md の Write は hook が止めるため。形の不正の判定は手順 1 で済んでいる）
3. 返らない（エラー・空のメッセージ）観点は 1 回だけ起動し直す。それでも返らなければ `失敗`
4. 形の不正でない観点の件数は、frontmatter の `description` ではなく本文を数えて決める。`## 指摘` の節（コードフェンスの中を除く）の `^### [A-Z]+-[0-9]+` の見出しの数が指摘の件数、そのうち「重大度」が High の数が High の件数、「札」が `再判断` の数が再判断の件数。観点の状態の表の「指摘（High / 再判断）」の列と、`unified.md` の frontmatter・理由の行・各区分の件数は、すべてこの数にそろえる（観点が `description` に書いた件数は本文と食い違うことがあるため。`<観点>.md` の `description` は書き直さず、返ったままにする）

Codex の結果は `codex.md` の「結果の扱い」で `tmp/adr-review/codex.md` にする。

## 観点の状態

Phase 2 で選んだ観点ごとに、次のどれか 1 つ:

| 状態 | 条件 |
|---|---|
| `完了` | 形の不正に当たらない |
| `形の不正` | `finding-format.md` の判定に当たる。指摘は集約に入れない |
| `失敗` | 起動し直しても返らない |
| `走らなかった（<理由>）` | 材料が無くて走らせなかった（Notion を読めない `adr-lineage` など） |

Codex はこの表に入れない（下の「Codex の扱い」）。

プロジェクト固有の観点のうち、`selection.md` の上限（5 本）で落としたものも、状態を `上限で落とした（得点 n）` にして同じ表に並べる（起動の仕方の列は「—」）。落とした観点は Phase 2 で選んだ観点ではないので、総合判定の「欠けた観点」には数えない（上限は観点の数を抑えるための決まりで、見落としの印ではないため）。一方、`select_lenses.py` が失敗したときの「プロジェクト固有の観点」の行（状態 `失敗`）は欠けた観点に数える（`selection.md`。プロジェクトの規約を見たかどうかが分からないため）。

## 重複をまとめる

- 同じ ADR の箇所について同じ問題を述べる指摘は 1 件にまとめ、一致した観点の ID を併記する（`[DQ-1・RC-2・CX-3]`）
- まとめた指摘の重大度は重い方、確信度は高い方
- `再判断` の札は、**札を付けた観点の略号の集合**で持つ（例: `[DQ-1・RC-2・CX-3]` のうち札を付けたのが DQ-1 と CX-3 なら `DQ・CX`）。同じ観点の 2 件は 1 観点と数え、Codex は `CX` の 1 観点と数える
- 観点どうしの食い違い（片方が良い点、片方が指摘とするなど）は、どちらを採るかを決め、判断を 1 行書く（「判断: …」）
- 指摘は捨てない。Low・確信度 low も残す

## Codex の扱い

- Codex の**欠け**（`--no-codex`・未実施・省略・形の不正）は観点の状態の表に入れず、総合判定の「欠けた観点」に数えない
- Codex が返した指摘（形の不正でないとき）は、他の観点と同じく重複をまとめ、High・`再判断` を数える

## 総合判定

上から当て、最初に当たった値にする（札は観点が付け、集約は数えるだけ。雰囲気で決めない）。

| # | 条件 | 総合判定 |
|---|---|---|
| 1 | `再判断` の札を **2 つ以上の観点**が付けた High（重複をまとめた 1 件）が 1 件以上 | `判断をやり直す` |
| 2 | High が 1 件以上 | `直してから出す` |
| 3 | Phase 2 で選んだ観点のうち、状態が `完了` でないものが 1 本以上（`select_lenses.py` が失敗した「プロジェクト固有の観点」の行を含む） | `直してから出す` |
| 4 | 上のどれにも当たらない | `出してよい` |

- 1 で 2 観点の一致を求めるのは、1 観点の札で反転すると、同じ ADR でも走らせるたびに総合判定が割れるため。札を付けた観点が 1 つだけの High（単独の `再判断`）は 2 の High として数え、「人への問い」に「<ID>: <観点>だけが判断が覆るとした（<要約>）。他の観点は覆るとしていない。判断をやり直すかを決める」の 1 行を足す。理由の行には単独の件数も書く（「単独の再判断 n 件は人への問いに回した」）
- 3 は、見ていない観点の High が 0 なのは「問題が無い」ではないため。理由は「<観点>が<状態>のため、<観点の受け持ち>を見ていない」の形で書く（例: 「Notion を読めないため、系譜（adr-lineage）を見ていない」）
- 判定の行は `**総合判定**: <値>` の 1 行で、値は 3 つのどれかの文字列だけにする（後で文字列一致で読むため）
