# 観点の出力の共通の形

`review-adr` の観点（新しい 5 本・既存の観点・プロジェクト固有の観点・Codex）が返す結果の形。集約（重複の統合・観点の状態・総合判定）が読む契約なので、束ねる側の `review-adr` が持つ。観点のスキルはこのファイルを参照し、写しを持たない（写すと集約の契約が観点の数だけずれるため）。

## 書き先

| 走らせ方 | 書き先 | 書く人 |
|---|---|---|
| `review-adr` から | `tmp/adr-review/<観点>.md` | 親（`review-adr`）。観点の実行役は最終メッセージで返すだけ |
| ADR に固有の 3 本を単独で | `tmp/adr-decision-quality.md`・`tmp/adr-premortem.md`・`tmp/adr-lineage.md` | 観点のスキル自身 |

`fact-check`・`rollout-check` を単独で走らせたときの形は、それぞれの SKILL.md の雛形（種類が違う）。`review-adr` から走らせたときはこのファイルの形に従う（fact-check だけは「## 人への問い」の後に「## 未実測」の節を足す。書き方は fact-check の SKILL.md）。

## 雛形

```markdown

## 対象・観点・読んだもの

- 対象: {ADR のタイトル}（{スナップショットのパス、または入力のパス・URL}）
- 立場: {self | review}
- 観点: {観点名}（略号 {略号}）
- 読んだもの: {スナップショット・コード・git・ルールのファイルを `file:L` で}

## 指摘

### {略号}-1. {要約}

- **重大度**: {High | Medium | Low}
- **確信度**: {high | medium | low}
- **札**: {再判断 | なし}
- **該当箇所**: {ADR の節名}「{引用の一部}」
- **根拠**: {`file:L`・コミット・Notion のページと節。無ければ「根拠なし（推測）」}
- **何が問題か**: {1〜3 文}
- **直し方の案**: {1〜3 文}

- {観点の問いに照らして、ADR が既に満たしているもの（勝つ条件を書いている・現状維持と比べている など）。無ければ「なし」}

- {コードや文書で確かめられない前提を、書いた人に問う形で。無ければ「なし」}
```

## 書き方の規則

- **全件を出す。** 確信度・重大度が低くても捨てない（フィルタと並べ替えは集約でする）
- 指摘が 0 件のときは、「指摘」の見出しの下に `指摘なし` の 1 行を必ず書く（何も書かないと形の不正と区別できないため）
- 指摘の ID は `<略号>-<n>`。`n` は 1 からの通し番号。略号は下の表の値で、依頼文で渡される
- 根拠の無い指摘は、根拠の欄に「根拠なし（推測）」と書いて残す
- frontmatter の `description` の件数（指摘 {n} 件・High {n} 件・再判断 {n} 件）は、指摘の見出しを書き終え、数え終えてから書く（集約は本文の見出しを数えるので、食い違うと `<観点>.md` を読む人だけが誤る）

### 重大度

| 重大度 | 意味 |
|---|---|
| High | このまま出すと判断が誤る、または決めたとおりに実装・運用すると事故・手戻りが起きる |
| Medium | 判断は変わらないが、読み手が誤解する・後で困る（根拠の欠け・期限の無いリスクなど） |
| Low | 読みやすさ・用語・体裁 |

### `再判断` の札

判断そのものが覆る指摘だけに付ける（例: 却下した案が ADR 自身の基準で採用案に勝つ、基準が問題を表していない、前提の事実が崩れている）。直せば同じ判断のまま出せる指摘には付けない。付けてよい条件は各観点の SKILL.md に書いてある。総合判定は、2 つ以上の観点が札を付けた High を数える（1 観点だけの札は人への問いに回る。`unified-template.md`）。

## 略号

| 観点 | 略号 |
|---|---|
| `adr-decision-quality`（判断の質） | `DQ` |
| `fact-check`（事実の裏取り） | `FC` |
| `adr-premortem`（失敗の想像） | `PM` |
| `rollout-check`（移行と撤退） | `RC` |
| `adr-lineage`（ADR の系譜） | `LN` |
| `adr` の自己レビュー | `SR` |
| `security-auditor`（セキュリティ） | `SA` |
| `coupling-anatomy`（結合） | `CP` |
| `ddd-expert`（DDD） | `DD` |
| Codex | `CX` |
| 表に無いプロジェクト固有の観点 | `PA`・`PB`・`PC`…（`review-adr` の Phase 2 で選んだ順） |

略号は英大文字だけにする（下の形の不正の判定の正規表現に当てるため）。ID の見出しの例（表の全行と、プロジェクト固有の観点の 2 本）:

```text
### DQ-1. 却下した案の勝つ条件が無い
### FC-1. 「0 件」の言い切りに出典が無い
### PM-1. 検出で止める強制が、ログの保持期間を超えると働かない
### RC-1. contract の段が無い
### LN-1. 置き換える ADR の未実測の項目が引き継がれていない
### SR-1. 要約が本文の範囲を超えて言い切っている
### SA-1. 鍵の失効の手順が無い
### CP-1. 新しいパッケージが既存の境界を跨いで依存する
### DD-1. 集約の境界が不変条件と合っていない
### CX-1. 代替案の比較に現状維持が無い
### PA-1. プロジェクトの命名規約に合わない
### PB-1. プロジェクトのテナント分離の規約を見ていない
```

## 形の不正の判定

集約（`review-adr` の Phase 4）が観点ごとに当てる決定的な規則。

**手順 0（前置きを捨てる）**: 最終メッセージの先頭の行が `---` なら何も捨てない。そうでなければ、`---` だけの行で、次の行が `type:` で始まる最初の行を探す。その行より前に、```` ``` ```` で始まる行も `## ` で始まる行も無いときだけ、その行より前（前置き）を捨てる。それ以外は何も捨てない。

- `type:` を条件にするのは、本文の途中の区切り線（`---`）を frontmatter の始まりと取り違えないため（雛形の frontmatter は `type:` から始まる）
- 前置きにコードフェンスと `## ` の見出しを許さないのは、本文の中の雛形の例から後ろを結果として受け取らないため（前置きは見出し 1 行と空行程度で、本文の開始ではない）

手順 0 の後の本文に次の規則を当て、どれか 1 つに当たれば、その観点は「形の不正」。規則 2・3 では、コードフェンス（```` ``` ```` で始まる行から次の ```` ``` ```` で始まる行まで）の中の行を数えない（frontmatter を付け足す経路では規則 1 が効かず、フェンスの中の雛形の例だけで規則 2・3 を通ってしまうため）:

1. 先頭の行が `---` でない（frontmatter が無い）
2. `## 指摘` の見出しの行が無い
3. `## 指摘` の行から次の `## ` の見出しの行（無ければ末尾）までに、`^### [A-Z]+-[0-9]+` に当たる行も、`指摘なし` だけの行も無い

形の不正でなければ、`<観点>.md` には手順 0 の後の本文を書く。形の不正の観点の指摘は集約に入れず、返ってきた最終メッセージをそのまま `<観点>.md` に残す。
