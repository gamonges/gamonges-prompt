ユーザーの質問に対して、必要十分な調査と分析を行い回答する。
回答に必要な範囲で、調査対象のコード・構成・アーキテクチャの仕様を理解してから回答すること。

**重要**: コードの変更をしない。調査結果に基づいた回答のみを提供し、調査結果を`./tmp/research.md`に記録する。

## 補助ドキュメントへの参照

必ず読む補助ドキュメントは無い（事実確認型の軽い調査で重い手順を読まないため）。

**条件付きで読む**:

| 補助ドキュメント | 読むタイミング |
|------------------|----------------|
| `../brief/reference/modes.md` | 質問ファイルの frontmatter に `mode:` がある時 |
| `../brief/reference/modes/<mode>.md` の `## ask の観点` | 上記で既知のモードに解決した時 |
| `./reference/design-material.md` | フェーズ 1 の型判定で設計材料型と判定した問いがある時 |
| `../grill/reference/business-scenario.md` | `./tmp/scenario.md` がある時（状態の判定のため） |
| `../brief/reference/entry.md` | 引数が実在するファイルを指していない時（引数なしを含む）。入力を文章・会話の依頼・既定のファイルのどれから得るかを決める |

「念のため全部読む」は禁止。条件付きの表はトリガー条件に該当する場合のみ読み込む。

### research.md への記録ルール

- **デフォルトは追記**: 既存の `./tmp/research.md` がある場合、末尾に `---`（区切り線）を挿入してから調査結果を追記する。既存の内容を削除・上書きしない。
- **上書きする場合**: ユーザーから「上書き」「リセット」「クリア」等の明示的な指示があった場合のみ、ファイルを上書きする。
- **基準を先頭に書く**: 記録の冒頭（追記なら追記ブロックの冒頭）に、対象 repo ごとの基準コミット（`git rev-parse --short HEAD`）と取得日時を書く。後から読む側が、どの時点のコードに対する主張かを判別できるようにするため。

## パラメーター

`$ARGUMENTS` で質問ファイルのパス、または質問の文章を渡せる。省略時は `./tmp/context.md` を使用する。どの入力を使うか（パス・文章・会話の依頼・既定のファイル）は、入口の正典 `../brief/reference/entry.md` に従う。

## ワークフロー上の位置付け

`/grill` の前工程。調査結果（`./tmp/research.md`）は `/grill`・`/design` の材料になる。単独でも使える。

## 実行条件

- 質問ファイル — 入口の正典で解決したもの（引数のパス、書き出した `./tmp/context.md`、既定の `./tmp/context.md` のいずれか）
- `openspec/specs/`（任意）— 既存の仕様ファイル。存在する場合は自動的に参照する

質問ファイルを解決できない場合は、正典の「止まるとき」に従って止まる（本題に入らず、口頭で答えて終わらない）。

## ハルシネーション防止ガイドライン

回答の信頼性を確保するため、以下のルールに従う:

- [ ] コードベース・ドキュメント・調査結果で**直接確認した情報のみ**を使用する
- [ ] コードを引用する場合は**ファイルパスと行番号**を付ける（例: `src/module/file.ts:L42`）
- [ ] 各主張に**照合度ラベル**を付ける。読み手が「どこまで裏取りされた主張か」を判別し、後工程で再確認する対象を選べるようにするため:

  | ラベル | 意味 |
  |--------|------|
  | **[Read]** | 該当行を直接読んで確認した |
  | **[grep]** | 検索結果の行で確認した（前後の文脈は読んでいない） |
  | **[subagent]** | サブエージェントの報告で、親は照合していない |
  | **[推測]** | 確認した事実からの推論 |

- [ ] **否定の主張**（「〜は無い」「〜していない」）には、grep の検索語と検索範囲を併記する（例: `grep -rn "fooId" src/` で 0 件）。検索語の言い換えや範囲の外に実在しうるので、読み手が検索の妥当性を判断できるようにする
- [ ] 検索結果がゼロのときは「その検索語・範囲では見つからなかった」と書き、不在の根拠にしない。特に意味検索の結果ゼロは、index の漏れ（ignore 設定・未 index のパス）でも起きる
- [ ] 根拠が見つからない場合は「**確認できませんでした**」と明記する
- [ ] 外部情報を引用する場合は**URL を付記**する

## 実行プロセス

### フェーズ 1: 質問の読み込みと整理

- [ ] 入口で解決した質問ファイルから質問を読み込む
- [ ] 個別の質問を識別する（区切り: `=====` やリスト形式など）。区切られた質問が無いファイルでは、目的や本文の依頼文から問いを起こし、起こした問いを回答の冒頭に列挙する（読み手が、何に答えたかを照合できるようにするため）
- [ ] ファイル参照やコンテキスト情報を抽出する（例: `tmp/plan.md:L144`）
- [ ] **モード**: モードの解決と適用範囲は正典（`../brief/reference/modes.md`）に従う。既知のモードに解決したら `modes/<mode>.md` の `## ask の観点` を読み、優先する観点を調査に加える。解決の結果は回答の「基準」欄に書く（`mode:` が無ければ `なし（宣言なし）` で、正典は読まない）
- [ ] **問いの型**を問いごとに判定する。型によって調査の手順と出力の構成が変わる:
  - **事実確認型**: 実装の詳細・挙動・所在・ライブラリの使い方など、確認すれば答えが定まる問い → フェーズ 4 の Q&A 形式で答える
  - **設計材料型**: 問いの中身が目的・方向性・理想形・拡張性・業務シナリオを扱い、答えが後工程の判断材料になる問い（`S-n` を調査の前提に使うことは、型を変えない） → `./reference/design-material.md` の手順と出力構成を加える
  - モードがあれば、`## ask の観点` の既定の型を初期値にし、問いの中身が別の型なら上書きする（例: bug モードでも「理想形は？」という問いは設計材料型にする。既定の型のまま軽い手順で答えると、判断材料が足りなくなるため）。モードが無ければ中身だけから判定する
- [ ] **業務シナリオ**: `./tmp/scenario.md` があれば、状態（`S-n` あり / シナリオ不要 / 不在）を正典（`../grill/reference/business-scenario.md`）で判定する。ask はシナリオを判定・生成しない（生成は grill Phase 0・design フェーズ 1.2・implement Phase 1 の 3 経路が担い、4 経路目を作ると判定基準がずれるため）
  - **`S-n` あり**: 題材が一致する場合に限り、主語・入口・出口を調査の前提に使う。各入口・出口の実装箇所を網羅し、期待値に反する現状があれば回答で指摘する
    - 題材の比較: 質問ファイルの frontmatter `title`（無ければ H1）と scenario.md の `title` が**完全一致**する時だけ一致とみなす。言い回しだけの違いでも使わず、「基準」欄に `不使用（title 不一致: {scenario.md の title}）` と書く。前題材の入口・出口を前提にするより使わない方が安全で、意味での一致を認めると実行ごとに判断が割れるため。同じ題材なら、利用者が title を揃えれば使われる
    - `title` が一致しても、1 つの `title` の下に別題材の `S-n` が追記されていることがある。各 `S-n` の主語・入口が質問の題材に関係するかを個別に確かめる
    - 使った `S-n`・使わなかった理由のどちらも「基準」欄に書く
    - 出口に期待値が書かれていないなど、期待値との照合ができない `S-n` は、その旨を未確認事項に書く
    - 業務シナリオの想定そのものを問われても、scenario.md は書かない。入口・出口の候補となる実装箇所を論点として回答し、シナリオにするのは `/grill` Phase 0 に回す
  - **シナリオ不要 / 不在**: 何もしない

### フェーズ 2: 調査

質問が複数あり相互に独立している場合、または複数ファイル・複数の情報源を横断する必要がある場合は、サブエージェントを同一ターンで複数 spawn して並列に調査する。単一の質問や 1 ファイルで完結する調査は直接実行する。

目的に合わせて第一手段を選ぶ。手段ごとに得意・不得意があり、1 つの手段の結果だけで網羅や不在を主張すると誤るため:

| 目的 | 第一手段 | 注意（理由） |
|------|---------|-------------|
| 呼び名の分からない概念の入口を探す | 意味検索（claude-context `search_code`） | 上位は seed / mock / fixture に偏りやすい。ヒットから本番コードへたどり直してから引用する |
| 別名で並存する同じ概念を探す | 意味検索を言い換えて複数回 | 1 回の検索語は 1 つの呼び名の近傍にしか当たらないため |
| 書込経路・ガード・除外条件の網羅 | grep（ORM の API に加え、生 SQL・バッチ・マイグレーション） | 意味検索は網羅に向かない。網羅の主張は grep の検索語と範囲で裏付ける |
| 定義・参照・実装・構造の把握 | Serena（`find_symbol` / `find_referencing_symbols` / `get_symbols_overview`）/ LSP | gitignore 対象のパスでは空で返ることがある。空のときは grep で確かめる |
| 件数・分布・実データでの不変条件 | DB 実測 | 実測手段はプロジェクトの CLAUDE.md / rules に記載があれば従う。無ければ実測項目を未確認事項の先頭に置く。コードからの推論は [推測] で書く |
| 仕様の意図・スコープ | `openspec/specs/`・proposal / design・タスク管理・ADR（Notion MCP が使える時） | PR 本文と食い違うときは配布物とコードを正とする。PR 本文は途中の意図のまま更新されないことがあるため |
| ライブラリ・外部仕様 | Context7 MCP / Web 検索 | 引用には URL を付ける |

- 意味検索を使う前に、対象の絶対パス（`git rev-parse --show-toplevel`）で claude-context `get_indexing_status` を確認する。応答に `✅` を含む（index 済み）なら `search_code(absPath, query)` を使う。`isError`（未 index）や `🔄`（進行中）なら未準備として Serena `search_for_pattern`・grep にフォールバックする（`🔄` は indexing 完了後の再実行で使える）。自動 index はせず、**未 index のときだけ** `/context-index` を案内する
- 質問ファイルで参照されたファイルは直接読み、コンテキストを理解する

### フェーズ 3: 分析・検証

- [ ] 収集した情報を整理し、各質問に対する回答を組み立てる
- [ ] **前提の判定**: 質問ファイルが置いている前提（明示されたものと、問いの立て方に含まれるもの）を列挙し、それぞれに **正しい / 訂正 / 確認不可** を付ける。訂正した前提は、回答の冒頭で示す（誤った前提のまま後工程へ渡ると、grill・design がその上に判断を積むため）
- [ ] 複数の情報源から得た回答が整合するか確認する
- [ ] 回答に根拠があるか最終確認する（ハルシネーション防止ガイドラインに照らす）

### フェーズ 4: 回答

回答の骨格は型によらず共通で、**基準・前提の判定を先頭に、未確認事項を末尾に 1 回だけ**書き、その間に問いごとの本文を並べる。問いの本文は型で変わる — 事実確認型は下記の `### 回答` / `### 参照`、設計材料型は `./reference/design-material.md` の構成（`## 要旨` を先頭に足し、問いの下の節を `###` に下げて置く）:

```
## 要旨
[設計材料型の問いがある時だけ。結論を 3〜5 行、訂正した前提があれば最初に]

## 基準
- 基準コミット: {repo ごとの sha}
- 取得日時: {datetime}
- モード: {bug 等 / なし（宣言なし） / なし（未知の値 X）}
- 参照した業務シナリオ: {S-n / 不使用（理由） / なし（シナリオ不要） / なし（不在）}

## 前提の判定
- [訂正] {前提} → {正しい事実}（根拠）
- [正しい] / [確認不可] ...

## 質問 1: [質問の要約]

### 回答
[調査結果に基づいた回答。主張ごとに照合度ラベルを付ける]

### 業務シナリオの入口・出口
[`S-n` を前提に使った時だけ。各入口・出口の実装箇所と、期待値に反する現状]

### 参照
- `file_path:L{number}` — [参照内容の説明]
- [URL] — [外部情報の説明]

## 質問 2: [質問の要約]
...

## 未確認事項
- [実測していない項目を先頭に、次に確認できなかったこと]
```

回答のポイント:

- [ ] 簡潔で明確な回答を提供する
- [ ] 具体的なファイルパスと行番号を付記する
- [ ] 必要に応じてコードスニペットや例を含める
- [ ] 確認できた事実と推測を照合度ラベルで区別する
