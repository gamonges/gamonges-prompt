# ADR 執筆ガイドライン

本ガイドラインは、プロダクトチームや関係者（エンジニア、QA、EM、PdM 等）と合意を作り、数年後に読んだ人にも「当時の制約の下でなぜその決定にしたか」が伝わる ADR を書くための原則と、それを守るための歯止めをまとめたものである。

**歯止めがある理由**: 2 節の原則 1〜3（代替案を挙げる・懸念に先回りする・数字で語る）は、どれも、元資料（`grill`・`plan`・`research` など）に無いことを「説得力を上げる」方向で書き足す圧力として働く。実際に、却下理由が一般論にすり替わる・推測が事実として言い切られる・未計測の数字が緩和策に足される、といった誤りが起きた。各原則の直下の **歯止め** は、その原則を守るときに一緒に守る。

---

## 1. ADR の本質とアンチパターン

### ADR の目的

ADR は「何を決めたか」だけの記録メモではない。将来のチームメンバーや他チームが読んで、当時の制約の下でなぜその選択にしたかを理解し、同じ議論を繰り返さずに済むようにするための文書である。

### 避けるアンチパターン

1. **決定事項しか書かれていない**:
   - なぜ他の案を退けたのかが書かれていないと、後から参加したメンバーが同じ案を蒸し返し、決定が形だけになる。
2. **現場の不安に答えていない**:
   - 新しい制約やルールを課すときに、開発者の「作業が遅くなるのでは」という不安に答えていないと、現場との摩擦を生む。
3. **メリットだけを書き、トレードオフを隠している**:
   - 意図して引き受けた負債や検査の粗さ（見逃しの可能性）を書かないと、レビューで指摘されて合意が遅れる。

## 2. ADR 執筆の 5 原則

| # | 原則 |
|---|---|
| 1 | 決定の説得力は、退けた代替案とその理由で決まる |
| 2 | 懸念は隠さず、緩和策と組にして書く |
| 3 | 数字と判断の基準で書き、主観的な形容詞に頼らない |
| 4 | 役割別の影響とスコープ外を書く |
| 5 | 決定が手順・自動化に関わるときは、手順の正本を 1 か所にする |

### 原則 1: 決定の説得力は、退けた代替案とその理由で決まる

- 採用した決定の正当性は、比較した代替案と、それを退けた理由によって伝わる。
- 代替案は、論点ごとに 2〜3 個を挙げてフェアに比べる。

**歯止め**:

- **代替案は、元資料に「退けた案」として記録されたものから取る。** 論点ごとに 2〜3 個に足りなければ、ADR に書き足さず、ユーザーに「この論点で他に検討した案はあるか」を聞く。足りない論点が複数あれば、論点の一覧で 1 回にまとめて聞く。論点は元資料の決定（`D-n` などの確定事項）ごとに数え、退けた案が 0 個の決定も論点に入れて聞く。元資料で検討していない案を作ると、照合（`cross-check.md`）で出典の無い文として削ることになるため。
- **元資料に退けた案が 4 個以上あれば、すべて書く。** 2〜3 個は下限で、元資料にある案を削らない。
- ユーザーに聞くときは、次の観点で候補を思い出してもらう（案を自分で作る型ではない）:
  - **構造・スコープ**: より重い案・より軽い案・段階的に進める案を検討したか
  - **強制の度合い・運用**: 一律に止める案・警告や自己申告にとどめる案を検討したか
  - **自動化・技術の選び方**: 別の道具や、別の順序で整える案を検討したか
- ユーザーが「他に検討した案は無い」と答えたら、下限を割ったまま書き、その論点に「他に検討した案は無い」と書く。
- **却下理由は、元資料の「退けた案」の行に書かれた理由を、言い回しごと写す。** 「なぜ現状の制約で破綻するか」を自分で組み立てると、もっともらしい一般論にすり替わり、元資料の本当の理由が消えるため。

### 原則 2: 懸念は隠さず、緩和策と組にして書く

- すべての設計はトレードオフである。チームやレビュアーが抱く不安を言葉にし、その懸念をどう抑えるか（緩和策）を組にして示す。
- 懸念の分類の例:
  - **開発のしやすさ**: 開発の所要時間・学ぶ手間・PR が止められる不安
  - **運用の統制**: 許可リストや例外の規定が抜け道になり、形だけになる可能性
  - **品質保証**: テストを軽くしたことによる見逃しの許容範囲
  - **外部への依存**: インフラ・他チーム・他システムとの調整にかかる時間
  - **道具の差**: 使うエージェントや IDE の違いによる運用のぶれ

**歯止め**:

- **懸念と緩和策は、元資料にある制約から作る。** 緩和策を厚く見せるために、未計測の数字（工数の目安など）や、行っていない設計判断（将来の拡張性など）を足さない。元資料に無いものは、読んだ人が事実として受け取り、後の判断の根拠に使ってしまうため。
- **緩和策の無い懸念は「受け入れるリスク」と書く。** 緩和策の欄を埋めるために作らない。

### 原則 3: 数字と判断の基準で書き、主観的な形容詞に頼らない

- 「多い」「少ない」「重い」の代わりに、数字を文脈の節に置く。
  - 例: 「本番トラフィックの 80% を占める主要コンポーネントだが、テストカバレッジは 5% にとどまる」
  - 例: 「直近 3 ヶ月の改修 PR 300 件を止めないため、改修は対象外とし、月数件の新規追加だけを検査の対象にする」
- 数字があると、トレードオフの線をどこに引いたかを読む人が追える。

**歯止め**:

- **数字は元資料・実測から取り、出典を出典表（`tmp/adr-sources.md`）に残す。** 数字と結論をつなぐ根拠も、元資料に書かれたものを使う。
- **件数を結論の根拠にするときは、その件数になった原因を元資料で確かめる。** 例えば「0 件だった」は、仕組みがあって使われなかった 0 件と、仕組みがそもそも無かった 0 件とで、根拠として別の意味になる。原因を取り違えると、結論の根拠がすり替わる。

### 原則 4: 役割別の影響とスコープ外を書く

- 読む人は「自分の明日の作業がどう変わるか」を知りたい。実装者・レビュアー・QA・インフラ担当など、役割ごとの影響と必要な行動を表にする。
- **スコープ外（今回はやらないこと）を書く。** 議論が広がること・範囲が膨らむこと・期待のずれを防ぐため。

**歯止め**:

- **役割別の表は、決定の本文で「その役割に何を求めているか」と一致させる。** 必須の要件と、任意の目安（「〜なら完了の目安」など）を混ぜない。表を決定と突き合わせずに書くと、決定に無い要件を課してしまうため。

### 原則 5: 決定が手順・自動化に関わるときは、手順の正本を 1 か所にする

この原則は ADR の書き方ではなく、決定の中身を考えるときの観点である。決定が作業の手順や自動化に関わるときに当てる。

- 文書とプロンプトの二重管理を避ける。手順の正本は人が読む Markdown の手順書に置き、AI 向けの道具やプロンプトはそれを参照する薄い入口にする。
- AI エージェントが作業を終えられるよう、結果を機械が読める形（JSON・明確な終了コード）で返す検査の道具を先に整える。

### 要約について

**歯止め**:

- **要約は、本文の決定の言い回しを短くしたものにとどめる。** 要約で「永久に」「完全に」と強めると、本文で書いたトレードオフ（例: 一部は比べない）と矛盾するため。

## 3. 文体の規則

語気で説得力を補うと、元資料に無い強さが ADR に入る。程度は数字か条件で書き、理由は元資料の根拠で書く。

| 種類 | 避ける表現 | 代わりに |
|---|---|---|
| 程度を強める語 | 永久に・完全に・100%・唯一・一切・到底・致命的・麻痺・明白・極めて・ゼロコスト | 程度は数字か条件で書く（「対象を〜に限る」「影響は〜の場合だけ」） |
| 権威づけ | 一流の〜・ベストプラクティスに基づき・〜の鉄則 | 削る。理由は元資料の根拠で書く |
| 外来語・造語 | サイレントドリフト・データドリブン・AI ネイティブ・AI-Ready・Ready to Merge | 「黙ってずれる」「件数から判断する」など、普通の日本語で書く |
| 見出しの英語の併記 | 決定事項（Decisions）・得られる価値（Positive Consequences） | 日本語の見出しだけにする（`adr-template.md` の見出し） |
| 体言止めの羅列 | 「〜の配備。」「〜の構築。」 | 述語のある文にする（「〜を入れる」「〜を作る」） |
| 根拠の無い将来の約束 | 「将来必要に応じて追加可能なアーキテクチャとしている」 | 設計判断として決めていなければ書かない |

あわせて次も守る:

- **時制**: 採用状況が「承認済み」でも、実装前のものは「〜する」「〜にする」と書く。「〜した」「実現した」は実装を終えたものにだけ使う。
- **推測**: 元資料で [推測]・未計測・未決になっている事項は、ADR でも「推測」「未計測」「未決」と書く。
- **用語**: 元資料の語を、別の概念の語に言い換えない。言い換えるなら、元資料の語を括弧で残す。

## 4. 表と図

- **表は Markdown の表で書く。** 罫線文字で描いた表は、全角と半角が混ざると列がずれ、Notion に貼っても表にならないため。
- **Notion に貼るときは、Notion の表（`<table>`）に変換する。**
- **ASCII 図は、構造（層の関係・分岐）を示すときだけに使う。** 列や項目を並べる用途には表を使う。

## 5. 自己レビューのチェックリスト

ADR を書き出す前に、次の観点で見直す:

- [ ] **要約**: 忙しい人が 1 分で読める要約があり、本文の範囲を超える言い切りが無いか
- [ ] **文脈**: 判断の根拠になる事実や数字があり、その出典が元資料にあるか
- [ ] **決定事項**: 何が決まったかが明確か
- [ ] **代替案と却下理由**: 論点ごとに代替案があり（足りない論点はユーザーに聞いたか）、却下理由が元資料の言い回しのままか
- [ ] **懸念と緩和策**: 懸念と緩和策が元資料の制約から作られ、緩和策の無い懸念を「受け入れるリスク」と書いたか
- [ ] **役割別の影響**: 各役割に求めることが決定の本文と一致し、必須と任意の目安が混ざっていないか
- [ ] **スコープ外**: 今回やらないことが書かれているか
- [ ] **出典表**: 元資料があるとき、出典表で対応先の無い文が 0 か（残した文はユーザーの確認を記録したか。合格しないまま残した文は報告に書くか）
- [ ] **元資料なし**: 元資料が無いとき、会話でユーザーが述べていない数字・固有名・理由・退けた案を書いていないか
- [ ] **推測・時制・用語**: 推測のタグを引き継ぎ、実装前のことを「〜する」と書き、元資料の語を言い換えていないか
- [ ] **文体**: 3 節の「避ける表現」の語が無く、見出しに英語の併記が無いか
