# Architecture Decision Record (ADR) 執筆ガイドライン

本ガイドラインは、プロダクトチームや関係者（エンジニア、QA、EM、PdM 等）と円滑に合意形成し、数年後も意思決定の正当性を担保し続けるための **「一流のソフトウェアエンジニアが実践する ADR 執筆の勘所」** をまとめたものである。

---

## 1. ADR の本質とアンチパターン

### ADR の目的
ADR は単なる「決定の記録メモ（What）」ではない。
本質は **「将来のチームメンバーや他チームに対し、当時の制約下でなぜその選択が最適解だったのかを証明し、納得感と協調を生み出すコミュニケーションツール」** である。

### 避けるべき 3 大アンチパターン
1. **決定事項（What）しか書かれていない**:
   - なぜ他の有力な代替案（Why not others）を退けたのかが書かれていないため、後から参加したメンバーによって容易に蒸し返されたり形骸化する。
2. **現場の心理的抵抗（開発速度や負荷）を先回りしていない**:
   - 新しい制約やルールを課す際、開発者の「生産性が落ちるのでは？」という不安に答えていないため、現場との摩擦を生む。
3. **都合の良いメリットばかり強調し、トレードオフを隠している**:
   - 意図的に引き受けた負債や検証の粗さ（偽陰性リスク）を隠蔽すると、レビューで突っ込まれ合意形成が遅延する。

## 2. ADR 執筆の 5 大原則（Core Principles）

```
┌────────────────────────────────────────────────────────────────────────┐
│                        ADR 執筆の 5 原則                               │
├──────────────────────────────────┬─────────────────────────────────────┤
│ 1. 決定の説得力は「却下した案」が決める │ 2. 懸念は隠さずマトリクス化して先回り │
├──────────────────────────────────┼─────────────────────────────────────┤
│ 3. 定量データ（Fact）で感情論を排す │ 4. 役割別の影響とスコープ外を定義する │
├──────────────────────────────────┴─────────────────────────────────────┤
│ 5. 人間と AI の協調（AI-Ready）を前提にプロセスの正本を一元化する      │
└────────────────────────────────────────────────────────────────────────┘
```

### 原則 1: 決定の説得力は「却下した代替案（Rejected Alternatives）」で決まる
- 「採用した決定」の正当性は、**比較検討した代替案の質と、それらを却下した論理の堅牢さ** によって決まる。
- 代替案は必ず以下の複数の観点から最低 2〜3 個立案し、フェアに比較する：
  - **構造・スコープ**: 「理想的だが重すぎる案」vs「軽量だが価値が薄い案」vs「段階的アプローチ（採用案）」
  - **強制力・運用プロセス**: 「一律全ブロック（厳格すぎ）」vs「警告・自己申告（形骸化リスク）」vs「境界を絞った機械的ブロック（採用案）」
  - **自動化・技術選定**: 「生成ツール先行」vs「評価・判定ハーネス先行（採用案）」

### 原則 2: 懸念（Concerns）は隠さず、先回りしてマトリクス化（Mitigations）する
- 完璧なアーキテクチャは存在しない。すべての設計はトレードオフである。
- チームやレビュアーが抱くであろう不安を先回りして言語化し、**「その懸念をどうコントロールしているか（緩和策）」** をセットで提示する。
- **代表的な懸念カテゴリ**:
  - *開発者体験（DX）*: 開発リードタイム悪化、学習コスト、PR ブロックの恐怖
  - *ガバナンス*: 許可リストや例外規定が抜け道・形骸化するリスク
  - *品質保証*: テスト軽量化に伴う偽陰性（検知漏れ）の許容範囲
  - *外部依存*: インフラや他チーム、他システムとの結合リードタイム
  - *ツール環境*: 利用するエージェントや IDE の差異による運用のブレ

### 原則 3: 定量データ（Fact）と判断基準（Drivers）で感情論を排す
- 「多い」「少ない」「重い」といった主観的形容詞を排し、客観的な数値を文脈（Context）に配置する。
  - 例: 「本番トラフィックの 80% を占める主要コンポーネントだが、テストカバレッジは 5% に留まる」
  - 例: 「直近 3 ヶ月の改修 PR 300 件を止めないため、改修は対象外とし、月数件の新規追加のみをゲート対象とする」
- 定量データがあることで、トレードオフの線引きが論理的に必然となる。

### 原則 4: 役割別の影響（Impact by Role）とスコープ外（Non-goals）を定義する
- 読者は「自分の明日の作業がどう変わるか」を知りたい。
  - 実装者、レビュアー、QA、SRE/インフラ担当など、ロール別のアクション表を設ける。
- **Non-goals（あえて今回はやらないこと）** を明記する。
  - 議論の発散、不要なスコープ拡大（スコープクリープ）、的外れな期待値のズレを強力に防止する。

### 原則 5: 人間と AI の協調（AI-Ready）を前提に設計する
- ドキュメントとプロンプトの二重管理を避ける。
  - 手順の SSOT は人間用の Markdown 手順書に置き、AI 向けツール/プロンプトはそれを参照する薄いラッパーとする。
- AI エージェントが自律的にタスクを完了できるよう、状態を機械可読（JSON / 明確な終了コード）で返す検証ハーネスを先行整備する。

## 3. レビューチェックリスト

ADR を公開・共有する前に、以下の観点で自己レビューを実施する：

- [ ] **TL;DR**: 忙しいステークホルダーが 1 分で理解できる要約があるか？
- [ ] **Context**: 判断の根拠となる客観的な事実や定量データ（数値）が含まれているか？
- [ ] **Decisions**: 何が決まり、何が合意されたのかが明確か？
- [ ] **Rejected Alternatives**: 検討した代替案が複数挙げられ、なぜそれを退けたのかが論理的に説明されているか？
- [ ] **Concerns & Mitigations**: 開発速度低下や運用の形骸化などの懸念に対し、具体的な緩和策が提示されているか？
- [ ] **Impact by Role**: 各ロール（開発者、レビュアー、QA 等）が次に何をすべきか明確か？
- [ ] **Non-goals**: スコープ外（今回はやらないこと）が明記され、議論の発散を防いでいるか？
