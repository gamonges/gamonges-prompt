# 検証パス

解説を書いた本人とは別の文脈で、指摘を head の実装に当て直す。指摘側の行番号・件数・「〜の可能性」を信用せず、すべて引き直させる。

## 起動

`general-purpose` のサブエージェントを 1 つ起動する（指摘が 10 件を超え、repo が分かれる（frontend と backend の contract など）ときは、repo ごとに分けて同一ターンで並べてよい）。渡すのは指摘の一覧と PR の座標だけで、解説の結論（区分・推奨）は渡さない（結論に引きずられて「正しい」と返しやすくなるため）。サブエージェントは親の会話もこのファイルも読まないので、プロンプトの末尾に下の「出力の雛形」の markdown ブロックを、frontmatter を含めてそのまま貼る。

プロンプト:

```text
あなたは PR のレビュー指摘の検証役です。読み取りのみで、GitHub への書き込み・checkout・ファイルの編集はしません（結果のファイル 1 つの書き出しを除く）。

対象: {owner}/{repo}#{n}、head {headRefOid}（base {baseRefName}）。
ファイルは必ず `gh api -H 'Accept: application/vnd.github.raw' "repos/{owner}/{repo}/contents/<path>?ref={headRefOid}"` で読む。ローカルのチェックアウトは古いことがあるので根拠にしない。
他リポジトリ（サーバー側の契約・controller など）は、その repo の既定のブランチ（または PR が依存する版に対応する commit）で読み、読んだ ref を書く。
{契約のパッケージに依存する PR のとき: PR が依存する `{契約のパッケージ名}` の版は {版}。その版の公開時刻と、サーバー側で読んだ契約のファイルの最終 commit の時刻を比べ、同じ内容と見てよいかを書く。}

検証する指摘（行番号は指摘側の値。信用せず引き直すこと）:
{指摘の一覧。番号・重大度・要旨・根拠として挙げた path:L行・根拠として挙げた規約}

各指摘について:
1. 判定: 正しい / 一部正しい / 誤り / 判定不能 のどれか
2. 根拠: head で引き直した `path:L行` と、そこに実際に書かれていること（短い引用）。規約を根拠にした指摘は、規約ファイルの該当行も引き直す
3. 訂正: 行番号・件数・対象の取り違え（例: 同じ定数でも表の値ではなく装飾の中身）・「可能性」の確定（実装済みか否か）
4. 補足: 指摘に無いが、検証中に見つけた代替案や反例（あれば）

結果は {出力先 verify.md} に、末尾に貼った雛形（frontmatter を含む）で書き出してください。最後に、訂正のあった指摘の番号だけを返してください。
```

## 出力の雛形

<!-- tmp-frontmatter: tmp/pr-explain/{repo}-{n}/verify.md -->
```markdown
---
type: PR Explanation Verify
title: PR #{n} 指摘の検証（{owner}/{repo} @ {head の先頭 7 桁}）
description: {検証した件数}件を検証し、訂正{訂正の件数}件・誤り{誤りの件数}件
status: stable
---
# PR #{n} 指摘の検証

略記: PR={head の先頭 7 桁}、{他リポジトリの略記と ref}。
contract: {版と、backend の contract の commit との対応。依存しない PR は「対象外」}

## {指摘の番号}. {要旨}: {正しい / 一部正しい / 誤り / 判定不能}
- 根拠: `{path}:L{n}` {短い引用}
- 訂正: {無ければ「なし」}
- 補足: {無ければ省く}

## 指摘の一覧への訂正点
- {解説に反映すべき訂正を 1 行ずつ}
```

## 反映

- 「誤り」は解説から消し、消したことを `verify.md` の訂正点に残す
- 「一部正しい」は、訂正どおりに書き直す（件数・行番号・対象）
- 「判定不能」は残し、「要確認（検証では決まらなかった: <理由>）」と書き添える
- 反映の後、重大度が変わった指摘について区分の機械的ルール（`./format-v3.md`）を当て直す
