# repo 別の観点（観点ファイル）

repo ごとのレビューの観点は skill の外のファイル（観点ファイル）に置く。チーム固有の方針・部品名・規約の中身は skill に書かず、観点ファイルに書く（skill は公開リポジトリで配るため）。

## 観点ファイルの探し方

1. 観点のディレクトリを決める: 引数 `--lenses <dir>` があればそれ、無ければ環境変数 `PR_EXPLAIN_LENSES_DIR`。どちらも無ければ観点ファイルは無い
2. ディレクトリの中の `<repo 名（owner を除く）>.md` を読む（例: 対象が `acme/web#123` なら `<dir>/web.md`）
3. ファイルが無い・読めないときは、下の「汎用の観点」だけで進め、解説（`quick.md`・`explain.md`）の項目 8 に「repo 固有の観点なし（探した場所: <パス>）」と書く。ディレクトリを渡されたのにファイルが無いときは、報告にもその 1 行を入れる（置き場所の誤りに気づけるように）

観点ファイルは対象リポジトリではなく、実行する人の手元のファイル。`~` は展開して読む。読んだパスを解説の項目 7 の表に載せる。

| モード | 読む節 |
|--------|--------|
| 軽い版 | `## 区分を上げる条件` だけ（あれば）。区分の機械的ルールのルール 1 に足して当てる |
| フル版 | すべての節。必ず読む |

## 観点ファイルの書式

見出しは次の 4 つ。無い節は省いてよい（省いた節は「該当なし」と同じに扱う）。

```markdown
# <repo 名> の観点

## 区分を上げる条件
<!-- 形式 v3 の機械的ルール 1 に足す、この repo で「変えたら C」にするもの。1 行 1 条件 -->
- 例: `packages/contract/` の型を変える
- 例: 決済の状態遷移を変える

## 観点
<!-- 解説の項目 8 に、観点ごとに小見出しを立てて書く。該当が無い観点も「該当なし（確かめた範囲: …）」と書く -->
### 1. <観点の名前>
- 何を確かめるか
- 指摘にするときに書くこと（代わりの部品・API の名前、それが実装済みか など）

## 読むべき規約ファイル
<!-- フェーズ 2 で、汎用の対象に足して全文読むもの。対象リポジトリの中のパス -->
- `docs/review-guide.md`

## 参照するチームの skill
<!-- フェーズ 2 で読む、対象リポジトリの skill。観点の小見出しにそのまま使ってよい -->
- `.claude/skills/<レビューの skill>/SKILL.md`
```

書き方の目安:

- 観点は「どこを見て・何を確かめ・何を書くか」まで書く。抽象的な方針（「品質を見る」）だけだと、解説が観点の名前をなぞるだけになる
- 「共通部品を使っていない」のような指摘は、代わりの部品の props で要件を満たせるかまで確かめさせる（満たせないなら「置き換え不可。理由: …」）
- 「サーバーが返すべき」のような指摘は、代わりの API・field が**実装済みか**まで確かめさせる。契約のパッケージに依存する PR では、PR が依存する版と、読んだ契約のファイルの版が一致するかも確かめさせる

## 汎用の観点（観点ファイルが無いとき・観点ファイルに足して使う）

形式 v3 の区分 C に当たりやすいものを観点にする。各観点で「この PR に当たるか」を 1 行ずつ書く。過去の試行で、人間の重い指摘はこの種類に集まった。

- **権限の実効範囲**: 差分に書かれた権限だけでなく、共通部品（ヘルパー・ポリシーの共通設定など）が暗黙に足す権限まで追う。PR 本文が「権限を付けない」と書いていたら、実効の権限と突き合わせる
- **契約の重複定義**: サーバーの契約が返すべきデータ・型・enum を、クライアントで定義し直していないか（表示のための変換は除く）
- **デプロイ順と配置の制約**: 他のスタック・他のリポジトリとのデプロイ順、単独でデプロイしたときに依存が守られるか
- **同時実行**: 同じリソースを触るジョブ・関数・バッチが重なったときの競合、ロック、上限
- **再試行と冪等性**: 再試行・再配信・再実行で二重に書かない・二重に消さないか、途中で落ちた後の再実行で整合が戻るか
- **外部サービスの契約**: ページング（cursor の意味と、範囲を変えたときの続き方）、レート制限とそのエラーの分類（403 を認証エラーと一律にしない等）、公式の仕様に無い挙動への依存（本文が「仕様に無い」と認めていれば項目 4 に）
- **エラーと失敗の可観測性**: エラーの種類が集約で消えないか、除外・スキップした件数がログ・メトリクスに残るか
- **除外・保留・スキップの二次影響**: 孤児の削除・差し替え・通常の更新など、同じデータを触る兄弟処理を列挙し、除外した回に何が残るか・上書きされるかを書く
