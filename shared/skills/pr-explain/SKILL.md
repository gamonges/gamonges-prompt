---
name: pr-explain
description: レビュー依頼された PR を「AI に任せる部分」と「人間が読む部分」に分けて解説する（既定は軽い版、--full で検証・図解つき）。PR の URL を渡された時、`/pr-explain` で使用。
---

レビュー依頼を受けた人間（オーナー）が、PR の全実装を読まずに「どこを自分で読むか」を決められる解説を作る。どの GitHub リポジトリでも同じ手順で回る。チームや repo に固有のレビューの観点は skill の外の観点ファイル（`--lenses <dir>` か `PR_EXPLAIN_LENSES_DIR`。`./reference/repo-lenses.md`）から読み、無ければ汎用の観点だけで進める。

**読み取り専用。** GitHub への書き込み（コメント・レビュー・ラベル・approve）、対象リポジトリの checkout・編集はしない。コメント案は作るが、投稿はオーナーの OK の後に呼び出し側が行う（解説は AI の判断を含むので、人間が確かめる前に PR に載せないため）。

## モード

| モード | 呼ばれ方 | やること | 重さ |
|--------|---------|---------|------|
| 軽い版（既定） | レビュー依頼で自動で呼ばれるとき。`/pr-explain <PR>` | フェーズ 1 → 「軽い版」の節。区分・意図・人間が読むべき箇所・本文と差分の食い違いだけ | 数分 |
| フル版 | オーナーが本格的にレビューすると決めたとき。`/pr-explain <PR> --full` | フェーズ 1〜8 のすべて（規約の全文読み・repo 別の観点・検証パス・コメント案・図解・既出の指摘） | 数十分 |

**`--full` を付けるかは、呼び出した人（オーナー）が決める。** ボット・hook などが自動で起動するときは軽い版だけを回し、自分の判断で `--full` に上げない（フル版は時間がかかり、オーナーが軽い版を読んで「本格的に読む」と決めた PR にだけ使うため）。軽い版の報告の末尾の「フルで見るなら」の一行が、その判断の入口になる。

軽い版は、規約ファイルの全文読み・観点ファイルの「区分を上げる条件」以外の節・検証パス・図解・コメント案・既出の指摘の読み込みをしない。

**必ず読む**（両モード）:

| 補助ドキュメント | 読むタイミング |
|------------------|----------------|
| `./reference/format-v3.md` | 解説を書く時（区分の規則と各項目の書き方・雛形）。軽い版は「区分」と項目 1〜4 の節だけ |
| `./reference/repo-lenses.md` | フェーズ 1 の手順 5 で観点ファイルを探す時（探し方・モードごとに読む節・書式・汎用の観点） |

**フル版だけで読む**:

| 補助ドキュメント | 読むタイミング |
|------------------|----------------|
| `./reference/verify.md` | フェーズ 4 で検証のサブエージェントを起動する時 |
| `./reference/overview-template.html` | フェーズ 6 で図解のデータの形を確かめる時（雛形の既定のデータ。雛形は直接編集しない） |
| `./reference/comments-draft.md` | フェーズ 5 でコメント案を作る時（AI の指摘に、作者に伝える価値のあるものが 1 件以上ある時だけ） |

## パラメーター

```
/pr-explain <PR> [--full] [--no-open] [--lenses <dir>]
```

- `<PR>`: PR の URL（`https://github.com/<owner>/<repo>/pull/<n>`）か `<owner>/<repo>#<n>`。無ければ聞き返す（推測で PR を選ばない）。呼び出し側がボットで聞き返せないときは、ファイルを作らず「PR の指定が必要」と報告して終える
- `--full`: フル版で回す。省略時は軽い版
- `--no-open`: フル版の図解をブラウザで開かない（`ORCA_CHAT_SCRATCH_DIR` があるときは開かないので効かない）
- `--lenses <dir>`: 観点ファイルのディレクトリ。省略時は環境変数 `PR_EXPLAIN_LENSES_DIR`。中の `<repo 名（owner を除く）>.md` を読む（`./reference/repo-lenses.md`）

## 出力先

すべて現在の作業ディレクトリの `./tmp/pr-explain/<repo>-<n>/` に置く（`<repo>` は owner を除いたリポジトリ名。例: `acme/web#123` なら `./tmp/pr-explain/web-123/`）。既存のファイルがあるときは別名のディレクトリになる（フェーズ 1 の手順 2）。以下「出力ディレクトリ」はフェーズ 1 で確定したものを指す。

| ファイル | 中身 | モード・フェーズ |
|----------|------|-----------------|
| `quick.md` | 軽い版の解説（項目 1〜4 と「フルで見るなら」の一行） | 軽い版 |
| `diff.patch` | head の差分 | 両モードのフェーズ 1 |
| `explain.md` | 解説（形式 v3 + repo 別の観点 + 既出の指摘） | フル版 3・4・7 |
| `verify.md` | 検証のサブエージェントの結果（指摘ごとの判定と訂正） | フル版 4 |
| `comments-draft.md` | PR に付けるコメントの案（未投稿） | フル版 5（作る価値がある時だけ） |
| `data.json` | 図解のデータ | フル版 6 |
| `overview.html` | 図解 1 枚 | フル版 6（`ORCA_CHAT_SCRATCH_DIR` がある時は置き場所と名前が変わる。フェーズ 6 を参照） |

既存のファイルの確認と別名の決め方はフェーズ 1 の手順 2 に置く（head が分かってから決めるため）。`diff.patch` は毎回 head で取り直す。

## 実行プロセス

### フェーズ 1: PR の取得

両モードで次の順に行う。フル版も `quick.md` は読まず、ここから回す。

1. **PR の情報を取る**: `gh pr view "$PR_NUM" -R "$PR_REPO" --json number,title,body,author,state,baseRefName,headRefName,headRefOid,additions,deletions,changedFiles,files,url`（`PR_REPO='<owner>/<repo>'`・`PR_NUM='<n>'`）
   - 失敗したら（PR が見つからない・gh が未認証など）ファイルを作らず、原因を 1 行報告して終える
   - `state` が `OPEN` 以外（merged・closed）でも続ける。報告と解説の冒頭に状態を書く
2. **出力ディレクトリを決める**: 既定は `./tmp/pr-explain/<repo>-<n>/`。これから書くファイル（軽い版は `quick.md`、フル版は `explain.md`・`verify.md`・`comments-draft.md`・`data.json`・`overview.html` と、`ORCA_CHAT_SCRATCH_DIR` があればその直下の `<出力ディレクトリの名前>-overview.html`）のどれかが既にあれば、上書き / 別名 / キャンセルを確認する
   - 軽い版の後にフル版を呼ぶのが通常の流れなので、ディレクトリがあること・`quick.md` があることはフル版の確認の理由にしない
   - 別名は `<repo>-<n>-<head の先頭 7 桁>/`。それも既にあれば上書きを確認する（ボットなら末尾に `-2`・`-3` … を付けた最初の空き）
   - 呼び出し側がボットで確認できないときは別名にする（前回の解説を黙って消さないため）
3. **差分を取る**: `mkdir -p <出力ディレクトリ>` の後に `gh pr diff "$PR_NUM" -R "$PR_REPO" > <出力ディレクトリ>/diff.patch`。失敗したら（差分が大きすぎる等）原因を報告して終える（軽い版の `quick.md` も作らない）
4. **head が動いていないか確かめる**: `gh pr view "$PR_NUM" -R "$PR_REPO" --json headRefOid` を取り直し、手順 1 と違えば手順 1 からやり直す（取得中に push されると、差分は新しい head・成果物の SHA は古い head になる）。やり直しは 1 回だけで、2 回目も違えば「取得中に push が続いた」と報告して終える
5. **観点ファイルを探す**: `./reference/repo-lenses.md` の「観点ファイルの探し方」に従い、`--lenses <dir>` か `PR_EXPLAIN_LENSES_DIR` の `<repo 名>.md` を探す。見つかったらパスを控え、モードごとに決まった節を読む（軽い版は `## 区分を上げる条件` だけ、フル版はすべて）。無ければ汎用の観点だけで進め、解説に「repo 固有の観点なし」と書く

報告には、使った出力ディレクトリのパスを必ず含める。

- 差分とファイルの中身は **head（`headRefOid`）** で見る。ファイルは `gh api -H 'Accept: application/vnd.github.raw' "repos/$PR_REPO/contents/<path>?ref=<headRefOid>"` で読む（`--jq .content | base64 -d` は 1MB を超えるファイル（OpenAPI の生成型など）で中身が空になる。`download_url` を curl で取る方法は外部 curl の確認の hook に止まる）。ローカルに対象リポジトリのチェックアウトがあっても、作業ツリーが head と違いうるので根拠にしない（過去の試行では、ローカルが数週間古く、規約ファイルも契約も古い版を読んでいた）。
- PR 本文に書かれたチケット・関連 PR（サーバー側の対の PR など）は、番号と状態（open / merged）だけ控える。
- **既存のレビューコメント・レビュー・issue コメントはこの段階では読まない**（フェーズ 7 まで）。先に読むと、解説が既出の指摘をなぞるだけになり、見落としを拾えない。

### 軽い版: 区分と読む箇所だけを書く（`--full` が無いとき）

フェーズ 1 の後、ここで終える（フェーズ 2 以降には進まない）。

1. 差分（`diff.patch`）と PR 本文だけを根拠にする。規約ファイルは読まない（例外: 区分を決めるのに要る 1 ファイルだけを head で読むのはよい。読んだら項目に書く）
2. `./reference/format-v3.md` の「区分」の機械的ルールのうち、**ルール 1 と 3 だけ**を当て（観点ファイルの `## 区分を上げる条件` があれば、ルール 1 に足して当てる）、項目 1〜4 を書く。順序は項目 3（本文と差分の食い違い）を最初に
   - ルール 2（項目 6 に重大度「高」があれば C）は当てない。軽い版は項目 6 を書かないので、当てる材料が無い。そのため軽い版の区分は暫定で、B を付けても「フルで見れば C になりうる」
   - ルール 1 の「変える」かどうかが差分だけで決まらないとき（共通部品が暗黙に足す権限など）は C に倒し、理由に「軽い版では決まらない」と書く（人間が読まない側に倒さないため）
3. 雛形の項目 5〜9 は書かない。代わりに末尾に次の一行を置く

<!-- tmp-frontmatter: tmp/pr-explain/{repo}-{n}/quick.md -->
```markdown
---
type: PR Explanation
title: PR #{n} {タイトル}（{owner}/{repo} @ {head の先頭 7 桁}）軽い版
description: {区分}。{意図の 1 文}
status: draft
---
# PR #{n} 解説・軽い版（head {head の先頭 7 桁}）{タイトル}

## 1. 区分
## 2. 意図
## 3. 本文と差分の食い違い
## 4. 人間が読むべき箇所

---
フルで見るなら: `/pr-explain {owner}/{repo}#{n} --full`（規約の全文読み・repo 別の観点・検証・図解・コメント案。数十分かかる）
```

報告には次を含める（受け手が `quick.md` を開く前に、読むかどうかを決められるように）:

- 区分と理由 1 行（効いたルールの番号つき）
- 本文と差分の食い違いの件数
- 人間が読むべき箇所の `path:L行` の一覧（各 1 行の問いつき）
- `quick.md` のパス（出力ディレクトリ）と、PR が open でなければその状態
- 使った観点ファイルのパス、または「repo 固有の観点なし」
- 最後に「フルで見るなら」の一行

報告の後に、`html-view` で `quick.md` を HTML にするかを 1 回だけ提案する。呼び出し側がボットで、読み手が報告の本文しか見ないときは提案しない。

### フェーズ 2: 手順 0 — 対象リポジトリの規約ファイルを読む（フル版）

規約ファイルの本文を全部読む（例外: 1000 行を超える skill は関係する節だけでよい。読んだ範囲を一覧に書く）。存在を確かめただけ・一覧を見ただけでは「読んだ」に数えない。blind 試行で唯一拾えなかった指摘（無効ボタンの理由がキーボードで見えない）は、規約ファイルを読んでいれば拾えたものだった。

対象（あるものすべて）:

- `AGENTS.md`、`CLAUDE.md`、`REVIEW.md`、`DESIGN.md`（あるもの）
- 観点ファイルの `## 読むべき規約ファイル` と `## 参照するチームの skill` に挙がったもの
- `.claude/rules/**`、`.cursor/rules/**`（片方がもう片方のミラーなら、差分を確かめたうえで片方を全文読めばよい。そう判断した根拠を一覧に書く）
- `.claude/skills/*review*/SKILL.md`
- PR が触る領域に対応する `.claude/skills/<領域>/SKILL.md`（例: 一覧画面の PR なら一覧画面の skill）

読む版は head（`ref=<headRefOid>`）。head に無いファイルは base（`ref=<baseRefName>`）で読む。一覧は次の形で控え、`explain.md` の項目 7 にそのまま載せる:

| ファイル | 版（ref） | 行数 | 読んだ範囲 |
|----------|----------|------|-----------|
| `AGENTS.md` | head | 345 | 全文 |
| `.claude/skills/data-fetching/SKILL.md` | head | 1049 | キャッシュ設定の節のみ |
| `~/review-lenses/web.md`（観点ファイル） | 手元 | 40 | 全文 |

ディレクトリの列挙は `gh api "repos/$PR_REPO/git/trees/<headRefOid>?recursive=1" --jq '.tree[].path'` で取る。

### フェーズ 3: 解説を書く

`./reference/format-v3.md` の雛形で `explain.md` を書き、項目 8 に、観点ファイルの `## 観点` の観点ごとの小見出しと、`./reference/repo-lenses.md` の汎用の観点を書く（観点ファイルが無ければ汎用の観点だけで、「repo 固有の観点なし」と添える）。この時点では「既出の指摘」の節は空けておく。

書く順序は **項目 3（本文と差分の食い違い）を最初に**する。blind 試行で最も精度が高かった信号で（6 件中 6 件が後続の commit と一致）、項目 4〜6 の着眼点もここから出る。

### フェーズ 4: 検証パス

項目 6 の AI の指摘と、repo 別の観点で出した指摘を、**別のサブエージェント**（`general-purpose`）に head の実装で検証させる。プロンプトと出力の形は `./reference/verify.md`。書いた本人が見直すと同じ思い込みで通してしまうため、別の文脈で引き直させる。

- 対象: 重大度 高・中のすべて。低は、区分の判定に効くものだけ
- 結果を `verify.md` に保存し、訂正（行番号・件数・「未実装の可能性」の確定・誤検知）を `explain.md` に反映する。反映したら、検証で重大度が変わった指摘について区分の機械的ルールを当て直す（高が消えたら C の理由も消える）
- 検証の結果が「判定不能」のものは、指摘を消さずに「要確認（検証では決まらなかった: <理由>）」と書き添える

検証は 1 回で終える。訂正を反映した後に新しい指摘を足したときだけ、その指摘に限ってもう 1 回回す（上限 2 回。2 回目でも決まらなければ「要確認」で出す）。

### フェーズ 5: コメント案（任意）

検証を通った指摘のうち、作者に伝える価値があるもの（オーナー固有の観点の違反・a11y・契約の重複定義など）があれば、`./reference/comments-draft.md` の形で `comments-draft.md` を作る。行番号は検証で引き直した head の値を使う。**投稿しない。** フェーズ 7 で既出の指摘を読んだ後に案を見直す（作者が据え置きと説明済みのものは消し、逆の判断を理由つきで選んでいるものは書き直す）。

### フェーズ 6: 図解

データを `<出力ディレクトリ>/data.json` に書き、スクリプトで雛形に流し込む。雛形（`./reference/overview-template.html`）は直接編集しない（PR の文字列に `</script>` があると、手で埋め込んだ HTML ではスクリプトが動く。スクリプトはデータを検証し、そうした文字をエスケープして埋め込む）:

```bash
python3 ~/.claude/skills/pr-explain/scripts/render_overview.py --data <出力ディレクトリ>/data.json --out <置き場所>
```

skill は対象の作業ディレクトリで動くので、install 後の絶対パスで呼ぶ（`.py` に実行ビットは付かないので `python3` を前に置く）。exit 1 なら stderr の 1 行（どのキーが悪いか）を直して流し直す。

入れるもの:

1. 課題と目的（解決したい課題・この PR の目的・前提）
2. 解決の方法（まとまりごとのカード。新規・変更・差分の外のタグ付き）
3. 処理の流れ（入口から結果まで、番号付きの手順）
4. モジュールのつながり（新規・変更・差分の外を色・線種・箱の中の語で分け、項目 4 の「人間が読むべき箇所」に同じ番号のピンを付ける）
5. どこをどう変えたか（まとまりごとの追加行数。生成物は別の色）

データの形（雛形の既定のデータが例。スクリプトが検証する）:

| キー | 中身・制約 |
|------|-----------|
| `title`・`meta` | 文字列 |
| `purpose[]` | `{title, body}` |
| `method[]` | `{kind, title, body}`。kind は `new`・`mod`・`ext` |
| `flow[]` | 文字列 |
| `graph.columns` | 列の見出し。1 個以上 |
| `graph.nodes[]` | `{id, col, label, note?, kind, pin?}`。col は 0〜列数−1、id は一意、kind は `new`・`mod`・`ext`、pin は整数か整数の配列（同じファイルに読む箇所が 2 つ以上あるとき） |
| `graph.edges[]` | `[元の id, 先の id]` か `[元, 先, ラベル]`。同じ列の行や隣の列どうしを結ぶと線が箱を避けやすい |
| `pins[]` | `{n, where, question}`。n は整数。図に載らないファイル（生成物・設定など）のピンは、この一覧にだけ出す |
| `files[]` | `{kind, name, what, added}`。kind は `new`・`mod`・`ext`・`gen`、added は非負の整数 |

`files[].added` は、フェーズ 1 の `gh pr view` の `files[].additions` をまとまりごとに足した実数（目分量で書かない）。削除行数は図に出さない。文字列の中の `` `…` `` は code の表示になる。空の配列の節は見出しごと隠れる。

置き場所:

- `ORCA_CHAT_SCRATCH_DIR` が設定されていれば `"$ORCA_CHAT_SCRATCH_DIR/<出力ディレクトリの名前>-overview.html"`（既定なら `<repo>-<n>-overview.html`、別名なら `<repo>-<n>-<head の先頭 7 桁>-overview.html`）に置き、応答に行頭から単独の行で `::orca-visual{file="<その basename>" title="PR #<n> の全体像"}` を書いて表示する。`file` はディレクトリを含まない basename で、英数字・`.`・`_`・`-` だけ（それ以外の文字やコードフェンスの中では表示されない。repo 名にそれ以外の文字があれば `-` に置き換える）
- 無ければ `<出力ディレクトリ>/overview.html` に置き、`open` で開く（`--no-open` があれば開かない）

### フェーズ 7: 既出の指摘を読んで足す

解説を書き終えた後に、既存のレビュー・行コメント・issue コメントを読む:

```bash
gh api "repos/$PR_REPO/pulls/$PR_NUM/reviews" --paginate
gh api "repos/$PR_REPO/pulls/$PR_NUM/comments" --paginate
gh api "repos/$PR_REPO/issues/$PR_NUM/comments" --paginate
```

`explain.md` の末尾の「既出の指摘」に分けて載せる。解説の本文は書き換えない（何を独力で拾えたかが分からなくなる）。載せるのは次の 4 つ:

- 既出の指摘の要約と、作者の対応（直した / 据え置き）
- 解説と重なったもの（項目番号を添える）
- 解説だけにあって既出に無いもの（オーナーが優先して読む候補）
- 解説の指摘と逆の判断を、作者が既出のやりとりで理由つきで選んでいるもの（例: 指摘が「型を契約から取る」、作者が「ルート固有の型への依存を外すために文字列で受けた」）。指摘は消さず、作者の理由と両立する直し方があればそれを添える。コメント案（フェーズ 5）はこの判断を踏まえて書き直す

### フェーズ 8: 報告

呼び出し元に次を返す:

- 区分と理由 1 行、人間が読むべき箇所の数、重大度 高・中の指摘の数（検証後）
- 出力ディレクトリと出力したファイルのパス（コメント案を作ったかどうかを含む）。PR が open でなければその状態
- 使った観点ファイルのパス、または「repo 固有の観点なし」
- 図解の表示（`::orca-visual` の行、または開いた HTML のパス）

HTML 化は図解で済んでいるので、`html-view` の提案はしない。

## Gotchas

- **区分 C は「契約・権限を変える」とき。** 契約を使うだけ・権限スコープで表示を出し分けるだけでは C にしない（過去の試行で、契約の API をクライアントに登録して権限スコープで項目を隠しただけの PR を C にした。読む箇所は絞れたので B が妥当だった）。詳細は `./reference/format-v3.md` の区分の節
- **契約の版を確かめる。** PR が契約のパッケージ（サーバーとクライアントで共有する型など）に依存するとき、PR が依存する版と、読んだ契約のファイルの commit が一致するかを見る（過去の試行で、古い commit の契約を引用して「未実装の可能性」と書き、実装済みの API の一覧も古かった）
- **指摘の「件数」は検証で数え直す。** 同じ定数を使っていても、表のセルの値と装飾の中身は別物のことがある（過去の試行で、5 箇所のうち 1 つが装飾で、規約違反は 4 箇所だった）
