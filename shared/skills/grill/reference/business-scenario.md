# 業務シナリオ記述の正典

`./tmp/scenario.md` について **3 つの関心事**を定義する — **いつ立てるか（発火判定）** / **どう書くか（記述書式）** / **何をもって閉じるか（完了の記録欄）**。

本ファイルが唯一の正典で、次の 7 skill がここを参照する（各所にコピーを持たない）:

| skill | 使う場面 |
|-------|---------|
| `grill` | Phase 0 = 主経路（発火判定・生成） |
| `design` | フェーズ 1.2 = フォールバック（発火判定・生成）、フェーズ 1.6 = Notion 反映 |
| `implement` | Phase 1 = 発火判定、Phase 4 = DoD 検査 |
| `spec-propose` | フェーズ 5.2 = openspec へ昇格 |
| `verification-authoring` | 順流 = 出口ごとの `Driving it` エントリ生成 |
| `create-pr` | PR 本文生成 = `tmp/` 確定事項との照合 |
| `ask` | 読むだけ = 状態の判定と、題材が一致する `S-n` を調査の前提に使う（判定・生成はしない） |

**なぜ 1 箇所に固定するか**: 発火判定は `grill` / `design` / `implement` の 3 経路が行い、記述書式は上表の 7 skill が読む。基準や項目名を各 skill に書くと、片方に判定や項目を足したときもう片方がずれる。**基準と書式は本ファイルに 1 回だけ置き、適用手順（列挙の集約・判定の帰結・反復の打ち切り）は各 skill 側に置く。**

## 何のために書くか

QA 指摘の再発原因は「**同一機能に複数の入口と複数の出口があり、その網羅が誰の責務にもなっていない**」ことにある。入口 3 つのうち 1 つだけ直して QA で落ちた例と、出口の画面名は既知だったのに期待値が書かれていなかったため「仕様どおりの動作」が指摘になった例が、いずれも実在する。業務シナリオは**実装前に入口と出口を網羅列挙し、期待値を言語化する**ためのものである。

**PdM が読める言葉で書く。** 内容は Notion の価値ページへそのまま反映され、PdM / QA へ確認を依頼する材料になる。テーブル名・カラム名・関数名で書くと、依頼された相手が期待値の違和感に気づけない。

## 発火判定（判定 1・2）

「業務シナリオを立てるか、`## 判定: シナリオ不要` で閉じるか」を次の 2 判定で決める。2 判定は**同じ列挙**（今回の変更が触る属性・列）に当てる — 判定ごとに独立したトリガーを置くと、どれかが必ず形骸化するため。

| # | 判定 | Yes の基準 |
|---|------|-----------|
| **判定 1** | **前提を置き換える属性か** | 列挙した属性のうち、既存の暗黙の前提（「全員がメールを持つ」等）を置き換えるものがある。必須 → 任意 / 単一 → 複数 / 一意 → 重複可 のような**制約の緩和**が典型 |
| **判定 2** | **何役を兼ねている列か** | 1 つの列が複数の役（識別子 / 表示名 / 連絡先 / 認証情報 等）を兼ねている。役が分岐したとき、片方の役だけを見た実装が生まれる |

- **いずれかが Yes → `S-n` を立てる**（下記「記述書式」）
- **いずれも No → `## 判定: シナリオ不要` で閉じる**（下記）

純技術的な内部変更に業務シナリオを強制しない（`grill/SKILL.md` の観点節と同じ方針）。ただし**判定したこと自体は記録する** — 理由は次節。

**`## 判定: シナリオ不要` の 1 ブロックを書く手間は暫定的に許容している。** 実運用で摩擦が過大とわかった場合は、判定そのものを消すのではなく**発火側に足切り条件を足して頻度を下げる**（`implement` Phase 1 が同じ型の足切りを持つ）。判定の記録を消すと、未判定と不要を見分けられない状態に戻る。

## `./tmp/scenario.md` の 3 つの状態

本ファイルを読む skill は、いずれも次の 3 状態を分岐する。**状態名は本節の定義を参照し、各 skill で言い換えない**（状態を 1 つ増やすと参照側すべてに要るため）。

**例外**: `spec-propose` は「不在」と「シナリオ不要」を同一扱いにする（どちらも昇格をスキップ）。理由は、不在は `implement` Phase 1 / Phase 4 が既に検知しており、`spec-propose` でも止めると二重の確認になって承認が形骸化するため。

**評価順**（この順で上から当て、最初に該当した状態を採る。3 状態は相互排他）:

| # | 状態 | 見分け方 | 意味 |
|---|------|---------|------|
| 1 | **S-n あり** | `## S-<数字>:` のブロックが 1 つでもある | 業務シナリオが立っている |
| 2 | **シナリオ不要** | 上に該当せず `## 判定: シナリオ不要` がある | 判定済み・不要 |
| 3 | **不在** | ファイルが無い、または上のいずれにも該当しない | **未判定**。発火判定を通していない、またはファイルを失った |

`## 判定: シナリオ不要` と `## S-<数字>:` が併存するファイルは **S-n あり**として扱う（シナリオが立っている以上、判定は済んでいる）。見分け方に `## S-1:` と固有の番号を書かないのは、`S-1` を削除したファイルが「不在」と誤判定されるため。

**「不在」を「シナリオ不要」と同一視しない。** `tmp/` はコミットされず、worktree の削除やセッションの作り直しで容易に失われる。不在を「不要」として扱うと、**シナリオを立てるべき変更でファイルを失っただけで完了判定が黙って通る**。判定結果そのものをファイルとして残すことで、「不在 = 未判定」と「判定済み = 不要」を分離する。

**塞がらない範囲**: `./tmp/scenario.md` はコミットされないため、レビュアや CI からは検査できない。保証されるのは「同一ローカル作業ツリー内で、判定を飛ばしたことが検知される」ところまでである。

## 題材の同一性（frontmatter と resume）

`./tmp/grill.md` と同じ規約を適用する — **同一題材なら resume（in-place で継続）／別題材なら上書き前に 1 問確認**する（`grill/SKILL.md` の入力節）。2 つのファイルで挙動が違うと、前題材の残骸を今回のシナリオと誤認する事故になる。

**不一致のときの 1 問は次の 3 択で、それぞれ帰結を持つ**（`/design` フェーズ 1.5 の確認と同じ形に揃える）:

| 選択肢 | 帰結 |
|--------|------|
| **上書き** | 既存の `S-n` を破棄し、新しい題材で `S-1` から書き直す |
| **追記** | 既存を残し、**既存の最大 `n` + 1** から新しい `S-n` を足す（採番の衝突を避ける） |
| **キャンセル** | `scenario.md` を触らず、Phase 0（または `/design` フェーズ 1.2）を中断する |

frontmatter（`grill.md` と同型。`type` と **`title` が必須**、他は任意 — `title` は上記の同一性判定に使うため、未記入だと判定が成立しない）:

```yaml
---
type: Business Scenario
title: <題材>                        # 同一題材かの判定に使う（**本ファイルでは必須**）
description: <この変更で何が変わるかの要約>
tags: [business-scenario, ...]
timestamp: <最終更新日時 ISO8601>    # in-place 更新のたびに現在時刻へ上書き
---
```

## 記述書式（固定 5 項目）

1 シナリオを `## S-n:` の 1 ブロックで書く。項目は 5 つで固定する（自由記述は網羅が保証されず、Gherkin 風は入口・出口が複数だと行が爆発する）。

```markdown
## S-1: <シナリオ名 = 主語が何を達成するか>
主語:  <人物像>
入口:  (1) <画面パス>  (2) <画面パス>  (3) …
操作:  <主語がその入口で行う操作>
出口:  (1) <画面名> → <期待値>
       (2) <画面名> → <期待値>
前提の置換: <属性名>（<変更前> → <変更後>）
```

| 項目 | 書き方 | なぜそう書くか |
|------|--------|---------------|
| **主語** | 人物像で書く。**判定 1 が Yes なら、その属性を持たない主語を必ず 1 つ含める** | 前提を置き換える変更は、置き換わった側の主語を立てない限り入口も出口も出てこない |
| **入口** | **網羅列挙**する | 1 つでも欠けると、そこだけ直し残して QA で落ちる |
| **操作** | 主語がその入口で行う操作を 1 行で書く | 入口ごとに操作が違う場合は `S-n` を分ける |
| **出口** | **画面名 ＋ 期待値のセット**で書く | 画面名だけでは不足する。期待値が書かれて初めて PdM / QA が違和感を持てる |
| **前提の置換** | `<属性名>（<変更前> → <変更後>）` | 判定 1 の入力そのもの。後から読む側が、どの前提が動いたかを 1 行で掴める |

## 完了の記録欄（`S-n` ごと）

各 `S-n` の末尾に 2 行を置く。**どちらも未記入のまま完了判定を通さない。**

```markdown
Notion 反映: <価値ページ URL> / 反映日: <YYYY-MM-DD> / 確認依頼先: <相手>
確認の決着: <確認済み | 未回答のため開発者判断でクローズ> / 判断者: <名前> / 日付: <YYYY-MM-DD> / 理由: <理由>
```

- **Notion 反映**: 仕様が確定した時点（実装前）に価値ページへ反映し、確認を依頼する。反映先 URL が無い場合は書き込まず、**未解決として上げる先は経路ごとに異なる** — `grill` からは `tmp/grill.md` の「未決事項」へ、`design` からは plan.md の「オープン質問」へ（`grill` の成果物に「オープン質問」節は無い）
- **確認の決着**: 確認の**返信を必須にしない**。未回答なら開発者が判断して閉じ、**判断者 / 日付 / 理由**を残す（返信を必須にすると、確認が要らない変更でも実装が止まる）

**この欄が保証する範囲**: 「**期待値が実装前に書かれ、確認が依頼された**」ところまで。期待の食い違いそのものの解消は保証しない。

## `## 判定: シナリオ不要` の書式

発火判定がいずれも No のとき、`S-n` を立てず次の 1 ブロックだけを書いて閉じる。

```markdown
## 判定: シナリオ不要
理由: <判定 1・2 がいずれも No である理由。列挙した属性・列を名指しする>
判定日: <YYYY-MM-DD>
```

**形式だけ埋めた `S-n` を立てない。** 埋められない項目は未解決として上げ（経路別の行き先は「完了の記録欄」節と同じ — `grill` は「未決事項」、`design` は「オープン質問」）、形だけの `S-n` は後続の DoD 検査が「S-n あり」の経路として扱うため、不要な確認依頼と未回答クローズの記録が連鎖する。

## 例

### BAD

```markdown
## S-1: 電話番号でアカウントを発行できるようにする
主語:  ユーザー
入口:  一括発行画面
操作:  電話番号で発行する
出口:  アカウント一覧に出る
前提の置換: -
```

- **主語が「ユーザー」**: 前提を置き換える属性を持たない主語になっておらず、立てた意味が無い
- **入口が 1 つ**: 網羅列挙になっていない（実際は 3 経路ある）
- **出口に期待値が無い**: 「出る」だけでは何がどの列に出るのかが決まらず、PdM / QA が違和感を持てない
- **前提の置換が空**: 判定 1 が Yes だったことの記録が失われる

### GOOD

```markdown
## S-1: メールを持たない従業員に電話番号で発行する
主語:  業務メール未登録・メイン電話番号のみ登録の従業員
入口:  (1) ITOC＞一括発行  (2) ソフトウェア詳細＞アカウント追加  (3) アラート＞要発行タブ
操作:  発行 ID 種別=メイン電話番号 の Software でアカウントを発行する
出口:  (1) Software アカウント一覧 → 発行に使った電話番号が ID 列に出る
       (2) ライセンス＞アサインメント一覧 → 同上
       (3) アラート＞要発行タブ → 対象者が消える
前提の置換: email（必須 → 任意）
Notion 反映: <価値ページ URL> / 反映日: 2026-09-18 / 確認依頼先: PdM
確認の決着: 未回答のため開発者判断でクローズ / 判断者: <名前> / 日付: 2026-09-18 / 理由: 既存実装の表示規則に揃えた
```

## PUBLIC リポジトリの制約

本ファイルに capability 名・テーブル名・URL・組織 ID を書かない。例は**画面名レベル**に留める（`verification-authoring/SKILL.md` の同名節と同じ制約）。具体値は各作業ツリーの `./tmp/scenario.md` 側にのみ置く。
