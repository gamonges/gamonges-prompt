計画・設計・前提を、共有理解に達するまで詰める。意思決定ツリーを上流から辿り、各分岐でまず「決めるために必要な情報」を洗い出し、前提が揃った分岐だけを決定へ進める。質問の出し方は下記「質問の粒度」節に従う。

**出力先**: 進行中の状態は `./tmp/grill.md` に集約し、業務シナリオだけは `./tmp/scenario.md` に分ける（いずれもコミット対象外）。ソースコードは変更しない。分けるのは、`scenario.md` を `/design` `/implement` `/spec-propose` が読む skill 間の受け渡しファイルとして使うため。

## 入力

`$ARGUMENTS` で grill 対象のコンテキストファイルを指定できる（**任意**）。省略時は `./tmp/plan.md` → `./tmp/context.md` の順で存在するものを初期材料に使う。いずれも無ければ、最初の1問で「何を grill するか」を聞いて開始する（`/design` のような即停止はしない）。

- **調査結果**: `./tmp/research.md`（`/ask` の出力）があれば材料として読む。まず記録ブロック（`---` 区切り。区切りが無ければ全体で 1 ブロック）ごとに、見出し・質問・内容から題材を読み取り、入力ファイルの `title` / H1 の題材と一致するかを確かめる。一致しないブロックは材料にせず、その旨を 1 行報告する（前タスクの調査を今回の事実として取り込まないため）。一致するブロックは照合度ラベルで扱いを分ける:
  - **[Read] / [grep]**: 根拠（research.md の該当箇所）を添えて「確定事項」に入れてよい。基準コミットが現在の HEAD と異なれば、その旨も添える
  - **[subagent] / [推測]** とラベルの無い主張: 確認が必要な前提として扱う（裏取りの無い主張を「確定事項」に入れると、以後の決定がその上に積まれるため）
- **モード**: モードの解決と適用範囲は正典（`../brief/reference/modes.md`）に従う。引数を省略して `./tmp/plan.md` を初期材料にした時、`./tmp/context.md` に `mode:` があれば「context.md のモードは使っていない」と 1 行報告する（前タスクの plan.md が残っていると、宣言したモードが黙って効かなくなるため）

既存の `./tmp/grill.md` がある場合は中身を読み、**同一題材なら resume（in-place で継続）／別題材なら上書き前に1問確認**する。不在なら新規作成する。

## コア原則

- **質問の粒度**: ブロッカーは 1 問ずつ、それ以外は 3〜4 問ずつ束ねて出す（判定基準と出し方は下記「質問の粒度」節）。
- ユーザーに聞く前に、repo / docs / diff / config で分かることは自分で探索して確認する。単一の探索や1ファイルで完結する確認は直接行い、複数の独立した確認が要る場合は同一ターンで並列に調べる。
- **情報のブレ防止**: 確定した事実は `./tmp/grill.md` の「確定事項」を単一の真実源とし、以後はそこを参照・更新する。会話の流れで再解釈しない。
- **コンテキスト肥大化の防止**: チャット出力は「直前に確定した n 行」＋「次の 1 問（ブロッカー）または 3〜4 問（束ね）」に絞る。全体像は毎ターン再掲せず `./tmp/grill.md` と `./tmp/grill.html` に外出しする。
- あいまいな回答はそのまま進めず、より具体的な次の1問で絞る。
- おすすめ回答は押し付けず、判断理由を短く添える。
- 設計の選択肢を複数提示するときは、各案に **pros/cons を表で必ず併記**する。選ばせるのが目的でなく、判断に必要な情報を揃えるのが目的。
- `AskUserQuestion` ツールは束ねた質問と、タスク所有者の振り分け・優先度確認など非設計の分岐に使う。**ブロッカーには使わない**（理由は下記「質問の粒度」節）。

## 質問の粒度

- **ブロッカー** = **後続の分岐の形（選択肢の集合）を変える上流の決定**。1 問ずつ、markdown の単問で出す
- **それ以外**は 3〜4 問ずつ束ね、`AskUserQuestion` で出す。選択肢が短くクリックで済み、決断疲れが減る

**運用テスト**: 「この問いの答えが A か B かで、**次の質問の選択肢そのものが変わるか**」— 変わるならブロッカー、変わらなければ束ねる。基準を決めずに運用すると「全部ブロッカー」に倒れ、束ねが消えて一問一答へ戻る。

**ブロッカーに `AskUserQuestion` を使わない理由**: ブロッカーは pros/cons が長く、選択肢の説明欄に収まらない。上記コア原則の「各案に pros/cons を表で必ず併記する」を満たせなくなる。

**束ねるときの「おすすめ回答」**: 選択肢の `description` に判断理由を短く書き、推す案を先頭に置く（markdown の単問と違い「おすすめ回答:」の行を立てない）。**束ねの下限は設けない** — 残り 1〜2 問でも、ブロッカーでなければ束ねて出す（単問に落とすかどうかは問いの性質で決め、残数では決めない）。

**判定の補助線**: 上の運用テストでブロッカーと判定されなかった問いでも、pros/cons が表を要する規模になったら markdown の単問に落とす。**第一基準はあくまで運用テスト**（後続の分岐の形が変わるか）で、補助線はそれを満たさない問いに対する追加条件である — 理由は、束ねた選択肢の説明欄に pros/cons 表が収まらず、コア原則の「各案に pros/cons を表で必ず併記する」を満たせなくなるため。

**この使い分けは暫定採用。** 運用して合わなければ一問一答へ戻す。差し戻す対象は次のとおり:

- 「質問の粒度」節（本節全体）
- コア原則の 3 行 — 「質問の粒度」/「コンテキスト肥大化の防止」/ `AskUserQuestion` の使い分け
- 「フェーズ遷移（per-branch gate）」節の、gate 結果の畳み込み単位を述べた行
- 「ワークフロー」手順 5 の、粒度に言及した箇所

他の節は粒度に依存していないため、ここだけ戻せば一問一答に復帰する。**対象を行番号で書かないのは、節の追加や再採番で参照が壊れるため。**

## Phase 0（業務シナリオの確立）

grill 起動直後に、今回の変更の**主語（人物像）・入口・出口**を確立して `./tmp/scenario.md` を生成する。**記述書式・発火判定の基準・3 状態の定義は `./reference/business-scenario.md`（正典）にあり、ここでは再宣言しない。** 本節は正典の基準を「どう当てるか」だけを持つ。

**既存の `./tmp/scenario.md` がある場合**は、正典の「3 つの状態」と「題材の同一性（frontmatter と resume）」に従って先に分岐する — **S-n あり**なら `title` の一致を確認して resume（不一致なら上書き前に確認）、**シナリオ不要**なら `title` の一致を確認して判定済みとして Phase 0 を閉じる（不一致なら、上書き（今回の題材で判定 1・2 からやり直す）かキャンセルかを確認する。シナリオ不要には足す `S-n` が無いので、正典の 3 択のうち追記は選択肢に入れない。前題材の「シナリオ不要」の判定を今回の題材に流用しない）、**不在**なら以下の手順で新規生成する。`./tmp/grill.md` と同じ resume 規約を `scenario.md` にも適用するのは、前題材の残骸を今回のシナリオと誤認しないため。

**列挙は 1 回に集約する**: 「今回の変更が触る属性・列」を 1 回だけ列挙し、その同じ列挙に正典の**判定 1（前提を置き換える属性か）**と**判定 2（何役を兼ねている列か）**を当てる。判定ごとに独立したトリガーを置くと、どれかが必ず形骸化するため、入力を共有して出力だけを 2 判定に分ける。

判定の帰結:

1. **判定 1 が Yes** → (a) 正典の記述書式表「主語」の規則を適用する (b) その属性の**全件 grep 棚卸し**で入口・出口を洗い出す (c) Notion 価値ページへの反映と確認依頼を課す（記録欄は正典の「完了の記録欄」）。**反映先 URL は Phase 0 の中でユーザーに 1 問で尋ね、「Notion 反映」欄に記入する**（この時点で反映日・確認依頼先は空でよい）。ユーザーが URL を持たない場合は `反映先 URL: 未定` と明記して閉じ、`/design` フェーズ 1.2 で再度尋ねる
2. **判定 2 が Yes** → その構造に名前を付け、**役ごとに主語を分けられるか**を確認する
3. **いずれも No** → 正典の `## 判定: シナリオ不要` の書式で書いて Phase 0 を閉じる

**URL を Phase 0 で尋ねる理由**: 反映先 URL の消費側（正典の「完了の記録欄」も `/design` フェーズ 1.2 も）はいずれも「URL が書かれていれば」という受け身の条件で発火する。生産する主体を決めないと、ユーザーが自発的に書かない限り Notion 反映と確認依頼は一度も実行されない。

**下記「観点」節との関係**: Phase 0 は無条件に通るフェーズ、観点節は条件付きで適用される節であり、**包含関係ではなく同じ方針を共有する**関係にある — 「変更内容が実際に触れる観点だけを立てる」という方針は両者に等しく当てはまる。純技術的な内部変更では判定 1・2 がいずれも No になるが、**素通りさせず `## 判定: シナリオ不要` の 1 ブロックだけを書いて閉じる** — 判定の記録が無いと、後続の DoD 検査が「未判定」と「不要」を見分けられない（正典の「3 つの状態」）。

反復の 4 点:

- **開始トリガー**: grill 起動直後。ワークフロー手順 2 の要約・初期化より前（Phase 0 はワークフロー手順 1 そのもの）
- **反復トリガー**: 固定 5 項目のうち未確定のものが残っている間
- **完了条件**: 判定 1・2 がいずれも No で `## 判定: シナリオ不要` を書いた時点、または 5 項目すべてが `./tmp/scenario.md` に埋まり、**判定 1 が Yes の場合は「Notion 反映」欄の URL が記入済み（または `未定` と明記済み）になった時点**
- **打ち切り**: 判定 1(b) の全件 grep 棚卸しは **1 巡で打ち切る**。確定しなかった入口・出口は「情報要求マップ」へ回し、Phase 0 自体は閉じる。Phase 0 で全入口を確定できないこと自体は許容し、未確定であることを可視化する（前提が揃う前に決定を迫らない、という下記 gate の方針と同じ）

## フェーズ遷移（per-branch gate）

各意思決定ノードで `Phase 1 → gate → Phase 2` を辿る。

- **Phase 1（情報の洗い出し）**: 「この分岐を決めるには何を知る必要があり／誰が持ち／どう計測・取得するか」を問う。
- **gate**: 決定に必要な前提事実がその場で揃ったかを判定する。
- **揃った場合 → Phase 2（決定前進）**: 推奨する設計判断を「おすすめ回答」として提示する。
- **揃わない場合 → 保留**: 「情報要求マップ」に記録し、その分岐の決定は保留したまま次の分岐へ進む。

前提が揃う前に決定を迫らない。

gate の結果は「直前の確定 n 行」に畳み込む（粒度は「質問の粒度」節に従う）。前進時は確定行に含め、保留時は「〈不足情報〉待ちで保留 → 情報要求マップに記録」の1行だけ示す。「Phase 1 に入ります」等のフェーズ実況はしない。

## 質問フォーマット

```
質問: …

おすすめ回答: …
```

- **Phase 1 のおすすめ回答** = まず取るべき情報（項目 × 取得元 × 計測・取得方法）。決定ではない。
- **Phase 2 のおすすめ回答** = 推奨する設計判断とその根拠。複数案があれば pros/cons 表を添える。

必要なら、質問の前に1–2行だけ現在の整理を添えてよい。

## 観点（条件付きトリガー）

変更内容が実際に触れる観点だけを質問として立てる。純技術的な内部変更で、業務観点を機械的に全件問わない。**業務・技術のどちらを強く掘るかは変更の性質で都度判断する**（優先度を固定しない）。既知のモードに解決したら `## grill の観点` を、依存順（上流の決定から）を崩さない範囲で先に確かめる候補として使う。候補を足すだけで、優先度を固定しないという方針は変えない。

- **業務・運用**: 顧客影響 / 権限 / データ移行 / 既存顧客 / 請求・会計・監査 / サポート・運用負荷。
- **セキュリティ・個人情報**: 認証・認可 / 個人情報（PII）の取り扱い / データ保護・漏洩時の影響。
- **技術**: API / data flow / state / failure mode / migration / rollout / test / 可観測性（監視・ログ・アラート）/ パフォーマンス・スケール。
- **整合性**: 既存コードベースの責務分界・命名・データモデル・運用パターンとの整合。技術的に実装可能でも、顧客体験・業務フロー・既存運用に対して不自然なら、その違和感を質問として扱う。
- **仮説の検証**: ユーザーの仮説について、根拠が薄い点・反例・未検証の前提・代替案を確認する。

## 成果物: `./tmp/grill.md`（OKF 準拠・単一ファイル）

[Open Knowledge Format](https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing) の単一概念ドキュメントとして生成する。先頭に YAML frontmatter を置き、本文に4ブロックを持つ。毎ターン in-place で更新し、履歴（`log.md` 相当）は貯めない。

frontmatter（`type` のみ OKF 必須、他は任意）:

```yaml
---
type: Grill Session
title: <題材>
description: <このセッションで詰める対象の要約>
tags: [grill, ...]
timestamp: <最終更新日時 ISO8601>   # in-place 更新のたびに現在時刻へ上書き
---
```

本文の4ブロック:

1. **確定事項** — 決定した分岐とその根拠。以後の単一の真実源。各項目に `D-n`（確定順の通し番号）を振る。
2. **情報要求マップ** — 未取得の分岐。`項目 × 取得元（redash / PdM / インフラチーム / … ） × 計測・取得方法` の表。
3. **分岐ツリー** — 残っている分岐と依存関係、現在地マーク。
4. **未決事項** — 保留中の分岐と保留理由。

コード参照や概念間リンクは `file_path:L{number}` / markdown リンクで記す。

### HTML（読む用ビュー）

`./tmp/grill.md` と `./tmp/scenario.md` が正で、**`./tmp/grill.html` は `grill.md` の 4 ブロックと `scenario.md` の業務シナリオを表示するだけのビュー**。HTML にしか無い情報を持たせない（持たせると正が 2 つになり、どちらが最新か読み手に判断させることになる）。

- **Phase 0 の完了時に 1 回だけ HTML 化を提案する。** 了承されたら `html-view tmp/scenario.md --output tmp/grill.html --style generic` で土台を作ってブラウザで開く（`--output` を付けないと出力が `tmp/scenario.html` になる）。html-view を使うのはこの 1 回だけで、以後は grill が `tmp/grill.html` を Edit で更新する（html-view は入力を 1 つしか取らず、`scenario.md` と `grill.md` を 1 枚にまとめられないため）。**Phase 0 で既存の `tmp/scenario.md` を同一題材として resume し（`title` が一致し。シナリオ不要で `title` が一致して閉じた場合を含む）、かつ `tmp/grill.html` が在ってその `<title>` が `scenario.md` の `title` と一致すれば、提案も html-view も行わずにその HTML を使い続け、HTML 化を了承済みとして扱う**（`grill.md` の `title` とは比べない。手順 2 より前の `grill.md` は前回の題材のことがあり、題材 X の残骸どうしが一致して、題材 Y を X の決定カードの下に足してしまう。html-view は既存の HTML を確認せずに作り直すので、呼ぶと決定カードが消える）。Phase 0 で `scenario.md` を新規作成・上書き・追記したとき、`tmp/grill.html` が無いとき、または `<title>` が一致しないとき（別題材の残骸）は、HTML が無いときと同じく 1 回だけ提案し、了承されたら土台を作る（断ったかどうかは記録しないので、HTML が無ければ実行ごとに 1 回提案する。確認せずに作り直さない。追記では前の題材の `S-n` も残るので、`<title>` の照合に使わない）。中身はここでは入れず、ワークフロー手順 2 の後に入れる（下記）。提案は繰り返さない（HTML 化の規約の例外として `AGENTS.md` に明記してある）
  - この時点で表示できるのは `scenario.md` の業務シナリオ（または `## 判定: シナリオ不要`）だけで、`grill.md` の 4 ブロックはワークフロー手順 2 以降で埋まる。**業務シナリオを最初に共有するのが目的**であり、空の 4 ブロックを表示するためではない
- **更新は差分だけにする**（HTML 化を了承された場合と、Phase 0 の完了時に既存の HTML を使い続けた場合）: 手順 2 で `grill.md` の扱い（新規作成・上書き・同一題材の resume）が決まったら、この手順で 1 回だけ次を行う（section を足すのはこの 1 か所）。業務シナリオ（土台の `<main>` の中身）がまだ `<section id="scenario">` で包まれていなければ包んで、中身を `scenario.md` の今の内容にそろえ（Phase 0 の resume で埋めた項目を反映する）、その後ろの 4 ブロック分の `<section id="decisions">`・`info-map`・`tree`・`open` を、`grill.md` の対応するブロックの今の中身（決定カードを含む）でそろえる（無ければ足し、在れば丸ごと差し替える。新規作成・上書き・resume のどれでも同じ規則にする。土台を作り直したかどうかや、無い section だけを足すかで分けると、`<title>` が偶然一致した土台で決定カードが出ない・`grill.md` を作り直したのに前の題材のカードが残って `id` が重複する）。**最後に** `tmp/grill.html` の `<title>` を `scenario.md` の `title` に書き換える（html-view の generic は見出しを入力の最初の `#` 行か basename から作るので、土台の `<title>` は題材と一致しない。次回の Phase 0 の照合がこの `<title>` に依る。書き換えを最後に置くのは、section を足す前に止まった土台を、次回に一致と取り違えて使い続けないため）。以後、決定は 1 件 1 カードにして `#decisions` の末尾に足す（Edit）。ほかの 3 ブロックと業務シナリオは、変わったセクションだけを丸ごと差し替える（`scenario.md` が変わったら `#scenario` の section を差し替える）。決定のたびに `html-view` を実行し直して全文を書き直さない。ブラウザは再読み込みで追従してもらう（決定のたびにタブを開き直さない）

  ```html
  <article class="decision" id="D-n"><h3>D-n: {title}</h3><p><strong>決定</strong>: {decision}</p>{body}<dl><dt>根拠</dt><dd>…</dd><dt>退けた案</dt><dd>…</dd><dt>派生</dt><dd>…</dd><dt>備考</dt><dd>…</dd></dl></article>
  ```

  `D-n` は `grill.md` の確定事項に振った番号と同じにする（Edit で差し替える箇所を一意に決めるため）。空の項目は `<dt>` ごと省く。`.decision` の規則が要るなら、初回だけ `<style>` に足し、色は `:root` の変数を使う
- 上記「コンテキスト肥大化の防止」との関係: **全体像の再掲先がチャットから `tmp/grill.html` へ移る**のであって、毎ターン再掲しない方針そのものは変えない

## ワークフロー

1. **Phase 0** を通し、`./tmp/scenario.md` に業務シナリオまたは `## 判定: シナリオ不要` を書く。
2. ユーザーの計画・設計・前提を短く要約し、未確定の意思決定を洗い出して `./tmp/grill.md` を初期化する（既存ファイルの扱いは「入力」節を参照）。
3. repo / docs / diff / config で答えられる事実は、質問せず探索して埋める。
4. 分岐を依存関係で整理し、上流の決定から順に着手する。
5. 各分岐で Phase 1 → gate → Phase 2 を進める（粒度は「質問の粒度」節に従う）。回答を受けたら、確定したこと・新しく分岐したことを `./tmp/grill.md` に反映し（in-place 更新）、HTML 化を了承されていれば `./tmp/grill.html` も更新し、チャットには「直前の確定 n 行 ＋ 次の質問」だけを返す。
6. 終了時は「確定事項」と「未決事項」を分けて簡潔にまとめ、末尾に次工程「`/design tmp/grill.md`」を案内する（`tmp/grill.md` はそのまま `/design` の `$ARGUMENTS` になる）。

## 終了・継続の判断

次の優先順位で判断する:

1. **ユーザーの明示中断が最優先** — 「まとめて」「stop」等が来たら、その時点で即「確定事項／未決事項」を出力して終了する。
2. **達成条件があれば満たすまで継続** — 会話でユーザーが明示した達成条件、または `./tmp/goal.md`（あれば読む）が満たされるまで grill を続け、skill 起点の停止提案は抑制する。特定の `/goal` 実装には密結合せず、「達成条件があれば従う」疎結合の契約とする。
3. **達成条件がなければ自発的に停止提案** — 主要な分岐が解決した、または残る分岐がすべて外部情報待ちでブロックされたら、停止してまとめることを提案する。「主要な分岐」＝他の分岐や実装方針への依存・影響が大きい分岐。leaf の細部詰めはしない。ハードな質問数上限は設けない。
