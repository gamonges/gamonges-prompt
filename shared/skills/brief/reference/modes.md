# モードの正典

「モード」は、作業の用途（概念設計・実装・リファクタリング・バグ調査）を宣言し、各工程の skill が**既定で優先する観点**を切り替えるための値である。本ファイルは **一覧・解決規則・消費者・変えてよい範囲** を定義する唯一の正典で、観点の中身は `./modes/<mode>.md` の各節に置く。

**なぜ 1 箇所に固定するか**: 解決規則（どのファイルのどこから読むか）を消費 skill ごとに書くと、モードを 1 つ足すたびに 4 か所がずれる。**規則は本ファイルに 1 回だけ置き、各 skill は「モードの解決と適用範囲は正典に従う」と書いて自分の節だけを読む。**

## モード一覧

| モード | 対象 | ファイル |
|--------|------|---------|
| `concept` | 新しい概念・ドメインの整理（用語・境界・既存概念との重複を詰める） | `./modes/concept.md` |
| `implement` | 要件が見えている機能の追加・変更 | `./modes/implement.md` |
| `refactor` | 挙動を変えずに構造を変える | `./modes/refactor.md` |
| `bug` | 期待と異なる挙動の原因調査と修正 | `./modes/bug.md` |

## 解決規則

| 消費者 | 読む場所 |
|--------|---------|
| `ask` / `design` | コンテキストファイル（引数、省略時は `./tmp/context.md`）の**先頭の** frontmatter の `mode:` |
| `grill` | 入力ファイルが実装計画ならその `モード:` 行、そうでなければコンテキストファイルの先頭の frontmatter の `mode:` |
| `implement` | 実装計画の `モード:` 行 |

- **実装計画かどうかは形式で判定する**: H1 が `# 実装計画` で始まるファイルを実装計画とみなす。ファイル名（`plan.md` / `plan-xxx.md`）には依らない。fix-plan.md は H1 が異なり `モード:` 行も持たないので、モードなしになる
- **`モード:` 行の位置**: H1 の後、最初の `## ` 見出しより前にある `モード: <値>` の行（間に空行を挟んでよい）。本文の途中にある同じ形の行は読まない。`design` が H1 の直下に転記する（書式は `design/reference/plan-template.md`）
- **frontmatter はファイル先頭のものだけを読む**。本文の途中にある `---` ブロックはモードとして扱わない（追記で frontmatter が重複しても、先頭の宣言だけが効くようにするため）

解決の結果は 3 通り。**宣言がある時**（既知のモード / 未知の値）は、どれになったかを 1 行で報告する（黙ってモードなしに落ちると、宣言したつもりのモードが効いていないことに気づけないため）。**宣言なし**は報告しない — 宣言の無い実行が大半なので毎回の 1 行は雑音になり、各 skill は宣言が無ければ本ファイルを読まないため。例外は `ask` で、回答の「基準」欄に `なし（宣言なし）` と書く（調査結果を後から読む側が、モードの有無を判別できるようにするため）:

| 結果 | 条件 | 報告の書き方 | その後 |
|------|------|-------------|--------|
| **既知のモード** | 値がモード一覧にある | `モード: bug` | `./modes/<mode>.md` の自分の節を読む |
| **宣言なし** | 値が無い | （報告しない。`ask` の基準欄だけ `なし（宣言なし）`） | 現行の動作のまま進める（後方互換） |
| **未知の値** | 値が一覧に無い | `モード: なし（未知の値 foo）` | `./modes/` は読まず、モードなしで進める。止めないのは、モードが観点の追加でしかなく、無くても工程は成立するため |

`design` が plan.md に `モード:` 行を転記するのは **既知のモード** の時だけ。未知の値を転記すると、`implement` で同じ報告が繰り返されるだけになるため。

## 消費者と読む節

| skill | 読む節（`./modes/<mode>.md`） | 使い方 | 採らない候補の理由の残し先 |
|-------|------------------------------|--------|--------------------------|
| `ask` | `## ask の観点` | 既定の型を型判定の初期値にし、優先する観点を調査に加える | 残さない（優先の度合いを変えるだけで、調査の範囲を約束しないため） |
| `grill` | `## grill の観点` | 依存順（上流の決定から）を崩さない範囲で、先に確かめる候補として使う | 残さない（質問の選び方は grill の通常の判断のため） |
| `design` | `## design の観点` | 各項目を実装ステップの分解・アンチゴール・重点セクションに反映し、plan.md に `モード:` 行を転記する | plan.md の「検討した代替案」に 1 行 |
| `implement` | `## implement の観点` | Phase 2 で各ステップの確認事項に加える | 完了報告（Phase 7）の残存課題に 1 行 |

`brief` は `## テンプレート` 節を書き出す生産者で、観点の節は読まない。`fix` / `review` / `revise` / `review-plan` はモードを読まない。

## モードが変えてよい範囲

モードが足すのは **「既定で優先する観点」と「計画に入れる先行ステップの候補」だけ**。次のものは変えない:

- 各工程の必須手順（ask のハルシネーション防止、design の受入条件、implement のレビューサイクル等）
- TDD 規律（`implement/reference/tdd-policy.md`）
- grill の「優先度を固定しない」方針

理由: モードは用途の違いを表すもので、品質基準の緩和ではない。規律を厳しくする方向の追加（例: bug モードで tdd-policy のバグ修正フローの適用対象を広げる）は、この「変えない」に当たらない。観点は候補であって必須ではない。後から「なぜ採らなかったか」が問われる design と implement だけが、採らない理由を上表の残し先に書く。

### `## design の観点` の書式

`design` が各項目の反映先を迷わないよう、次の 3 ラベルで書く（該当が無いラベルも「なし」と書いて残す）:

- **先行ステップの候補**: 実装ステップの先頭に置くステップ
- **重点を置くセクション**: plan.md で特に厚く書くセクション、またはフェーズ 4 のチェックカテゴリ
- **アンチゴールに加える項目**: plan.md のアンチゴールに書く項目

## モードの追加手順

1. `./modes/<mode>.md` を既存ファイルと同じ 6 節（`## 対象` / `## テンプレート` / `## ask の観点` / `## grill の観点` / `## design の観点` / `## implement の観点`）で作る。観点を足さない工程も節は残し、「既定（追加なし）」と書く（`## design の観点` だけは上記の 3 ラベルで書く）
2. 本ファイルのモード一覧に 1 行加え、`brief/SKILL.md` の `argument-hint` に値を足す
3. 消費 skill の本文は変えない

見出しの同一性は次で確かめる。`## テンプレート` 節のコードフェンス内にも `## ` 見出しがあり、モードごとに違うので、フェンスの中を除いて比べる:

```bash
h() { awk '/^```/{f=!f} !f && /^## /' "$1"; }
diff <(h modes/concept.md) <(h modes/<mode>.md)
```
