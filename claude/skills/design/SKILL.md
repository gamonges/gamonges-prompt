要件定義やコンテキスト情報をもとに、実装計画を新規作成する。

**重要**: `./tmp/plan.md` または Cursor の plan モードで作成された実装計画書のみ作成・変更する。他のファイルは変更しない。
**規約**: CLAUDE.md の Skills 共通規約に従う

## 補助ドキュメントへの参照

| 補助ドキュメント | 読むタイミング |
|------------------|----------------|
| `./reference/plan-template.md` | フェーズ 5 で plan.md を出力する時（構成テンプレート本体） |
| `./reference/phase-details.md` | フェーズ 1-4 の調査・確認手順 / 任意セクション該当判定ルール / 記入例を確認する時 / フェーズ 4 で 7 カテゴリチェックを実施する時 |
| `./reference/acceptance-criteria.md` | フェーズ 5 で受入条件（Acceptance Criteria）を記述する時 / Given/When/Then 形式のテンプレを使う時 |

「念のため全部読む」は禁止。表のトリガー条件に該当する場合のみ読み込む。

## パラメーター

`$ARGUMENTS` でコンテキストファイルのパスを指定できる。省略時は `./tmp/context.md` を使用する。

## ワークフロー上の位置付け

| 前工程 | 本コマンド | 後工程 |
|--------|-----------|--------|
| 要件定義・仕様検討 | `/design` 計画作成 | `/revise` 計画修正 → `/implement` 実装 |

## 実行条件

以下のファイルを参照する:

- `$ARGUMENTS`（指定がない場合は `./tmp/context.md`）— 要件・コンテキスト情報
- `./tmp/research.md`（任意）— `/ask` の調査結果
- `./tmp/coupling-precheck.md`（任意）— `/coupling-precheck` の結合バランス整理結果
- `openspec/specs/`（任意）— 既存仕様
- `openspec/config.yaml`（任意）— プロジェクト固有ルール

コンテキストファイルが存在しない場合: プロセスを即座に停止し、ユーザーに報告する。

## 実行プロセス

### フェーズ 1: コンテキスト読み込み

要件を「機能要件」「非機能要件」「制約事項」に分類し、`./tmp/research.md` / `openspec/specs/` / `openspec/config.yaml` を参照する。`./tmp/coupling-precheck.md` が存在する場合はあわせて参照する。詳細は `./reference/phase-details.md`。

### フェーズ 1.5: 既存 plan.md の確認

`./tmp/plan.md` が既に存在する場合、**プロセスを即座に停止**してユーザーに「上書き / 追記 / キャンセル」を確認する。詳細は `./reference/phase-details.md`。

### フェーズ 2: ユーザー確認（必要に応じて）

曖昧な要件 / 矛盾する要件 / 技術的制約が不明 を検出したら停止してユーザーに報告。詳細は `./reference/phase-details.md`。

### フェーズ 3: コードベース調査

調査対象が複数モジュールに渡る・複数の独立した観点を並行調査する場合は、サブエージェントを同一ターンで複数 spawn して並列に調査する。対象が少数の明確なファイルに収まる場合は直接読む。以下の観点を調査する:

- [ ] **既存パターン（検索の使い分け）**: 概念/自然言語検索は、対象の絶対パス（`git rev-parse --show-toplevel`）で claude-context `get_indexing_status` を確認。応答に `✅` を含む（index 済み）なら `search_code(absPath, query)` を優先。`isError`（未 index）/ `🔄`（進行中）は未準備として Serena `search_for_pattern`・grep にフォールバック（claude-context が効くのは index 済みパスのみ。`🔄` は完了後の再実行で使える）。自動 index はせず、**未 index 時のみ** `/context-index` を案内。シンボル精密ナビ・構造把握は Serena（`find_symbol` / `find_referencing_symbols` / `get_symbols_overview`）。新しい比較・正規化・重複判定ロジックを設計する場合は、同種の既存判定関数（`is*Matching`、`normalize*` 等の命名パターン）をプロジェクト全体で grep し、整合・差異を明記する。
- [ ] **影響範囲**: 変更対象ファイル・モジュールの依存関係調査
- [ ] **外部情報**: Web search で外部ドキュメント・事例検索
- [ ] **ライブラリ情報**: Context7 MCP で使用方法確認

### フェーズ 4: 実装計画の策定

- [ ] 要件を実装ステップに分解
- [ ] 各ステップの影響範囲・変更対象ファイルを特定
- [ ] テスト方針を明記
- [ ] **プロジェクト固有規約を参照**（階層的フォールバック、詳細は `./reference/phase-details.md`）
- [ ] 各ステップの依存関係と実行順序を決定
- [ ] **要件カバレッジを検証**
- [ ] **データ生成経路の遡及確認**: 読み取り専用ロジック（判定・集計・表示等）を設計する場合でも、対象データの生成経路（Command Handler・書き込み API 等）を最低 1 段階遡り、値の構造的保証（不変条件・null 許容・重複可能性等）を確認する。確認できない場合は『オープン質問』に追加する（読み取り専用ロジックを含まない設計は該当なし）
- [ ] **コメント方針**: 実装ステップで残すべきコメントを計画する場合は `code-comments` スキルの方針に従う（経緯は書かず、判断・制約を残す）
- [ ] **任意セクションの該当判定**（詳細は `./reference/phase-details.md`）
- [ ] **構造的欠陥防止チェック（7 カテゴリ）**:
  - [ ] **統合点トレース**: skip / 削除 / 短絡提案の副作用を 1 件ずつ列挙
  - [ ] **Decision 間整合性**: Decision を 3 個以上立てたら相互整合性マトリクスを必須化
  - [ ] **並列性マトリクス**: 並列子実行を伴う feature は共有リソース × 並列度を必須記述
  - [ ] **「変更不要」根拠**: 「変更不要」「透過」と書く箇所には grep / read 根拠を併記
  - [ ] **HTTP contract concrete 化**: 抽象 IF を書いたら curl で叩ける具体例を併記
  - [ ] **完了パスツリー**: feature の完了パスを tree で書き出し各葉に AC を割り当て
  - [ ] **対称性チェック**: 並行する分岐・CTE・実装パスが存在する場合、一方への変更がもう一方にも同じ種類の変更を要するかを1行で確認する

  > 詳細テンプレートと BAD/GOOD 例は `./reference/phase-details.md` の「構造的欠陥防止チェックリスト」を参照。軽微な計画 / 該当しない場合は各項目「該当なし」と明記して OK。
- [ ] **確信度評価**（high / medium / low + low には検証ステップを必須記述）

### フェーズ 5: plan.md の出力

`./tmp/plan.md` に構成テンプレート（`./reference/plan-template.md`）へ沿って実装計画を出力する。各セクションの **[必須] / [任意] / [該当時]** 指示に従い、該当しない場合はセクションごと省略する（空セクションを残さない）。

該当判定ルールと記入例（アンチゴール / ファイル変更マップ / ステップ依存関係 / オープン質問 / 確信度サマリ low）は `./reference/phase-details.md` を参照。

> 状態遷移が複雑な場合は、本コマンド完了後に `/state-machine` を実行して状態遷移図を後付けで追加できる。
> 結合バランスの観点で不安が残る設計判断がある場合は、本コマンド完了後に `/coupling-gate` を実行して plan.md の結合バランスを検証できる。

### フェーズ 6: 完了報告

以下の内容をユーザーに報告する:

- 作成した計画の要約（ステップ数、ファイル変更マップの要約）
- 計画策定中に判断した設計上のポイント
- 確信度サマリの medium/low 件数と検証ステップの有無
- 次のステップの案内:
  - `/review-plan` で計画レビュー（推奨、特に medium/low 確信度がある場合）
  - `/revise` で計画修正
  - `/implement` で実装開始
