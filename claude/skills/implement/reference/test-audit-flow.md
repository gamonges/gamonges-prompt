# テスト監査の作用点（implement skill 補助）

判定基準は `../../test-audit/SKILL.md`、出力の書式は同ファイルの「標準出力書式」にあり、ここでは再宣言しない。本ファイルが持つのは、4 か所の作用点それぞれについて「いつ・誰が・何を入力にするか」だけ。

| 作用点 | いつ | 誰が | 出力先 |
|--------|------|------|--------|
| ① 主担当表 | Phase 2 | test-auditor（`owner-table`） | 計画ファイルの `## テスト主担当表` |
| ② 既存テストの判定 | 既存テストが落ちた・変更が要る時（3.2 / 並列実装の結果マージ / 3.5 / Phase 4 / Phase 6） | 本人 | 記録・Phase 7 |
| ③ 1 本ごとの照合 | 3.3 | 本人 | 表の更新履歴 |
| ④ 変更監査 | Phase 6 の開始時 | test-auditor（`change-audit`） | 指摘への対応・Phase 7 |

## 発火条件

作用点ごとに判定する。計画起点の足切り（①）を事象起点の作用点（②・③）に当てない。

- **①**: 計画に、テストを書く・変えるステップがある時。または、振る舞いを変える実装・バグ修正・fix-plan 由来のステップがある時（`tdd-policy.md` がテストを必須とする条件の要約。判定はこの列挙で行い、Phase 2 で tdd-policy を読まなくてよい）。振る舞いを保つリファクタだけの計画や、Markdown だけの変更では発火させない
- **②**: 今回の実行より前からあるテストが落ちた・変更が要る時は、計画の中身に関わらず常に。主担当表の「ケース追加で拡張」に従って既存の table にケースを足すのは、計画どおりの追加で ② に当たらない
- **③**: そのステップで書いた・変えたテストがある時（② で直した・書き直したテストを含む）
- **④**: ① が発火した時、または記録に「新規・書き直し・統合元・削除」の行が 1 件以上ある時。① が発火せず記録が追従修正だけの実行では発火させない（契約が意図どおり変わっただけで、新しい層の重複を生まないため）

## 記録（本人）

④ の監査範囲は、本人のこの記録で決まる。implement はコミットしないので、TDD で作った新規テストファイルは untracked のまま残り、`git diff <commit>` に出ない。書いた本人が記録し、判定役に推定させない。

- 3.5 ごとに、そのステップで書いた・変えたテストを、計画ファイルの `## テスト主担当表` 節の「この実行で書いた・変えたテスト」に追記する。3.5 の外（Phase 4・Phase 6）で書いた・変えたテストは、その直後に追記する
- 記録は計画ファイル単位で持つ。同じ計画の再実行・再開では前の記録を残し、④ の範囲に含める（同じ変更の続きのため）。別の計画で計画ファイルを作り直す時は、節を持ち越さない
- 区分はケース単位で付ける。既存のファイルや table にケースを足した場合も「新規」
- 統合元と削除は、編集の**前に**位置 `file:L` とアサーションの要旨を書き写す（コミットしていない変更は、作業ツリーから消えると `git show` で読めないため）。統合は統合元の 1 行に吸収先の `file:L` を書き、吸収先に足したケースを別の行にしない
- 節がまだ無い時（① が発火しなかった実行で ② が初めて発火した時）は、test-audit の「repo のテスト前提の推定」を本人が当て、「repo のテスト前提」と「この実行で書いた・変えたテスト」だけを持つ節を計画ファイルの末尾に作る
- 計画ファイルは本人だけが書く
  - Medium/Large ステップの並列編集での扱いは `agent-selection.md` の並列実行プロトコル 2. に従う。記録は結果マージの後、3.5 で書く
  - Phase 5.5 の documenter にも `## テスト主担当表` 節を変えさせない

## ① Phase 2 — 主担当表

- 計画ファイルに `## テスト主担当表` の見出しがあり（コードブロックの中の引用は数えない）、契約の表（`C-n` の行）もあれば、呼ばずに引き継ぐ。`/implement` の再実行で節が 2 つになると、3.0 で読み直した時にどちらが最新か決まらないため。ずれは ③ で直す
  - 見出しはあるが契約の表が無い（前の実行が ② だけで作った記録の節）時は呼ぶ。返ってきた「repo のテスト前提」で既存の前提を置き換え（食い違った項目は更新履歴に書く）、その後に契約の表を差し込む。記録は残す
- fix-plan の実行では、fix-plan.md に表を作る（元の plan.md の表は上書きしない）。① には元の plan.md を渡さない。元の表とのずれは ④ の A で突き合わせる
- 呼び出し（foreground で呼び、応答を受けるまで作業ツリーを編集しない）:

  ```
  Agent(
    subagent_type: "test-auditor",
    description: "テスト主担当表の作成",
    prompt: "mode: owner-table\nplan_file: <絶対パス>\nrepo_root: <絶対パス>\n出力: test-audit の『主担当表』書式のみ"
  )
  ```

- 返ってきた表を、計画ファイルの末尾に `## テスト主担当表` として本人が書き込む（判定役は書けない）
- 書式（repo のテスト前提・契約の表）が欠けていたら、欠けた部分を名指しして 1 回だけ再依頼する。それでも欠けていたら未実施として本人の判定に切り替え、Phase 7 の (4) に書く
- 表が、計画の受入条件で名指しされたテストケースを別の層へ移す・落とす場合は、implement の `SKILL.md` 3.5 の「計画にない変更」と同じく計画ファイルに設計判断を一言残し、Phase 7 の (5) にも載せる（受入条件はレビューで合意した契約のため）

## ② 既存テストが落ちた・変更が要る時（本人）

- **開始トリガー**: 今回の実行より前からあるテストが落ちた、または変更が要ると分かった時点。3.2 の ③ Green / ⑤ Refactor、並列実装の結果マージ、3.5、Phase 4、Phase 6 の修正実行のどこで起きても同じ
- **手順**
  1. 一度に複数落ちたら、先に原因（同じ呼び出し形の変更・同じ fixture の変更等）でまとめ、まとまりごとに判定する。1 本ずつ読み直すとコストがかさみ、同じ原因への判定もぶれる
  2. test-audit の Value bar にある「判定の前に読むもの」を読む
  3. 追従修正の**前に**、test-audit の「既存テストの判定」の木を当てる。根元の環境依存の分岐（単独実行・順序を変えた再実行）を最初に当てる
  4. 葉ごとに次へ進む

| 葉 | 次の行動 | 記録 |
|----|----------|------|
| 環境・順序依存 | 依存の原因（実行順・時刻・共有状態等）を直す。直せなければ理由を Phase 7 の残存課題に書く。統合・削除の判定に入れない | — |
| 追従修正 | 直した後のテストに ③ の照合を当てる | 追従修正 |
| 本体を直す | テストを残し、本体の回帰を直す（Retention bar） | — |
| 書き直す | owner の境界で振る舞いを検証する形に書き直し、`tdd-policy.md` の TDD サイクル ④ Mutation で落ちることを確かめる | 書き直し |
| 統合する | 編集前の要旨を記録してから、吸収先へケースを移す。移転は作用点 ④ の C ブロックで独立に確かめる | 統合元 → 吸収先・Phase 7 (2) |
| 削除候補 | 下記の承認を経る | 削除・Phase 7 (2) |

- **削除候補のユーザー承認**
  - test-audit の「削除の根拠 7 項目」を本文に並べ、AskUserQuestion で承認を取る。候補が複数あれば multiSelect で候補ごとに採否を選べるようにする（1 問の選択肢は 4 つまでなので、5 件以上は 4 件ずつ問いを分ける。1 件だけ残る問いは「削除する / 残す」の 2 択にする）
  - 承認 → 編集前の要旨を記録 → 削除（外せる seam も同じ変更で外す）
  - 不承認 → 「残す」に戻し、書き直すか追従修正するかを改めて判定する
- 統合・削除の後は、repo 前提の「CI で実行する閾値・検査」のうちローカルで実行できるものを変更ファイルに対して実行する（統合元を消すとカバレッジや未使用 export の検出が変わりうるため）
- 統合・削除で計画の受入条件（「既存テストを維持する」等）から外れる時は、implement の `SKILL.md` 3.5 の「計画にない変更」と同じく計画ファイルに設計判断を一言残す

## ③ 3.3 — 1 本ごとの照合（本人）

- **対象**: そのステップで書いた・変えたテストケース（it / test ブロック単位。② で直した・書き直したものを含む）。同じファイルの触っていないテストは対象にしない（既存テストの掃除を目的にしない）
- **照合**: test-audit の gate 4 問 / junk patterns / 検証できない境界での書き方 / 主担当表との一致（表がある実行のみ）
  - gate は 3.3 で当てる。TDD サイクル ① には段を足さない（層とファイルは主担当表で先に決まっている）
- 表と実際のテストがずれていたら、表を更新し、更新履歴に理由を書く
- 表の更新だけの扱いは `review-cycle.md` の「発動条件の判定」に従う（修正発生に数えない）
- 表が無い実行では出力先は無い。照合で見つかった問題は `review-cycle.md` の「修正発生あり」として直す
- 今回の実行より前からあるテスト（② で直したもの）が gate を通らない時は、直接消さずに ② の判定木に戻す。戻す時は根と 2 番目の分岐（契約を意図どおり変えた）を当てず、「振る舞いを保つ変更のはず」の下の「アサーションが実装を見ている」から当てる（追従修正を当て直すと同じ所を回り続けるため）

## ④ Phase 6 — 変更監査

- **開始トリガー**: Phase 6 の全体レビューの前（発火条件を満たす場合）。その時点で満たさなくても、Phase 6 の全体レビューでテストを書いた・変えたことで満たしたら、その時点で行う
- **入力**
  - 計画ファイル（範囲は `## テスト主担当表` 節の「この実行で書いた・変えたテスト」の行）
  - `repo_root`: `git rev-parse --show-toplevel`
  - `base`: `git merge-base HEAD $(git symbolic-ref --short refs/remotes/origin/HEAD)` の SHA。解決できなければ比較の起点をユーザーに確認する
  - `ref_plan_files`（fix-plan の実行時のみ）: 元の plan.md。判定役は読み取り専用で使い、A でその表とも突き合わせ、記録漏れの判定ではその記録を除外する
- **呼び出し**（① と同じく foreground で呼び、応答を受けるまで作業ツリーを編集しない）:

  ```
  Agent(
    subagent_type: "test-auditor",
    description: "テスト変更監査",
    prompt: "mode: change-audit\nplan_file: <絶対パス>\nrepo_root: <絶対パス>\nbase: <merge-base の SHA>\nref_plan_files: <元の plan.md の絶対パス>\n出力: test-audit の『変更監査』書式のみ（A–E。表が無い実行では A を「表なし」と書いて省略）"
  )
  ```

  - `ref_plan_files:` の行は fix-plan の実行でなければ行ごと外す
  - 再監査では `focus: <変えたテストの file:L の列挙>` の行を足す（範囲の行のうち、判定役が見るものを絞る）

- 指摘への対応は本人が行う。指摘を採らない時は、理由を Phase 7 の (3) に残す（独立判定の意味は確証バイアスを外すことにあり、黙って退けるとその意味が消える）
- **反復トリガー**: 指摘に対応してテストを統合・削除・書き直した時、または Phase 6 の全体レビューでテストを書いた・変えた時。変えたテストを記録してから、範囲をそのテストに絞って再監査する
- **完了条件**: 指摘（test-audit の「変更監査」の定義）がゼロになる。または残る指摘がすべて、理由つきで「採らない」と記録されている
- **打ち切り**: `review-cycle.md` 冒頭の値に従う（初回の監査を 1 巡目と数える。値はここでは再宣言しない）
- 書式のブロック（A–E の見出し）が欠けていたら、欠けたブロックを名指しして 1 回だけ再依頼する。それでも欠けていたら未実施として扱い、Phase 7 の (4) に書く

## test-auditor が見つからない・判定基準が読み込まれていない時

- `Agent type 'test-auditor' not found` を受けたら、他の agent type で代替しない。`general-purpose` 等で呼び直すと Edit / Write を持つ判定役になり、判定と修正が黙って混ざる
- ① と ④ を本人の判定に切り替え、Phase 7 の (4) に「独立監査は未実施（test-auditor 不在）」と書く。本人の判定も同じ書式（主担当表 / 変更監査の A–E）で書き、① の表は計画ファイルに書き込む（④ の発火条件「① が発火した時」はこの場合も満たす）
- skill の配布元（`setup.sh` のあるリポジトリ）のメインチェックアウトで `./setup.sh install` を実行し、その後に新しいセッションを開始するよう案内する（`~/.claude/agents/` を初めて作った install は、再起動しないと読み込まれない）
- 判定役が「test-audit の判定基準が読み込まれていない」と返した時は、再依頼しない（書式の欠けとは違い、再依頼では直らない）。同じく本人の判定に切り替え、Phase 7 の (4) に「独立監査は未実施（判定基準の preload 不在）」と書く。`settings.json` の `skillOverrides` で `test-audit` を `off` / `user-invocable-only` にしていないか、`./setup.sh status` で skill が配置されているかを確かめるよう案内する

## Phase 7 に足す項目

件数ではなく、記録と対応の依頼として書く。該当が無い項目は「なし」と書く。

1. **repo 規約が必須とするが、gate は不要と判定したテスト**（②・③ のどちらで判定したものも）: テスト名・規約の出典 `file:L`・gate の判定理由
2. **`test:` コミットに分ける変更**: ファイル・テスト名・判定（統合 → 吸収先 / 削除 → 残る証明）・外した seam。提案するコミットメッセージには設計判断を 1 行含める。本体への追従と同じファイルで混ざる場合は、非対話で分ける手順を添える（統合・削除の hunk だけを含む patch を `git diff` から作り、`git apply --cached` でステージする）。ユーザーが手でコミットする場合は `git add -p` も使える
3. **採らなかった監査の指摘と理由**
4. **独立監査を実施したか**（未実施ならその理由。発火条件に当たらなかった / test-auditor が不在 / 判定基準が読み込まれていない、を区別する）
5. **受入条件で名指しされたテストのうち、主担当表が別の層へ移した・落としたもの**: テスト名・移した先・理由
