## 実装計画ファイル

引数 `$ARGUMENTS` で指定したファイルを参照する。

**条件付きで読む**:

## 実行プロセス

### Phase 1: 実装計画の読込

- 実装計画ファイルを読み込み、すべてのコンテキストと要件を理解する
- **モード**: 正典（`../brief/reference/modes.md`）の解決規則で実装計画の `モード:` 行を読む。行があれば解決の結果を 1 行報告する（fix-plan.md は行を持たないので、モードなし）
- 必要に応じて Web 検索とコードベース探索を追加で行う
- セマンティックなコード検索には Serena MCP、ライブラリ・フレームワークの使用方法には Context7 MCP を使用する
- **業務シナリオの有無を確認する**（状態の定義と発火判定の基準は `../grill/reference/business-scenario.md` が正典）。まず足切りを当て、**次のいずれかに該当すれば本検査を発火させない**:
  - 実装計画の**変更対象ファイル一覧**に、ユーザー経路から到達できる機能のコードが含まれない（ドキュメント・設定・テストのみ、プロンプト集・ツール定義のみ 等）
  - 対象リポジトリが `openspec/specs/` を持たない

  **変更対象ファイル一覧が読み取れない計画（自由形式等）では、足切りを適用せず検査を発火させる。** 条件が評価できないときに素通しすると、判定を飛ばしたことが検知されない状態に戻る。

  足切りを通過した場合、`./tmp/scenario.md` が**不在**なら正典の判定 1・2 をその場で当て、いずれかが Yes なら `S-n` を、いずれも No なら `## 判定: シナリオ不要` を書いて閉じる。判定に必要な材料（触る属性・列の列挙）が揃わない場合は**実装に入らず停止**し、`/grill` Phase 0 を案内する。
  **`S-n` を立てた場合、Notion 反映は `/design` フェーズ 1.6 でのみ行われる** — `/design` を経ない経路では反映先 URL と反映日が未記入のまま Phase 4 に到達し、2 欄検査で理由つきの明示が求められる。
  **足切りを判定より前に置くのは**、日常的に発火する確認が「中身を読まずに承認する習慣」を育て、素通しとは別方向で検査を無効化するため。

### Phase 2: 設計と計画

- すべての要件に対応する包括的な計画を作成する
- 複雑なタスクを小さく管理可能なフェーズに分解し、TodoWrite tool で実装計画を作成・追跡する
- 既存コードから従うべき実装パターンを特定する
- TDD で書くべきテストの種類（単体/統合）と失敗パターンをプラン内で明示する
- 既知のモードに解決した場合、`## implement の観点` を各ステップの確認事項に加える。TDD 規律（`./reference/tdd-policy.md`）への追加であって、置き換えではない。採らない観点は Phase 7 の完了報告の残存課題に理由を 1 行書く
- **各ステップにレビューサイクル（修正が出なくなるまで反復）を組み込んだ計画を立てる**
- plan.md の各ステップに `- [ ]` チェックボックスがない場合は付与する

### Phase 2.5: エージェント選択

プロジェクトタイプと変更内容に基づき、専門エージェントを決定する。詳細は `./reference/agent-selection.md` を参照。

### Phase 3: 実装の実行（ステップごとにレビューサイクル適用）

各ステップで以下のサイクルを実行する。

#### 3.0 コンテキスト再読込

ステップ開始時に以下を再読込し、コンテキストドリフトを防止する:
1. **CLAUDE.md**: プロジェクト規約の最新状態
2. **実装計画ファイル**: 現在のステップの詳細と前後の依存関係
3. **関連仕様ファイル**: openspec/specs/ 配下の該当仕様（存在する場合）
4. **前ステップの出力**: 直前ステップのレビュー結果や修正内容

#### 3.1 ステップ実装

- 実装計画のステップを実行する
- セマンティックなコード検索には Serena MCP を使用する
- 実装は使用モデルに依存しない汎用的な記法で行う

**Small ステップ（変更ファイル < 3）**: メインエージェントが直接 TDD サイクルを実行する（3.2 に進む）。

**Medium/Large ステップ（変更ファイル >= 3）**: `./reference/agent-selection.md` の並列実行プロトコルと結果マージプロトコルに従う。

> **並列編集の指針**: Medium/Large ステップで**独立した編集が複数ある場合**は、同一ターンで複数の Agent 呼出を発行して並列実行する（直列に 1 つずつ呼ばない）。例: 「3 件の独立した編集が必要 → 1 メッセージ内で 3 つの Agent 呼出を並列発行」。逆に、単一ファイルで完結する作業や相互依存のある編集は subagent を使わず直接実行する。Claude 5 世代はデフォルトで subagent を控えめに spawn するため、並列が有効な箇所では上記のように明示する（この並列編集は本ワークフローの本質的価値であり維持する）。

#### 3.2 TDD サイクル

新規テストを書く場合は `./reference/tdd-policy.md` の TDD サイクル詳細（① Red → ② Red 確認 → ③ Green → ④ Mutation → ⑤ Refactor）に従う。

バグ修正ステップの場合は `./reference/tdd-policy.md` の「バグ修正時のリグレッションテスト必須化」フローに従う。

#### 3.3 レビューサイクル

`./reference/review-cycle.md` のレビュー観点チェックリストと手順に従う。開始トリガー / 反復トリガー / 完了条件 / 打ち切りは同ファイルの冒頭に定義があり、ここでは再宣言しない（3 巡の値を変えるとき直す箇所を 1 つに保つため）。

#### 3.5 ステップ完了確認

- テストがすべて通ることを確認
- TodoWrite で該当ステップを completed にマーク
- plan.md 内の該当ステップ `- [ ]` を `- [x]` に更新
- 計画にない変更を追加した場合（typo 修正・lint 対応・変数名の微修正等、スコープ追加を伴わない軽微な付随修正は対象外）: (a) 別 PR に分離する、または (b) 追加する場合は plan.md かコミットメッセージに一言設計判断を残す
- 次のステップへ進む

### Phase 4: 最終検証

- format、lint を **変更対象ファイルのみ** に実行（L-1: プロジェクト全体への実行は禁止）
- test を実行し、すべての失敗を修正する
- typecheck は自動実行しない（L-2）。ユーザーに手動実行を促すか CI に委ねる
- ドメイン層・複雑ロジックの追加箇所は新規テストが緑になることを確認し、必要に応じて回帰テストも走らせる
- plan.md の確信度サマリまたはステップ詳細で実機検証（staging 環境実行・EXPLAIN・実データ抽出等）が明記されている場合、`/review` に出す前に本ステップで実施する
- **変更した capability に `openspec/specs/<capability>/verification.md` が存在する場合、`verify-scenario` skill で実行する**（openspec を持たないリポジトリ、および verification.md を持たない変更では発火させない — 無条件に走らせると Phase 4 の所要時間が理由なく伸びる）
- 実行後に `draft:` が残る Driving 行がある場合、Phase 7 の完了報告で**未検証として件数を明示する**（未実行の行は成果物ではないため、「検証済み」と書かない）
- **業務シナリオの DoD を検査する**: `./tmp/scenario.md` を読み、3 状態で分岐する（状態の定義・項目名・**どの状態かの評価順**は `../grill/reference/business-scenario.md` が正典。以下の並びは状態ごとの手順であって評価順ではない）
  - **シナリオ不要**（`## 判定: シナリオ不要`）→ 検査をスキップする
  - **S-n あり** → 各 `S-n` の「Notion 反映」「確認の決着」の **2 欄とも**埋まっていることを検査する（項目名は正典の「完了の記録欄」）
    - 「確認の決着」が空 → 完了とせず、開発者に判断を促す。未回答のままでも**開発者判断でクローズできる** — 判断者 / 日付 / 理由を `./tmp/scenario.md` に書けば進む（PdM / QA の返信を必須にすると、確認が要らない変更でも実装が止まる）
    - 「Notion 反映」が空 → 反映先 URL が `未定` であることが理由か否かを開発者に確認し、未記入のまま進める場合は **Phase 7 の完了報告に理由つきで明示する**
  - **不在** → Phase 1 の確認を通っていれば、ここで不在にはならない。それでも不在の場合は**実装中に失われた**ことを意味するため、完了とせず開発者へ報告する（`tmp/` はコミットされず容易に失われる）
  - **この検査が保証する範囲**: 正典の「塞がらない範囲」と「この欄が保証する範囲」を参照する（`../grill/reference/business-scenario.md`）
- 受入基準が満たされていることを確認する

### Phase 5: コメントの整理

実装コード内のコメントを `code-comments` スキルの方針に従って整理する（方針の SSOT は `code-comments`。ここでは再宣言しない）。

- **残すコメント**: `code-comments` の「残すべき 7 分類」「判定ヒューリスティック」に照らし、コードから読み取れない情報（why / 不変条件 / 危険 / 意図 / 根拠）を持つものを残す
- **削除するコメント**: `code-comments` の「アンチパターン」に該当するもの（冗長な言い換え / レビュー対応の経緯 / コメントアウトされた旧コード）を削除する
- **レビュー指摘への対応**: 経緯をそのまま書かず、`code-comments` の「蒸留」に従いコードから読めない制約・理由に変換する（蒸留結果がコードで表現できるならコメントではなくコードを直す）

### Phase 5.5: ドキュメント同期

Phase 6 の全体レビュー前に、documenter エージェントを起動してドキュメントとコードの整合性を検証する。

1. documenter エージェントが全ステップの変更をまとめて検証
2. plan.md / openspec/specs/ との差分を検出 → 必要なら更新
3. レビューサイクルで発見された問題パターンを auto-memory に `type: feedback` として記録
4. 知識の圧縮（既存の記憶に該当があれば新規作成せず更新する）

UI 変更がある場合は Phase 6.1 のチェック項目に「WCAG 2.1 AA 準拠」「デザインシステム整合性」を追加。
パフォーマンス最適化が該当する場合は Phase 6.1 に「N+1 クエリ」「不要な再レンダリング」を追加。

### Phase 6: 全体レビューサイクル

実装全体に対して **レビュー → 修正** を、修正が出なくなるまで反復する（3.3 と同じ停止条件）。修正ゼロなら 1 巡で完了。**上限と到達時の扱いは `./reference/review-cycle.md` 冒頭の打ち切り条件に従う**（値を再宣言しないのは、変えるときに直す箇所を 1 つに保つため。L76 と同じ理由）。

**レビュー観点**: 全体俯瞰 / ステップ間整合性 / アーキテクチャ / パフォーマンス（N+1、不要な再レンダリング） / セキュリティ / UI 変更時は WCAG 2.1 AA + デザインシステム / ドキュメント (TSDoc) 整合性

**修正実行**: 発見した問題を修正 → 必要ならリファクタ → テスト再実行 → lint/format を **変更対象ファイルのみ** に実行（L-1）→ typecheck はユーザーに手動実行を促す（L-2）。レビューで計画にない変更（スコープ追加）が生じた場合は 3.5 と同じ基準に従う（typo 修正・lint 対応等の軽微な付随修正は対象外。(a) 別 PR に分離する、または (b) 追加する場合は plan.md かコミットメッセージに一言設計判断を残す）

### Phase 7: 完了報告

- すべてのチェックリスト項目が完了したことを確認する
- 実装計画を再度読み、すべてを実装したことを確認する
- レビューサイクルの実施記録を含めて完了ステータスを報告する

**tmp/ クリーンアップ:**
- `./tmp/step-*` ファイルを削除する（一時的なエージェント出力）
- `./tmp/plan.md` は保持する

**報告フォーマット**: 以下の項目を含む `## 実装完了報告` を出力する:

- 実装サマリー（ステップ数、レビューサイクル回数）
- エージェント実行サマリー（使用した専門エージェント、並列実行回数）
- TDD チェックポイント実施記録（ユーザー確認回数、再作成回数）
- 品質確認結果（lint / format / typecheck / test の各チェックリスト）
- レビューで発見・修正した主な問題
- verification.md の実行結果（該当時）: 実行した Driving 行数と、`draft:` が残る未検証行の件数
- 業務シナリオの DoD（該当時）: 未回答のまま開発者判断でクローズした `S-n` の件数とその理由、および **「Notion 反映」が未記入のまま進めた `S-n` の件数とその理由**（`draft:` 残件と同じ扱いで、閉じ方を報告に残す）
- 残存課題（あれば）
