## 原則

- 確度を優先し、削除の件数を目標にしない。迷ったら残す側（削除しない・統合しない）に倒す。残すべきでないことを示してから消す
- TDD 規律は弱めない。効かせるのは「どの契約を、どの層に 1 つ置くか」だけ
- repo の規約が必須とするテストは書く。gate は形（層・アサーション・重複）だけに効かせる

用語:

- **契約** = テストが守る観測可能な振る舞い・不変条件・独立した取り決め
- **主担当（owner）** = その契約を最も強い境界で検証する 1 つのテスト。**最も強い境界** = 契約を実装している入口のうち、契約が依存する実物（DB・外部 I/O 等）をモックせずに通せるもの。依存する実物が無い計算なら、その関数の単体
- **層** = テストが対象を呼び出す入口（関数・usecase・QueryService・HTTP 等）と、その下で実物を通す範囲の組。どちらかが違えば別の層（例: 同じ usecase をモックで呼ぶ単体と実 DB で呼ぶテスト / 同じ DB を使うテストでも usecase と QueryService）
- **seam** = 本番の呼び出し元が必要としない export・フラグ・ラッパー・注入口

## repo のテスト前提の推定

判定の前に、対象 repo から次を推定する。repo 固有の前提はここでしか得ない（本スキルに repo 固有の名前は書かない）。

- **読むもの**: `CLAUDE.md` / `AGENTS.md`（repo 直下と対象範囲）/ `.claude/rules/` / `.cursor/rules/` / CI の設定（`.github/workflows/` 等）/ テストランナーの設定 / `package.json` の scripts
- **得るもの**
  - テスト種別と配置の規約（種別ごとの置き場所・命名）
  - CI で実行されるテストと、実行されないテスト
  - 規約が必須とするテスト
  - CI で実行する閾値・検査（カバレッジ閾値・未使用 export の検出・型検査の有無）と、それぞれが失敗でマージを止めるか
- 各項目に `file:L` の根拠を付け、推測で埋めない
- 検索して見つからなかった項目は「なし」と書き、検索したコマンドと範囲を根拠にする（CI が実行しない等、「無い」ことを根拠にする時も同じ）。「不明」は、検索できなかった時と、判断に repo の外の情報（ブランチ保護の設定等）が要る時だけ使う
- 規約は文言どおりに読む。種別（単体 / 統合等）を指定していなければ種別を補わない。「新規の X」の新規は、計画が新しく作るもの（変更監査では base に無いもの）
- 「CI で実行する」かは CI の設定から判定する。「止める」かは別に書く: 実行するが止めないもの（`continue-on-error` 等）は「非ブロッキング」、ブランチ保護など repo の外の設定で決まるものは「止めるかは不明」。補足や呼び出し側の手順が見るのは「CI で実行する」のほう
- 「規約が必須とするテスト」が「不明」の時は、既存テストを統合・削除の葉に進めない

## Authoring gate

テストを足す前に 4 問に答える。答えられない問いがあれば、まだ足さない。

1. どの観測可能な振る舞い・不変条件・独立した契約を守るか
2. どんな現実的な回帰で落ちるか
3. なぜ既存のカバレッジでは捕まらないか
   - 契約 1 つに主担当 1 つ。主担当は最も強い境界に置く
   - 別の層にもテストを置くなら、その層に固有のリスク（通信・ライフサイクル等、主担当が届かない失敗）が要る
   - 似たテストを足すより、table-driven のケースや共有 fixture を拡張する。重複した準備は同じ変更でまとめる
4. 本番の呼び出し元が必要としない seam を要するか。要するなら、テストを本物の境界へ移す

repo 前提による補足（推定が「不明」の項目では適用しない）:

- CI で実行されないと分かっている種別のテストは、Q2 の回帰を捕まえない。そのテストだけを主担当にしない
- 型検査を CI で実行する repo では、型検査が捕まえる回帰（型の不一致・存在しないプロパティの参照等）は、Q3 の「既存のカバレッジで捕まる」に当たる。型検査を CI で実行しない、または不明な repo では適用しない（呼び出し側がローカルで型検査を実行するとは限らず、誰も捕まえない回帰になる）

続けて、すべての [junk patterns](#junk-patterns) と照合する。当たれば gate を通さない。ただし [Retention bar](#retention-bar) が、そのテストが独立に守る契約を名指しできる時は通す。

振る舞いを保つリファクタで壊れる形のテストは、振る舞いではなく実装を検証している。入れる前に owner の境界で書き直す。

**バグの回帰テスト**

- 修正前のコードで、意図した理由で落ちることを示す。落ちたことを示せない回帰テストは、修正ではなくモックを証明している
- owner の境界の修正後に通る
- owner の境界に 1 つ置けば足りる。同じシナリオを、通過する全層で再現しない

## Junk patterns

gate は新規テストがこれに当たれば拒否し、変更監査は範囲の行のテストでこれに当たるものを探す。

**何も守っていない**

- アサーションの無いカバレッジ稼ぎ
- 自己比較・受け取った値をそのまま返すだけのコピー
- fixture・一覧・manifest・export リストの書き写し
- ソース・import・文字列の完全一致 grep
- テスト専用の export・global・ラッパーを保つためだけのテスト
- 呼び出し元がテストだけの本番コード（dead code）。計画が段階導入（本番の呼び出し元を後続で接続する）を明示しているものは数えない

**証明が重複している**

- 本物の境界で検証済みの契約を、private な述語や呼び出し形で検証し直すテスト
- 同じ契約の重複呼び出し
- 共有ヘルパーの振る舞いを、利用側ごとに検証し直すテスト

**偽の証明**

- 期待値をテスト対象のヘルパー・レンダラー・列挙で作っている
- 検証する振る舞いをモック自身が実装している。または 1 つの同じモックが異なる API の代役をしている
- owner が作るべき受領・受理・コールバックの順序を fixture が供給している。または、その経路が書き込まないストアに対して永続化を検証している
- 宣言されたフラグを言い直すだけで、フラグが約束する配送・応答を実行しない機能テスト
- 無関係な理由で通る negative（別のガードによる拒否・本番の経路が到達しない拒否）
- 名前や fixture が入力以上を約束している（例: 「期限切れを除外する」という名前なのに、期限切れの入力を 1 件も与えていない）

## 検証できない境界での書き方

テスト環境が本物の境界を検証できない時（DOM の無い実行環境等）:

- 判断を、本番でも意味のある純関数・props に出して検証する
- ソースの文字列 grep や、フレームワーク内部のモック（例: `vi.mock('react')` で `useState` を差し替える）による回避は junk として拒否する
- テストのためだけの分割は、gate の Q4（seam）で拒否する

## Value bar

- 振る舞いを保つ変更のために変えなければならない既存テストは疑わしい。ただし自動的に削除してよいわけではない（新規なら gate が拒否する）
- 判定の前に読むもの: テスト全体と本番の owner、その入口・呼び出し元・呼び出し先・兄弟実装、重なるテスト、CI での扱い、関連する経緯。repo 直下と対象範囲の `AGENTS.md` / `CLAUDE.md` を先に読む。依存ライブラリの振る舞いを主張するテストは、依存のソースか型を直接読む

## Retention bar

公開 API・プロトコル・設定・マイグレーション・ストレージ・セキュリティ・既定値・アーキテクチャの契約を独立して守るテストは残す。次も残す:

- 順序が観測可能な振る舞いである時の、呼び出し順の検証
- 現実的な失敗モードを持つ回帰テスト
- 最も安い独立のガードになっているソース検査（契約＝利用者に見えるキー・バイト列・パスが変わると落ち、識別子だけのリファクタでは落ちないもの）
- baseline で落ちる、残すと判定したテスト: 本体のバグの可能性として扱い、再現して owner を直す。テストは消さない

遅い・静的であることは削除の理由にならない。実装に似て見えるテストでも、独立した契約でありうる。そうでないと示してから消す。

## 既存テストの判定

既存テストが落ちた・変更が要る時に当てる。判定はテスト名ではなくアサーションで行う。

```
既存テストが落ちた / 変更が要る
├─ （落ちた時のみ）単独実行・順序を変えた再実行では落ちない
│   └─ 環境・順序依存の偽陰性（統合・削除の判定に入れない）
├─ 今回の変更が、このテストの守る契約を意図どおり変えた
│   └─ 追従修正
└─ 振る舞いを保つ変更のはず
    ├─ アサーションが観測可能な振る舞いを見ている
    │   └─ 本体を直す（Retention bar）
    └─ アサーションが実装（呼び出し形・mock の配線・内部表現）を見ている
        ├─ repo 規約が必須とするテスト → 書き直す（統合・削除に進めない）
        ├─ owner の境界に他の証明が無い → 書き直す
        ├─ 他に証明があり、このテストにしか無いケースがある → 統合する
        └─ 他に証明があり、固有のケースも無い → 削除候補
```

| 葉 | そう判定するための読解の根拠 |
|----|------------------------------|
| 環境・順序依存 | 落ちたテストが、単独実行と順序を変えた再実行の両方で通ったこと（落ちていない「変更が要る」テストには当てない） |
| 追従修正 | 計画・仕様がこの契約の変更を名指ししており、新しい期待値がその変更と一致すること。計画が名指しした呼び出し側の契約（公開 API の名前・引数等）の変更に、アサーションを変えずに呼び出しの形だけを合わせる場合を含む |
| 本体を直す | 落ちたアサーションが、公開の出力・永続化された状態・外部への副作用を見ていること |
| 書き直す | アサーションが実装を見ており、owner の境界にこの契約の他の証明が無いこと（または規約が必須とすること）。書き直し先はその境界で振る舞いを検証する形 |
| 統合する | 吸収先（`file:L`）が同じ契約を owner の境界で検証しており、このテストにしか無い入力・期待値（吸収先では区別できない回帰を含む）を列挙できること |
| 削除候補 | 同じ契約のすべての入力・期待値について、それを検証している吸収先の `file:L` を示せること（吸収先は複数に分かれてもよい。1 つでも示せなければ統合する）。示す吸収先は、このテストが捕まえる回帰で落ちる入力を持つこと（吸収先の入力では正しい実装と回帰した実装が同じ結果になるなら、その入力・期待値は移っていない）。[削除の根拠 7 項目](#削除の根拠-7-項目)を揃えられること |

- repo 規約が必須とするテストは、gate が不要と判定しても統合・削除の葉に進めない。gate の判定は呼び出し側に返す
- 根拠を揃えられない時は、1 つ上の残す側の葉（削除候補 → 統合する → 書き直す）に倒す

## 削除の根拠 7 項目

既存テスト（今回の実行より前からあるテスト。この実行で直した・書き直したものを含む）を削除する前に、すべてを記録する。1 つでも欠けたら削除しない。この実行で作ったケース（記録の区分「新規」）を取り下げる時は 7 項目の記録は要らないが、取り下げてよいかは「削除候補」の葉と同じ条件（入力・期待値ごとの吸収先と、その入力が回帰を区別できること）で判定する。

1. テスト名と位置（`file:L`）
2. 実際に検出できる失敗
3. 対象の本番コード・テスト支援コードの、テスト以外の呼び出し元
4. owner の境界に残る、より強い証明の場所（または証明が要らない理由）
5. 経緯と、そのテスト・seam が存在する理由
6. 削除で外せる本番コード・テスト支援コード
7. リスクと、確かめる検証コマンド

6 に挙げた seam は、テストの削除と同じ変更で外す（エイリアスを残さない）。外す前に、テスト以外の参照が無いことを `rg` の結果（`file:L`）で 3 に残す。

## 標準出力書式

2 つの書式は `test-auditor` と `implement` が共有する。

### 主担当表

`owner-table` モードの出力。呼び出し側が計画ファイルの `## テスト主担当表` 節に書き込む。「この実行で書いた・変えたテスト」は判定役ではなく呼び出し側が記録する（判定役は見出しと表ヘッダだけを返す）。契約の表を持たず、「repo のテスト前提」と「この実行で書いた・変えたテスト」だけを持つ節もありうる。

```markdown
## テスト主担当表

repo のテスト前提:
- テスト種別と配置: <種別 = 置き場所・命名> — 根拠: <file:L>
- CI で実行される / されない: <…> — 根拠: <file:L>
- 規約が必須とするテスト: <…> — 根拠: <file:L>
- CI で実行する閾値・検査: <… / なし>（型検査の有無を含む。それぞれ ブロッキング / 非ブロッキング / 止めるかは不明） — 根拠: <file:L>

| # | 契約（守る振る舞い・不変条件） | 捕まえる回帰 | 主担当（層 / ファイル） | 既存の証明 | 他層のテストと固有リスク | 規約上の必須 | ステップ |
|---|---|---|---|---|---|---|---|
| C-1 | ... | ... | ... | なし / 一部: <file:L>（証明していない部分） / <file:L>（ケース追加で拡張） | なし / <層>: <固有リスク> | — / <規約 file:L> | N |

更新履歴: <更新した行と理由>

### この実行で書いた・変えたテスト
| ステップ | 区分（新規 / 追従修正 / 書き直し / 統合元 → 吸収先 / 削除） | テスト（file:L・ケース名） | 編集前の位置とアサーションの要旨（統合元・削除のみ） |
|---|---|---|---|
```

- 契約ごとに Q1–Q3 を当て、主担当を 1 つに絞る。他層のテストを残す行には固有リスクを書く。固有リスクが無ければ、主担当の 1 層に寄せる
- 計画が、本番の呼び出し元の無い本番コード（テスト用の DI・export 等）を足すステップには Q4 を当て、「（観測可能な契約なし）」の行として主担当を置かずに書く
- 規約が必須とするテストは「規約上の必須」列に出典を書き、主担当とは別に残す

### 変更監査

`change-audit` モードの出力。監査の対象は「この実行で書いた・変えたテスト」の行に限る。**指摘** = A の「ずれ / 主担当なし」の行、B の行（推奨が「規約必須のため残す」または固有リスクがあって残すものを除く）、C の「一部欠落 / 移っていない」の行、D・E の行（A の「一致」、B の残す行、C の「移っている」は確認の結果で、指摘に数えない）。各指摘には、ブロックが持つ列に従って severity（high / medium / low）と confidence（high / medium / low）を付け、確度に関わらず全件出す。

```markdown
### A. 主担当表との突き合わせ
| 契約 | 表の主担当 | 実際のテスト（file:L） | 判定（一致 / ずれ / 主担当なし） | 根拠 | severity | confidence |
### B. 層の重複
| # | 契約 | テストの組（file:L × file:L） | 他層の固有リスク（無し / 内容） | 規約上の必須（— / 規約 file:L） | 推奨（主担当に残す側・統合先 / 規約必須のため残す） | severity | confidence |
### C. 統合の移転確認（読解による。保全ミューテーションはしない）
| # | 統合元 | 元のアサーション | 吸収先（file:L） | 判定（移っている / 一部欠落 / 移っていない） | confidence |
### D. 唯一の証明を失った契約
| # | 契約 | 失わせた変更 | 戻し方の提案 | severity |
### E. その他（1 本ごとの junk・seam の取りこぼし・記録漏れ）
| # | テスト（file:L） | 該当パターン | 推奨 | severity | confidence |
```

- A: 主担当表が無い実行では「表なし」と書いて省略する
- B: 別の層どうしの重複を書く（同じ層の重複は E の「証明が重複している」）。組の相手は範囲外のテストでもよく、推奨は範囲内の側について書く。「規約上の必須」の行は統合・削除を推奨せず、「規約必須のため残す」とする
- C: 移っているかは、吸収先の入力で統合元が捕まえていた回帰を区別できるかで判定する（「削除候補」の葉と同じ条件）
- E: 範囲の行への 1 本ごとの gate（バグの回帰テストを含む）と junk、seam の取りこぼし、記録漏れ、記録の不一致（区分・位置）、前提の訂正（計画ファイルの repo 前提と食い違う根拠・「不明」を埋める根拠）を書く。根拠の `file:L` は「該当パターン」列に書く。同じパターンの複数ケースは 1 行にまとめてよい（`file:L` を列挙する）。範囲の行で指摘が無いものは、表の下に「指摘なし: <テスト>（理由）」を 1 行ずつ書く
- 同じテストが B と E の両方に当たれば、両方に載せる
- 推奨の語彙は、記録の区分で分ける
  - 区分「新規」（この実行で作ったケース）: 「取り下げる（主担当 `file:L` がある）/ 主担当へ移してから取り下げる（このテストにしか無い入力・期待値がある）/ 書き直す / ケースを拡張する / 残す」。取り下げの条件は[削除の根拠 7 項目](#削除の根拠-7-項目)の前書きのとおり
  - 区分「追従修正・書き直し・統合元」（今回の実行より前からあるテスト）: [既存テストの判定](#既存テストの判定)の葉の語。削除候補は削除の根拠 7 項目とユーザーの承認を要し、「取り下げる」とは書かない
- severity: **high** = 回帰を見逃す状態を作る（唯一の証明の喪失・規約が必須とするテストの統合や削除）/ **medium** = 現実的な回帰を見逃すのに、名前や形がそれを守っているように見せる（偽の証明・空回りする negative・振る舞いを名乗るのに何も守っていないテスト等）/ **low** = 回帰の見逃しにつながらない重複・名前のずれ・記録と前提の不備。記録漏れは low に固定する（判定役には、この実行で書いたものかユーザーの作業中のものかを区別できないため。見込みは confidence で表す）
- confidence: **high** = 一次資料（コード・テスト・規約の `file:L`）で直接示せた / **medium** = 読解による推論を含む / **low** = 推測が中心
- 該当が無いブロックも見出しは残し、「該当なし」と書く
