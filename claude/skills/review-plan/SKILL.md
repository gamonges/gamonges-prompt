実装計画（plan.md）をスタッフエンジニアの視点でレビューし、実装前にアーキテクチャ整合性・リスク・実装順序・代替案を体系的に評価する。

**重要**: ソースコードは一切変更しない。`./tmp/plan-review.md` のみ出力する。
**規約**: CLAUDE.md の Skills 共通規約に従う

## 補助ドキュメントへの参照

| 補助ドキュメント | 読むタイミング |
|------------------|----------------|
| `./reference/report-template.md` | フェーズ 4 で `plan-review.md` を出力する時 |

「念のため全部読む」は禁止。表のトリガー条件に該当する場合のみ読み込む。

## パラメーター

`$ARGUMENTS` で実装計画ファイルのパスを指定できる。省略時は `./tmp/plan.md` を使用する。

## ワークフロー上の位置付け

| 前工程 | 本コマンド | 後工程 |
|--------|-----------|--------|
| `/design` 計画作成 | `/review-plan` 計画レビュー | `/revise` 計画修正 → `/implement` 実装 |

## 実行条件

以下のファイルが存在することを確認する:

- `$ARGUMENTS`（指定がない場合は `./tmp/plan.md`）— 実装計画
- `./tmp/coupling-gate.md`（任意）— `/coupling-gate` の結合バランスチェック結果。存在する場合は指摘に統合する

ファイルが存在しない場合:

- プロセスを即座に停止する
- どの条件が満たされていないかをユーザーに報告する
- レビューを続行しない

## スタッフエンジニアの思考フレームワーク

通常のコードレビュー（`/review`）とは異なり、以下の視座で計画を評価する:

- **システム思考**: 変更がシステム全体に与える影響（他モジュールへの波及、データフローの変化）
- **長期的視点**: 技術的負債の蓄積、将来のメンテナンスコスト、拡張性への影響
- **横断的関心事**: セキュリティ、パフォーマンス、オブザーバビリティ、障害耐性
- **組織的影響**: チーム境界をまたぐ変更、必要な知識・スキルの有無
- **プラグマティズム**: 適切な複雑度か（オーバーエンジニアリング / アンダーエンジニアリング）

## 指摘の重要度

| レベル | 意味 |
|--------|------|
| ❌ Critical | 計画の修正が必須。このまま実装すると問題が生じる |
| ⚠️ Warning | 修正を推奨。品質・保守性に影響する |
| ℹ️ Note | 検討・確認を推奨。判断はユーザーに委ねる |
| 💡 代替案 | 検討に値する別アプローチの提案 |
| ✅ Good | 計画の良い点（積極的に評価する） |

## Finding Format Standard

**すべての指摘で以下の形式を使用する:**

```
- `plan.md:L42` — 指摘内容
```

- 計画内の記述への参照は `plan.md:L{number}` 形式
- コードベース内のファイルへの参照は `src/full/path/to/file.tsx:L42` 形式（相対パス必須）
- 行番号が特定できない場合はセクション名で参照: `plan.md (ステップ 3)`

## 総合判定（3段階）

| 判定 | 意味 | 次のアクション |
|------|------|----------------|
| **LGTM** | 軽微な指摘のみ。実装に進んでよい | `/implement` |
| **要修正** | 指摘事項を反映してから実装すべき | `/revise ./tmp/plan-review.md` |
| **要再設計** | 根本的なアプローチの見直しが必要 | `/design`（再設計） |

## 実行プロセス

### フェーズ 1: 実装計画の読み込み

- [ ] 実装計画ファイル（`$ARGUMENTS` または `./tmp/plan.md`）を読み込む
- [ ] `./tmp/context.md` が存在する場合は、元の要件・コンテキストも読み込む
- [ ] 計画の全体構造を把握する:
  - 概要・目的
  - 実装ステップの数と依存関係
  - 変更対象ファイル一覧
  - テスト方針
  - 影響範囲

### フェーズ 2: コードベース調査

計画が前提としている内容を実コードと照合し、机上の空論を防ぐ。

- [ ] **ファイル・モジュールの存在確認**: 計画で参照されているファイルパスが実際に存在するか
- [ ] **既存パターンとの整合**: Serena MCP でセマンティック検索を行い、計画のアプローチが既存のコードパターンと整合するか
- [ ] **依存関係の検証**: 計画が前提としている依存関係（ライブラリ、モジュール間の関係）が正しいか
- [ ] **ライブラリ情報**: Context7 MCP で、計画が使用するライブラリ・API の使い方が正しいか確認（必要に応じて）
- [ ] **共有リソースの書き込みエントリポイント照合**: plan.md の並列性マトリクスが共有リソースを記載している場合、そのリソースに書き込む実コードパスを grep で洗い出し、記載された対策範囲と一致するか照合する（書き込みエントリポイントの定義は `phase-details.md` の「書き込みエントリポイントの完備性」を参照。1 系統のみ対策されている場合は Critical として指摘）
- [ ] **安全性根拠の区別**: plan.md の並列性マトリクスにおける「安全」の根拠が排他制御によるものか、メッセージ順序保証のみに依存していないかを確認する（`phase-details.md` の「安全性根拠の区別」参照）。後者のみを根拠にしている場合は Critical として指摘する

### フェーズ 3: 観点を切り替えたレビュー

同じ抽象度で反復しても見逃される構造的欠陥（統合点見落とし / Decision 矛盾 / 並列性未定義 / 根拠なし断言 / 抽象 IF 放置 / 完了パス漏れ）は、**観点を意図的に切り替える**ことで検出する。

**完了条件**: 下表の 3 観点すべてを通過し、かつ新規 finding が出なくなった時点。観点を跨いだ指摘が出た場合は、関連する観点に戻って再確認する。

観点は 3.1 → 3.2 → 3.3 の順で扱う（後の観点が前の観点の結論に依存するため）。横断観点・3.5・3.6 は 3 観点すべてを通過した後の共通チェック。

| 観点 | 探すもの |
|------|---------|
| **機能の正しさ**（3.1） | アルゴリズム / 型 / Decision の妥当性 / 既存パターン整合 / よりシンプルな代替 |
| **既存システムとの境界**（3.2） | CDK / Step Functions の経路 / backend API シグネチャ / 並列共有リソース / skip 提案の副作用 / 実装順序・依存関係 |
| **暗黙の前提**（3.3） | 「変更不要」「透過」「skip しても OK」の根拠 / Stub と本番の gap / Decision 間の論理矛盾 / HTTP contract の concrete 化漏れ / 完了パスツリーの網羅性 |

#### 3.1 観点: 機能の正しさ

- [ ] 既存のアーキテクチャパターン（レイヤー構成、命名規則、ディレクトリ構造）と整合するか
- [ ] 新しいパターンを導入している場合、その必然性と一貫性は妥当か
- [ ] モジュール間の責務分担は明確か
- [ ] インターフェース設計（API 境界、型定義）は適切か
- [ ] よりシンプルな解決策が存在しないか / 既存ユーティリティを活用できる箇所はないか
- [ ] ライブラリやフレームワークの標準機能で代替できる部分はないか
- [ ] YAGNI 原則に反する過剰な設計はないか
- [ ] **結合バランス**: `./tmp/coupling-gate.md` が存在する場合はその判定を優先参照し、存在しない場合も統合強度×距離×変動性の観点でTight Coupling/Low Cohesionの危険域がないか確認する（`coupling-gate`スキル参照）

#### 3.2 観点: 既存システムとの境界

- [ ] エッジケース・障害シナリオ（ネットワークエラー、データ不整合、競合状態）への対処が計画されているか
- [ ] **統合点トレース**: skip / 削除 / 短絡提案の副作用（downstream の前提条件 / 監視 / 既存テスト）が追跡されているか
- [ ] **並列性マトリクス**: 並列実行で共有リソース（DB connection / S3 prefix / API レート）の衝突パターンが整理されているか
- [ ] ステップ間の依存関係は正しく定義されているか / 並列化可能なステップが直列になっていないか
- [ ] テストファーストのアプローチが適切に組み込まれているか
- [ ] 各ステップの粒度は適切か（大きすぎ / 小さすぎ）/ 途中で動作確認できるマイルストーンが設定されているか

#### 3.3 観点: 暗黙の前提

- [ ] **「変更不要」「透過」根拠**: 計画内で「変更不要」「透過」「影響なし」と書かれた箇所に grep / read 根拠が併記されているか
- [ ] **Decision 間整合性**: Decision を 3 個以上立てた場合、相互整合性マトリクス（前提 / 衝突しない相手 / 責任分界）が記述されているか
- [ ] **HTTP contract concrete 化**: 抽象 IF（型シグネチャ・OpenAPI 概略）に method / path / header / body / response の 5 要素 + curl 例が併記されているか
- [ ] **完了パスツリー**: 成功 / 失敗 / partial / retryable / cancelled 等の分岐が tree で書き出され、各葉に AC が割り当たっているか
- [ ] Stub と本番の gap（テスト時のモックと本番挙動の差）が明示されているか

> 観点 3.2・3.3 の太字項目の詳細テンプレートと BAD/GOOD 例は `../design/reference/phase-details.md` の「構造的欠陥防止チェックリスト」を参照。

#### 横断観点（3 観点すべてを通過した後に実施）

- [ ] セキュリティ上の懸念（認証・認可、入力バリデーション、クロステナント）はないか
- [ ] パフォーマンスへの影響（N+1 クエリ、不要な再レンダリング、大量データ処理）は考慮されているか
- [ ] マイグレーション・デプロイ時のリスク（ダウンタイム、ロールバック手順）は考慮されているか

#### 3.5 確信度サマリの優先確認

`/design` で生成された plan.md に `## 確信度サマリ` セクションが含まれている場合、本レビューでは **low confidence のステップを優先的に検証する**。

- [ ] `## 確信度サマリ` の low 行を抽出する
- [ ] 各 low ステップの「検証ステップ」が実施済みかを確認する
- [ ] 未実施の場合は **Critical** として指摘し、検証ステップの実施を要求する
- [ ] 検証ステップ実施後も low のままなら、根本原因を再分析するよう推奨する

#### 3.6 運用委譲パターンの検出

- [ ] plan.md 内で「運用で対応」「運用ドキュメントに記載」「運用件数を抑える」等の運用委譲フレーズを検索する
- [ ] 該当箇所ごとに「コード側ガードで代替可能か」を確認する
- [ ] 判断はユーザーに委ねるため、指摘は **Warning** として記録する（Critical にはしない）

### フェーズ 4: レビューレポート生成

`./tmp/plan-review.md` にレポートテンプレート（`./reference/report-template.md`）へ沿って出力する。該当なしの区分はセクションごと省略する。

### フェーズ 5: 完了報告

以下の内容をユーザーに報告する:

- **総合判定**（LGTM / 要修正 / 要再設計）
- 各区分の指摘件数
- 特に重要な指摘事項（Critical がある場合はその要約）
- 次のステップの案内:
  - **LGTM の場合**: `/implement` で実装開始
  - **要修正の場合**: `/revise ./tmp/plan-review.md` で計画を修正
  - **要再設計の場合**: `/design` で再設計
