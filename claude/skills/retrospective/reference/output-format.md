# 振り返りレポート出力フォーマット

> SKILL.md フェーズ 4 で出力するレポートのテンプレートと、Phase 2-3 の分析観点。

## レポートテンプレート

```markdown
# 📊 [日付] プルリクエスト振り返り

## 作成したプルリクエスト一覧

- PR #xxx: タイトル
  - 規模: +xxx/-xxx 行、x ファイル
  - 状態: [Open/Merged/Closed]
  - 概要

## 🎯 実装内容の分析

### 技術的な特徴

### アーキテクチャと設計パターン

### コード品質の観点

## 🌟 あなたの実装スタイルの特徴

### 強み

### 傾向

## 📚 得られた学び

### 技術的な学び

### 設計の学び

### プロセスの学び

## 💡 今後に活かせる観点

**提案件数: N 件**

| # | 区分 | 提案 | 対象 skill / ファイル | 変更箇所 |
|---|------|------|---------------------|---------|
| 1 | すぐに | … | `claude/skills/<name>/SKILL.md` | `:L{n}` の … |
| 2 | 中長期 | … | **運用ルール（skill 化不可）** | — |
| 3 | 深掘り | … | `claude/skills/<name>/SKILL.md` | `:L{n}` の … |

## 🎓 今日の教訓
```

### 「今後に活かせる観点」の出力要件

- **提案 1 件ごとに「どの skill のどこを変えるか」を書く。** 書けないものは「**運用ルール（skill 化不可）**」と明示する。skill 名の欄が無いと提案が改善へ着地せず、振り返りが読み物で終わる（実績: 8 提案のうち skill 名を伴うものが 0 件だった回がある）
- **提案件数を明記する。** 圧縮・要約の過程で提案が落ちるため（実績: memory の要約フィールドへ圧縮した際に 8 提案 → 5 提案へ減った）、件数があれば脱落を検知できる
- **時間軸は「区分」列（すぐに / 中長期 / 深掘り）で表す。** 時間軸ごとに小見出しを分けると件数の明記が 3 箇所に散り、脱落の検知が効かなくなる

## Phase 2: 実装内容の分析観点

### 技術的側面

- アーキテクチャパターン（レイヤード / DDD / クリーンアーキテクチャ等）
- 設計パターン（Adapter / Repository / Value Object 等）
- データフローと責務の分離
- テストカバレッジと品質保証の方法

### コード品質

- 命名規則の一貫性
- コメントとドキュメンテーション
- エラーハンドリング
- パフォーマンスへの配慮

### バックエンド・フロントエンド連携（該当時）

- API 設計の一貫性
- データ変換の責務配置
- 型安全性の確保
- UX/UI への配慮

## Phase 3: 学びと知見の抽出

### 実装の傾向と特徴

- 実装スタイルの特徴
- よく使うパターンやアプローチ
- 強みとして現れている点

### 得られた学び

- 新しく学んだ技術や手法
- うまくいった設計判断
- 効果的だったアプローチ

### 改善の余地

- さらに良くできる点
- 今後取り組むべき課題
- 強化すべきスキル

## 出力スタイル

- Markdown 形式、絵文字で視認性向上
- コードブロックで具体例提示
- セクションごとに整理

## 振り返りのポイント

### 技術的観点

- 採用した設計パターンとその妥当性
- テスト戦略とカバレッジ
- パフォーマンスとスケーラビリティ
- セキュリティと堅牢性

### プロセス観点

- PR 作成までの時間
- レビューで指摘された点
- コミュニケーションの質
- ドキュメンテーションの充実度

### 成長観点

- 新しく習得した技術やパターン
- 過去の自分との比較
- チームへの貢献度
- 次回に活かせる改善点

## 期待される成果

- ✅ 自分の成長を可視化
- ✅ 実装パターンの傾向を把握
- ✅ 強みと改善点が明確化
- ✅ チーム全体の知見として共有
- ✅ 継続的な学習習慣の定着
